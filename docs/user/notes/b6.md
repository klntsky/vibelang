## Proposed markers: 2

- `src/schema/085-introduction.md`, configuring compiler prerequisites. Which exact synchronous Schema builders, `.pipe` methods, and Effect data combinators receive compiler-shipped trusted contracts? STYLE explicitly shows ordinary calls for unchanged data APIs, while D5 requires a declared trust boundary for ordinary imported functions. The proposed convention permits the synchronous description builders and data combinators used throughout these pages. Throwing parsers, constructors, generated comparison/formatting callbacks, and derivation functions that can throw use explicit boundaries. This is a documentation assumption, not a claim that compiler contracts already exist.
- `src/schema/099-standard-schema.md`, choosing synchronous or asynchronous validation. How should the compiler type and lower a Standard Schema validator that returns either a synchronous validation result or a Promise? The example treats invocation inside `Effect.tryPromise` with native `Promise.resolve` as an explicit foreign-code boundary; the language documents Promise boundaries but does not specify this mixed-return standard interface.

## Conflicts and precedence

The spec is being revised concurrently. These observations concern the Part I/II text read at the start of this batch; they are not requests to revert later spec edits.

- Service declaration examples still used `service`, while D1 requires abstract classes with fully contracted abstract members. The service example in `091-transformations.md` follows D1.
- Control declarations still used `control`, while D2 requires abstract classes extending the global `Control`. No new control-operation syntax is introduced in this batch.
- Earlier examples imported `Data.TaggedError`, while D3 and STYLE use global `TaggedError` for ordinary errors and `Schema.TaggedError` for serializable errors. The pages use the current global prelude and the Effect 4 schema error-class API.
- The spec described modules as imported and listed `transfer` among proposed globals. D4 makes `Effect`, `Schema`, and `Layer` global, and D16 keeps `transfer` internal. These pages omit redundant global imports in EffectScript and expose no `transfer` API.
- The spec's plain-function sections allowed direct foreign calls and classified thrown exceptions as defects. D5 requires explicit `Effect.try` or `Effect.tryPromise` boundaries or trusted contracts. The examples use explicit boundaries for throwing synchronous interpreters and foreign interfaces; the remaining synchronous builder trust gap has the Proposed marker above. STYLE's statement that unchanged Schema/data builders are plain calls is the relevant tension between STYLE and D5.
- The spec showed direct `fetch`, `node:crypto`, ambient time reads, and other platform calls. D6 requires Effect modules for platform work, and D5 excludes ambient time/randomness reads. Schema conversions here use a service, fixed date parsing, or Effect APIs; no `.es` example calls a platform API.
- The spec still marked program thunks, `pipe`, `wire`, block-owned `fork`, and public handlers as proposals or open choices. D7, D8, D16, and D19 settle those choices. Passing `() => value` to a schema default or Effect callback follows the settled program-value rule without an extra proposal marker.
- Part II included `Effect.sync` bodies in the plain-compilation category and restricted pure recursion to tail-call loops, with other pure recursion on heap frames. D10 excludes every Effect boundary from plain compilation and allows pure recursion on the host stack. Examples use plain callbacks only when their bodies have no Effect operations; a callback passed through `Effect.try` is an explicit Effect boundary.
- Part II promised per-call-site specialization for higher-order functions. D11 postpones it. These pages do not promise specialized compilation of Schema callbacks.
- Partial annotation spelling remains open under D12/O7 and STYLE. Examples use full contracts where a declaration has no body, infer ordinary function contracts, and use explicit pure callback result types to break recursive schema inference. They introduce no partial-contract syntax.

## Upstream versus local API observations

- The pinned default-constructor page says `makeEffect` fails with `SchemaError`. Local `Schema.BottomWithoutNew.makeEffect` and `SchemaParser.makeEffect` expose `SchemaIssue.Issue` directly. `089-advanced-usage.md`, `096-classes.md`, and `097-default-constructors.md` follow the local implementation and explain the distinction from decoding failures.
- The pinned constructor examples print detailed validation text for throwing construction. Local `make` documents a generic `Error("Schema validation failed")` with the issue in `cause`. The constructor pages describe that behavior and show issue formatting explicitly.
- The upstream annotations table describes `parseOptions` annotations as node overrides, while its getting-started page says annotations do not override parser options. The local parser and Schema annotation definitions provide no execution hook for a `parseOptions` schema annotation. The pages pass options to interpreters and do not present arbitrary metadata as an execution control.
- Recursive callbacks retain both decoded and encoded interfaces when they differ. The Iso page uses a structural representation, not JavaScript object identity, despite the stub's phrase "identity codecs".
