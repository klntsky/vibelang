## Conflicts in the sources of truth

These refer to the spec as read at the start of the batch, while another writer was revising it. They are recorded rather than fixed outside the authorized directories.

- **Service declarations:** the spec's first examples and dependency-injection section use `service`; D1 requires abstract classes. The Redacted page uses an abstract service class. Imported platform service keys are accessed with the existing `Effect.service` API, so no new callable-key syntax is assumed.
- **Control declarations and prelude:** the spec uses `control`, imports modules now in the prelude, and lists `transfer` as a public built-in. D2 uses `abstract class ... extends Control`; D4 defines the globals; D16 keeps `transfer` internal. No page in this batch exposes the old control syntax or `transfer`.
- **Program spelling and pipelines:** the spec labels no-argument programs and program-aware `pipe` as unresolved proposals. D7 and D8 settle both, including no pipeline operator in v0. Pages use no-argument programs without proposal markers.
- **Plain-code trust and failure classification:** the spec's TypeScript-interop and call-rule sections allow arbitrary bare plain calls and describe their exceptions as defects. D5 requires a trusted contract or an `Effect.try`/`Effect.tryPromise` boundary; trusted built-ins can also expose expected failures. Pages use explicit boundaries for imported plain helpers and Path's synchronous service methods. Direct operations on unchanged Effect data modules follow STYLE.md's explicit instruction to build those values with plain calls. The compiler still needs a concrete catalog of trusted standard-library contracts; these pages do not define its metadata format.
- **Platform APIs:** the spec's promise example calls browser `fetch` from `.es`; D5 and D6 require Effect platform APIs instead. Platform pages use FileSystem, Path, Terminal, Logger, and runtime adapters, with no native API calls from `.es`.
- **Plain compilation and recursion:** the spec includes `Effect.sync` bodies among plain-compilation candidates and still discusses tail-loop restrictions and the pure-recursion choice as open. D10 excludes every Effect boundary, preserves evaluation order, and settles pure recursion on the JavaScript stack. Protocol proposals require bodies with no Effect operations; no recursion claim is carried into these pages.
- **Higher-order specialization:** the spec's callback section says the compiler specializes per call site. D11 requires higher-order frames in v0. No page promises specialization.
- **Background lifetime:** the spec still labels block-owned `fork` as proposed. D19 settles it. No page in this batch changes or relies on an alternative fiber lifetime.
- **TypeScript control interop:** the spec broadly says TypeScript Effect contracts pass through unchanged. D20 rejects calls whose R contains a control operation in v0. No such imported operation is used here.
- **Mixed causes:** the spec's broad statement that catch handles typed errors needs D13's stricter qualification for mixed causes. The Cause page explicitly says any defect or interruption prevents ordinary catch from handling that cause. Cleanup failure preservation and resource ownership follow D14 and D15.

No direct contradiction between STYLE.md and DECISIONS.md required a different language rule in these pages. EffectScript error examples use global `TaggedError` (D3); `Data.Error` remains available for ordinary errors.

## Upstream and API verification

Fetched each stub's corresponding MDX with `gh api` from `Effect-TS/website`, commit `9b2ad8c7569b7ca65562185052c1122167eae906`, under `apps/web/src/content/docs/v4/`. All prose and examples were written afresh. The local package at `experiments/node_modules/effect` identifies itself as 4.0.5; its `src` files were used to check API exports, service methods, signatures, and relevant implementation behavior.

Notable upstream discrepancies resolved against local source:

- The HashSet page contains an older reference-equality claim for objects, contradicted by its own later section. Local Equal and Hash implementations compare plain records structurally. The new pages use structural equality and mention immutability because equality and hashes are cached.
- The Duration page calls durations nonnegative. Local 4.0.5 supports negative finite values and both infinity directions. The new page documents signed values.
- The PlatformLogger page says omitting `batchWindow` writes immediately. Local `Logger.toFile` uses `options?.batchWindow ?? 1000`, flushes on scope closure, and ignores errors from later file writes. The new page describes these actual semantics.
- The Runtime page gives an incomplete interruption exit-code account. Local `Runtime.defaultTeardown` uses 0 for success, 130 for interruption-only causes, and the configured error exit code or 1 for other failures.
- Upstream uses several old heading names such as `unsafeFromString`, while local exports use `fromStringUnsafe`. The prose and examples use current local export names.
- Upstream DateTime examples mix host-local dates with zone adjustment. New examples use explicit UTC strings or explicit calendar parts and distinguish attaching a zone from interpreting local wall time.

`Exit` extends Effect; `Option` and `Result` do not. Exit constructor calls therefore run under the settled call rule. The Exit page uses `Effect.exit` to obtain exit data and explains one-level execution of an Effect-returning call. Platform adapters are separate packages, absent from the local experiments installation; adapter export names follow the fetched upstream pages. Core APIs used by their examples were checked locally.

Validation: all 117 code fences using `ts` parsed with the installed TypeScript parser, with no syntax errors. A namespace/member audit checked referenced core Effect APIs against local exports (including the `try_ as try` alias); platform service members were checked against their interfaces. Executed assertions against the local package verified decimal arithmetic, chunk updates, cause reasons, time zones and formatting, signed durations, structural equality and hashes, set operations, Option ordering, ranges, redaction, and runtime exit codes.
