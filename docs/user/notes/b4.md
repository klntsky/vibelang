## Source conflicts and resolutions

- **Plain library calls:** STYLE.md says unchanged Effect modules build values with plain calls. D5 requires an explicit boundary or a trusted contract for other plain JavaScript/TypeScript functions, but neither the decision log nor Parts I/II enumerate trusted Effect library builders. Marked the Stream (including supporting Filter and Cause builders), Sink, Brand, and Match builder assumptions above. Existing standard-library usage conventions cover supporting value modules such as Option and Schedule; arbitrary returned functions still have explicit boundaries in the Brand and Match pages.
- **Service declarations:** The spec repeatedly uses the `service` keyword, including its introductory comparison and dependency-injection examples. D1 and STYLE.md use abstract classes with fully annotated abstract members. All service examples in this batch use that form.
- **Control declarations and public operations:** The spec uses `control` declarations and presents `transfer` as a user-visible operation. D2 uses abstract classes extending `Control`; D16 keeps `transfer` internal. This batch introduces neither old syntax nor a public transfer API.
- **Prelude and errors:** The spec imports Effect, Layer, and Data in examples, describes its built-ins as proposed, and uses `Data.TaggedError`. D3/D4 and STYLE.md establish the global prelude and global `TaggedError`. This batch imports modules outside the prelude and uses the global tagged-error constructor.
- **Program values and pipelines:** The spec marks zero-argument programs and `pipe` as proposals/open O1. D7/D8 settle them for v0. These pages teach program functions and the global `pipe` as established rules, without repeating obsolete proposal markers.
- **Plain calls and exceptions:** The spec's TypeScript-interoperability chapter and call table permit arbitrary plain calls, treating exceptions as defects, and discuss that as O11. D5 replaces that rule with trust or an explicit boundary. The spec's error rules also say only explicit `throw` adds to E, conflicting with D5's trusted built-in exceptions and explicit boundary errors. This batch uses explicit boundaries for foreign brand constructors and returned matchers, Effect clock reads, and EffectScript errors.
- **Platform APIs and time:** The spec's Promise examples call browser `fetch` from EffectScript, and some resource examples invoke raw platform-shaped APIs. D5/D6 and STYLE.md require Effect modules instead. The pinned upstream pages also use `setTimeout`, `Date.now`, `new Date`, Node assertions, and console calls. This batch uses Effect timing/logging, service interfaces, a local EffectScript test assertion helper, and TypeScript adapters for raw callback registration.
- **Plain compilation and recursion:** The spec says trusted `Effect.sync` work can compile as plain synchronous code, gives a special recursion eligibility rule, and leaves O10 open. D10 excludes every Effect boundary from plain compilation and settles pure recursion as ordinary JavaScript recursion. Pure callbacks here perform no Effect operation and have no expected failure; no old recursion claims are taught.
- **Higher-order specialization:** The spec claims per-call-site specialization. D11 says higher-order functions use frames in v0. These pages make no specialization or performance promise.
- **Mixed causes:** The spec's general catch examples do not state D13's mixed-cause restriction. The Stream error page explicitly says ordinary `catch` propagates a cause containing a defect or interruption rather than handling its typed-failure component.
- **Fork lifetime:** The spec labels `fork` and its block lifetime as proposed/open O5. D19 and STYLE.md settle block ownership. TestClock examples use `fork` as established syntax and rely on block-exit interruption for recurring work.
- **Resource ownership and cleanup:** D14/D15 and STYLE.md govern ownership and preservation of cleanup failures. Stream resources are acquired without `using` within a stream-owned Scope; examples scope the complete resource-using pipeline. The resource page warns against returning a Stream that refers to an already-released local `using` resource.

## Effect API verification and upstream corrections

Checked all qualified Effect-module names used in the pages, including reserved-name export aliases such as `Stream.catch`, `Effect.let`, `Deferred.await`, `Match.null`, and `Match.undefined`, against `experiments/node_modules/effect/src`. Also checked unqualified variant names mentioned in prose against their module exports and checked relevant call signatures and implementations. The installed package declares version 4.0.5.

`TestClock` comes from `effect/testing`; `TestClock.layer()` is a function. Platform runtime imports and `it.effect` follow STYLE.md and the pinned upstream runtime guidance; these live in separate packages, outside the supplied `effect/src` tree, and those packages are not installed in `experiments/node_modules`.

The following upstream details needed clarification or correction:

- `Stream.scoped` wraps a Stream, not an Effect; `Stream.fromEffect` introduces resource acquisition. Scope the complete pipeline that uses the resource.
- `Stream.paginate` emits the members of a returned batch and uses `Option` for the next state. `Stream.unfold` emits one element per step and stops with `undefined`.
- `Cause.done()` returns an Effect, so the EffectScript call runs the completion signal directly.
- `Stream.partition` takes a Filter. Both branches need active consumers to avoid bounded-buffer deadlock. `groupByKey` produces a Stream of key/group-Stream pairs; concurrent group consumption avoids the same distribution problem.
- `Stream.timeout` ends normally. `Stream.timeoutOrElse` supports failure, cause failure, or a replacement stream, with a timeout per upstream pull. Older upstream subsection names such as timeoutFail are not APIs used by these pages.
- `Sink.mapEnd` sees only the remainder of an already-pulled batch, not the whole unread source. Examples explicitly contrast one-batch and rechunked sources. `ignoreLeftover` does not drain input.
- Repeated sinks can emit a final empty result when input ends exactly at a completed sink boundary. Filtering/grouping guidance includes that behavior.
- Weighted `Sink.fold` examples stop after reaching the cost threshold and can overshoot it; they are not strict maximum-weight packing.
- `Effect.whileLoop` in 4.0.5 takes one options object with `while`, `body`, and `step`, and returns void. The upstream prose describes an initial-state/result-collection form not present in the installed source.
- Brand refinement uses `Brand.make`, and invalid constructor input throws `Brand.BrandError`. The plain constructor boundary is explicit in EffectScript.
- Match callbacks are ordinary synchronous callbacks. None performs Effect work; use ordinary branching for those cases.
