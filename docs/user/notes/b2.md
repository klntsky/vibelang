## Conflicts found in the supplied references

The observations below refer to the spec text read during this batch. Another writer is revising that file concurrently. These notes do not request changes outside this batch.

- **Service declarations.** Part I's first example and dependency-injection topic, and Part II's declaration examples, use the proposed `service` keyword. D1 and STYLE require fully abstract classes without an `extends` clause or type parameters. The pages use abstract classes, explicit abstract members, nominal identity, and static layer fields.
- **Control declarations and public continuation operations.** The handlers topic uses `control`, lists `transfer` publicly, and leaves public handler exposure open. D2 uses abstract classes extending global `Control`; D16 settles the four public operations and keeps `transfer` internal. The batch does not introduce control syntax or advertise `transfer`.
- **Error imports and the prelude.** Older Part I examples import `Effect`, `Layer`, and `Data` for tagged errors, and the prelude description omits newer globals while including `transfer`. D3, D4, and STYLE make `Effect`, `Layer`, `Schema`, and `TaggedError` global and exclude public `transfer`. The pages use global `TaggedError`; `Data.Error` is imported only for the untagged-error topic.
- **Foreign calls and exceptions.** The functions/calls, TypeScript-boundary, and call-rules topics allow bare plain TypeScript calls and describe any exception as a defect; the Promise example calls browser `fetch` directly. D5 requires an explicit trust boundary for other plain foreign calls, forbids platform APIs, and gives built-ins trusted exception contracts. D6 requires Effect's platform modules. These pages avoid platform calls, foreign unwrapped helpers, and the blanket claim that every built-in exception is a defect.
- **Programs and pipelines.** The programs topic and Part II still call nullary program functions and `pipe` open proposals. D7 and D8 settle those spellings and reject a v0 pipeline operator. The pages use nullary functions and global `pipe` without Proposed markers.
- **Plain JavaScript compilation.** Part II includes trusted `Effect.sync` bodies in the synchronous class, restricts general pure recursion to heap frames, and leaves that recursion rule open. D10 excludes all Effect operations from the plain path and compiles eligible pure recursion to the host stack. The pages describe synchronous callbacks as eligible only when they perform no Effect operations and cannot fail with typed errors.
- **Higher-order specialization.** Part II says higher-order functions specialize per call site. D11 uses frames in v0 and defers specialization. The batch makes no specialization claim.
- **Callback contracts.** D57 now specifies partial return annotations with explicit `infer Name` slots. D12 still makes contract-free callback parameters accept any contract. Omitted slots in a return annotation with a body are ES2003; defaults in other type positions keep their TypeScript meaning.
- **Mixed causes and catch.** The spec's general “catch handles typed errors” descriptions omit the mixed-cause condition. D13 requires propagation of the entire cause when any defect or interruption is present. The error overview, expected-error, fallback, cause, and cleanup pages state that condition for ordinary `try`/`catch`.
- **Resource ownership.** The resources topic broadly describes a block as supplying a scope. D14 and STYLE clarify that only `using` acquisitions belong to that block; other acquisitions retain the caller's scope even beside a `using`. The scope page includes a mixed-ownership example, and service factories acquire long-lived resources without lexical `using`.
- **Cleanup failure.** The spec's general cleanup rule preserves failures, while D15 additionally makes preservation explicit under abandonment and interruption. The batch consistently says cleanup failures are retained, and never presents cleanup as replacing and dropping an earlier failure.
- **Continuation requirements and tail resume.** The handler examples leave the `resumeWith` requirement restriction unstated; the spec also presents the generator-shaped handler form. D17 requires injected `R = never`, and D18 requires tail-resume compilation. This batch introduces no conflicting continuation examples.
- **Fork lifetime.** The concurrency topic calls block-owned `fork` proposed. D19 settles that lifetime and names `Effect.forkScoped` and `Effect.forkDetach` for longer lifetimes. The timeout page describes explicit fiber lifetimes without treating block ownership as open.
- **TypeScript control-operation interop.** The spec broadly promises unchanged TypeScript Effect interop. D20 excludes TypeScript functions whose requirements contain a control operation in v0. The batch makes no unrestricted control-operation interop promise.
- **Layer acquisition boundaries.** The dependency-injection topic already says layers build once per `provide`; D21 and STYLE confirm this and prescribe `ManagedRuntime` for multiple entry points. The layers and memoization pages distinguish one shared graph from separate local provision boundaries. This is a clarification, not an unresolved conflict.

No conflict between STYLE and DECISIONS affects the examples in this batch. The pages follow DECISIONS for the older spec passages above.
