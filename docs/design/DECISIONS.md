# VibeLang decision log

Working log, 2026-10-16. The spec (`src/`), the prototypes, and the end-user docs follow this file. Each entry says who decided: **Will** for the owner's decisions, **default** for calls made to produce a confident spec, which Will can overturn. Evidence paths are relative to the repository root.

## Declarations: TypeScript syntax only

**D1. Services are abstract classes** (default, from Will's idea). The `service` keyword is removed.

```ts
abstract class Users {
  abstract find(id: string): Effect<User, UserNotFound, never>
  abstract rename(id: string, name: string): Effect<void, UserNotFound, never>

  static readonly layer = Layer.effect(Users, () => {
    const db = Database()
    return { find(id) { … }, rename(id, name) { … } }
  })
}
```

- A class declared in a `.vibe` file is a service when it is `abstract`, has no `extends` clause, has no type parameters, and every instance member is abstract (methods with full contracts, `abstract readonly` values). Static members are allowed and stay on the class, matching Effect 4's `static readonly layer` idiom.
- The compiler makes service classes nominal: plain abstract classes with the same members collapse structurally, so providing one service type-checks as providing another, and the program dies at run time with `Service not found` (`experiments/scratch-abstract-services/probe.ts`).
- The key is derived from package, module path, and class name, and duplicates are rejected program-wide (unchanged from the earlier `service` rule).
- Emit: an Effect 4 `Context.Service` class, so TypeScript code sees an ordinary service. (Superseded by D45: the class form breaks `implements`; the emission is an interface plus a key class.)
- Implement a service with an object literal or a class that `implements Users`. `extends Users`, `new Users()`, `instanceof Users`, and a generic service class are errors with fixes.
- Evidence that this reuses no valid TypeScript meaning: `Users.find(id)` on an abstract member is TS2339 and `Users()` is TS2348 today. Evidence that it rarely collides with ordinary inheritance: Smithers has no abstract classes in 4,461 files; opencode has 5 in 3,235, and its only fully abstract one extends another class.

**D2. Control operations are abstract classes that extend the global `Control`** (default). The `control` keyword is removed.

```ts
abstract class Approval extends Control {
  abstract approve(request: string): Effect<boolean, ReviewBusy, never>
}
```

**D3. Errors use the global `TaggedError`** (Will). `class UserNotFound extends TaggedError("UserNotFound")<{ readonly id: string }> {}` is exactly Effect's `Data.TaggedError`. Errors that must be serialized use `Schema.TaggedError`, which real code already prefers (Smithers: 312 `Schema.TaggedError` to 133 `Data.TaggedError`). Deriving the tag from the class name is a later proposal, not v0.

**D4. The prelude** (default, from Will's "some things should be global"). In scope in every `.vibe` file without an import: `Effect` (namespace and the `Effect<A, E, R>` type), `Schema`, `Layer`, `TaggedError`, `Control`, and the built-ins `pipe`, `wire`, `fork`, `handle`, `resume`, `resumeWith`, `abandon`. Everything else is imported from `effect` as usual. Measured: `Effect` is imported by 77-81% of Effect files, `Schema` by 39-44%, `Layer` by 34-44%, and nothing else by more than 22% (Smithers 2,149 files, opencode 1,031). `Context` is not needed once services are classes; `Option` and `Array` would shadow JavaScript names.

## Code that is not Effect

**D5. Calls to non-Effect code need a declared trust level** (Will: "we need to be careful. We don't know if it can throw"; replaces the O11 recommendation).

| Callee | Rule |
| --- | --- |
| A function returning `Effect` (VibeLang or TypeScript) | Calls run it (unchanged) |
| JavaScript language built-ins: `String`, `Array`, `Math`, `JSON`, `Number`, `Object`, `Map`, `Set`, `RegExp`, deterministic `Date` parsing | Trusted contracts shipped with the compiler give each one a control class (`pure` or `sync`) and say which exceptions are expected failures (for example `JSON.parse` fails with `SyntaxError`) and which are defects |
| Platform APIs: `node:*` modules and browser globals such as `fetch`, `setTimeout`, `process`, `localStorage` | Not callable from `.vibe` files (EK4402); the error names the Effect module to use (D6) |
| Clock and randomness reads: `Date.now()`, `new Date()`, `Math.random()`, `crypto.randomUUID()` | Use `Clock`, `DateTime`, and `Random` so tests control them (EK4403) |
| Any other plain TypeScript or JavaScript function | Needs an explicit boundary: `Effect.try` or `Effect.tryPromise`, or a trusted contract declared once for that function. A bare call is an error (EK4401) whose fix offers both |

Pure helpers written in `.vibe` get inferred contracts and compile to plain JavaScript (D10), so most project code never needs a boundary.

**D6. The standard library is Effect's** (Will: "utilize that not necessarily reinvent the wheel with one to one node.js apis"). VibeLang adds no Node.js clones. Mapping: files → `FileSystem`; paths → `Path`; HTTP → `HttpClient` and `HttpApi`; child processes → `effect/process`; timers → `Effect.sleep` and `Schedule`; environment → `Config`; console → `Console` and `Effect.log`; time → `Clock` and `DateTime`; randomness → `Random`; crypto → `Crypto`; sockets → `effect/socket`; workers → `effect/workers`; terminal → `effect/cli` and `Terminal`; storage → `KeyValueStore`; SQL → `effect/sql`. Runtimes come from `@effect/platform-node`, `-bun`, and `-browser`.

## Calls, programs, and pipelines

**D7. Program values are functions with no arguments** (default; O1 option A).

**D8. No `|>` in v0; keep the `pipe(program, …stages)` built-in** (amended by D110; superseded by D154) (default). TC39's pipeline operator collides with "calls run": in `f(x) |> Effect.retry(%, p)` the call runs before the pipe sees it, and every stage that calls a combinator would run too. The pipe census shows the payoff is small: outside tests, 1.1% (Smithers) and 2.6% (opencode) of Effect pipes keep two or more stages once statements replace `map`, `flatMap`, `catch`, and `ensuring` (`docs/research/pipe-census.md`). Revisit if the TC39 proposal reaches Stage 3.

**D9. A function value passed where a plain JavaScript function is expected** (amended by D66, D112, D113) passes the plain-JavaScript variant if the function is eligible (D10); otherwise it is EK4301 (Fable review, finding 3).

**D10. Plain JavaScript compilation** (amended by D65, D67) (default, from Will's first feedback). A function compiles to plain JavaScript when it performs no Effect operation at all (control class `pure` or `sync`, which now excludes `Effect.sync` bodies and every other Effect boundary) and its E is `never`. Generated code keeps source evaluation order. `pure` permits inlining, never removal or reordering. Pure recursion runs on the JavaScript stack, like any JavaScript function; past the host limit it is a `RangeError` defect (resolves O10). Functions that can pause use heap frames and recurse without limit.

**D11. Higher-order functions compile to frames in v0**; per-call-site specialization comes later (Fable, finding 5).

**D12. A function type without a contract accepts any contract** (amended by D68) (default; P14 kept). It means "inferred from each call's argument", never `never`. Codex's review argues this is a partial-annotation spelling; it is listed with O7 for Will.

## Errors and cleanup

**D13. `catch` handles a failure only when the cause contains no defect and no interruption**; otherwise the whole cause propagates (Codex R1: `Effect.catch` swallows a defect from a mixed cause).

**D14. Only `using` acquisitions belong to the block.** A resource acquired without `using` belongs to the caller, even when the same block also has a `using` (Codex R8).

**D15. A failure during cleanup is never dropped**, including during explicit `abandon` under interruption (Codex R2b; kernel fix).

## Handlers and concurrency

**D16. v0 exposes `handle`, `resume`, `resumeWith`, and `abandon`. `transfer` stays inside the standard library** (producers' external iteration, the Stream adapter) until a continuation can no longer outlive its capturing fiber (Codex R5; G3). Resolves O3.

**D17. `resumeWith` runs code whose R is `never`** (Codex R7: an injected requirement resolves in the capture-time Context).

**D18. A clause whose last step is `resume` compiles to the kernel's tail-resume shape**, so producers run in constant stack (both reviews: the generator-shaped clause leaks two frames per element).

**D19. `fork` is block-owned** (amended by D96): the child is interrupted when its block exits. `Effect.forkScoped` (adds `Scope` to R) and `Effect.forkDetach` give longer lifetimes (resolves O5).

**D20. A TypeScript function whose R contains a control operation cannot be called from VibeLang in v0** (EK4202), because it may fork internally where the handler cannot reach (Codex R6).

**D21. Each `Effect.provide` builds its layers once.** Provide the application layer once, at `main`; programs with several entry points use `ManagedRuntime` (Fable, finding 6).

## Calls the confident spec needed (2026-10-16)

These fill gaps the decisions above left open. All are defaults; the spec's chapters cite them.

**D22. Effect's own packages are trusted** (default). An export of `effect` or an `@effect/*` package that does not return an `Effect` is a `sync` call whose exceptions are defects, exactly as inside `Effect.gen` today; a callback it calls synchronously follows D9. Values and functions that those exports return are trusted on the same terms: a `Brand` constructor and its methods, the function `Match.exhaustive` returns, and the stage a dual API returns when called without its data argument (amended 2026-10-16 after the docs consistency pass). Without this, D5 would demand a boundary around every `Option.map`. Evidence: D6 makes Effect the standard library; `Option` and `Result` are plain data in Effect 4 (`experiments/node_modules/effect/src/Option.ts:57`, `Result.ts:68`).

**D23. A trusted contract is a JSDoc tag on the TypeScript declaration** (amended by D100, D101, D108) (default; the spelling D5 left open). `/** @vibelang trusted */` declares a synchronous function `sync`; each `@throws {T}` names an exception class that is an expected failure and joins E; any other exception is a defect. The tag cannot be put on a function that returns a Promise or an `Effect`. A function from a package you cannot edit is trusted by re-exporting it from a `.ts` file you own, with the tag. Inside the callback of an explicit boundary (`Effect.try`, `Effect.tryPromise`, `Effect.sync`, `Effect.promise`), calls to plain TypeScript are allowed; platform APIs (EK4402) and clock or randomness reads (EK4403) are not. Reasons: TypeScript syntax only, as in D1; it is the same metadata channel the compiler already writes into declarations; `@throws` is standard JSDoc.

**D24. A call runs its result only when the call's type is `Effect<A, E, R>` itself** (amended by D90, D109) (default). A type that extends `Effect` and carries structure of its own (`Config`, `Exit`, a service class, a `TaggedError` instance) is data when a call returns it; calling such a value runs it; `new` never runs anything. Without this, `Config.String("X")` would read the variable before `Config.withDefault` could see it, and a function returning an error instance would fail. Evidence: `Config<T> extends Effect<T, ConfigError>` (`Config.ts:113`), `Exit` (`Exit.ts:89`), `Context.Key` (`Context.ts:68`), `YieldableError` (`Cause.ts:1312`). S22-3 amendment to S5-1 (effectscript-4a): at an Effect return boundary, a returned value assignable to the contract's declared success type A returns as data; only a returned Effect subtype that is not assignable to A runs. A contextual A of `unknown` or `any` names no success value: in a function with no written return contract, such as an arrow given to a tsc callback typed `(n) => Effect<unknown>`, a returned subtype runs (S5-1). A contract written on the function, such as `unknown!!`, names its success value, and the subtype returns as data.

**D25. `using` adds no masking policy of its own** (default; KERNEL-CHANGES.md left it open). An acquisition is masked or interruptible as its `Effect.acquireRelease` says: masked by default, so cancellation waits for the acquisition and then releases it; `{ interruptible: true }` for a wait on the outside world that cancellation must reach. Evidence: K15a-K15c.

**D26. Producers** (amended by D82) (default; resolves O4 and the design half of G12).
- `function*` in a `.vibe` file declares a producer; `yield` performs the built-in `Yield` operation. Generator-style Effect code (`Effect.gen`, `Option.gen`) stays in `.ts` files (EK1002).
- `for...of` is chosen by the iterated type: over a producer it installs a `Yield` handler (internal iteration); over a `Stream` it pulls with `Stream.toPull` and closes the stream when the loop exits; over any other iterable it is JavaScript's loop.
- To TypeScript, and wherever a `Stream` is expected, a producer is a `Stream`. The adapter runs the producer on its own fiber and hands over each element only when the stream pulls it, through a zero-capacity handoff (a one-element buffer would let the producer run one element ahead, prototype finding 26), so a pull from any fiber works and the producer never runs ahead; closing the stream interrupts that fiber, which runs the producer's cleanup. Reason: Stream operators such as `merge` pull on other fibers, and a continuation is fiber-affine (P5). G12 is the confirming experiment.

**D27. `wire` is a compiler intrinsic with a bounded contract** (default; resolves O6). It reads each argument's `Layer<Out, E, In>` type. An argument whose type does not name its outputs is EK3204; compose it with `Layer.provide`. Inputs no argument provides stay in the result's `In`, as with `Layer.provide`, and are reported with their dependency path (EK3201) where the program's R must be empty. Duplicate outputs are EK3202, cycles EK3203.

**D28. A `catch` over several expected failures receives the first** (default; K14a). The `catch` handles the cause as a whole, as `Effect.catch` does; `Effect.catchCause` sees every failure.

**D29. Proposals P1-P22 are the spec's rules**, as revised in Chapter 29 of the spec where the 2026-10-16 reviews broke them (default).

## Tooling (2026-10-16)

All defaults; Chapter 28 of the spec states them with examples. Package names are unscoped and follow the name (D125).

**D30. Installation.** (amended by D80, D83) Two npm packages. `vibelang` ships the fork's single native binary, `vibelang`, through per-platform optional dependencies, as `typescript@7` does. `vibelang` accepts every `tsc` flag and adds no new commands: `vibelang` type-checks and emits, `vibelang --noEmit` checks, `vibelang --watch` and `vibelang -b` rebuild, `vibelang --lsp --stdio` serves editors, and `vibelang --api` serves build tools. `vibelang-runtime` holds the kernel and the runtime helpers; generated code imports only it and `effect`. v0 supports `effect` 4.0.5 exactly (the runtime checks the version at load); the compiler is the TypeScript 7.1 checker (P16), so `.ts` files in the same program check as TypeScript 7.1 checks them; the runtime runs where `effect@4.0.5` and its platform packages run, and the evidence was gathered on Node 26.10 and Bun 1.4.1.

**D31. Build integration.** (amended by D105, D106, D107) Libraries and servers build with `vibelang` or `vibelang --watch`. Applications built with Vite use `vibelang-vite`, which compiles each requested `.vibe` module through `vibelang --api`, returns JavaScript with composed source maps, forwards diagnostics to Vite's overlay, and invalidates a module's importers for hot reload when the module's exported contracts or control classes change, because callers compile differently. Imports name source files: `.vibe` code imports `./welcome.vibe`, the emitted JavaScript imports `./welcome.js`, and TypeScript code imports `./welcome.js`, which the compiler resolves to `welcome.vibe` as it resolves `.js` to `.ts`.

**D32. The editor.** (amended by D76, D79) The language server is the fork's own: `vibelang --lsp --stdio`, from the project's `vibelang`. It serves `.vibe` and `.ts` files of the same program, so one server owns both. The VS Code extension `vibelang.vibelang` registers the `vibelang` language for `*.vibe`, starts that server, and asks VS Code's built-in TypeScript features to stand down in workspaces that contain `.vibe` files. Other editors configure their LSP client to run `vibelang --lsp --stdio` for `*.vibe` and `*.ts`. GitHub highlights `.vibe` as JavaScript unless `.gitattributes` says `*.vibe linguist-language=TypeScript`.

**D33. v0 editor features.** (amended by D77, D78) Hover shows a function's inferred contract and control class and, at a call, the success value. Completions add service members, prelude names, and `catch` narrowing by error class. Quick fixes exist for every EK diagnostic that has a mechanical fix (Chapter 28 lists them). Refactors: convert an `Effect.gen` or `Effect.fn` function into a VibeLang function, convert a `Context.Service` class into an abstract service class, implement a service (scaffold an object literal or an `implements` class), and write the inferred contract as an annotation.

**D34. Diagnostics configuration.** (amended by D61, D104) A `compilerOptions.vibelang` block in `tsconfig.json`. Every EK diagnostic is an error and cannot be lowered, because each marks code with no meaning or code that would compile unsoundly, with two exceptions that are policy, not soundness (amended after the prototype): EK2004 (an Effect try block with E = `never`; D260) is a warning by default, and EK4403 (a clock or randomness read) is an error by default; a project may set either to `"error"`, `"warning"`, or `"off"`, and an EK4403 read then compiles as a trusted `sync` call. The block also holds `"tracing": "none" | "exported" | "all"` (default `"none"`), which compiles the chosen functions with `Effect.fn` spans. `vibelang` exits non-zero on any error; diagnostics print at `.vibe` spans.

**D35. One owner per diagnostic.** The compiler owns every type and language diagnostic for `.vibe` and `.ts` files in the program, in the terminal, the editor, and the Vite overlay. Oxlint owns lint: it parses `.vibe` as TypeScript (VibeLang adds no syntax) and runs only syntactic rules there; its type-aware mode (tsgolint) skips `.vibe` files, because tsgolint embeds TypeScript's checker and would analyze the wrong semantics. `vibelang-oxlint-config` sets that override and turns off syntactic rules whose premise VibeLang changes, such as `require-yield`. Vite Plus runs the two through those same two pieces, the Vite plugin and the Oxlint config, so no rule has two owners and nothing needs deduplication.

**D36. Debugging.** (amended by D104) `vibelang` and the Vite plugin write source maps composed from `.vibe` through generated TypeScript to JavaScript, so any debugger that reads standard source maps (VS Code's JavaScript debugger for Node.js, Bun, and Chrome targets; Chrome and Edge DevTools; JetBrains IDEs) maps breakpoints and paused frames to `.vibe` lines. Compiled functions, clauses, and producers are generator functions named after their source; region closures are named `<function>$try`, `$catch`, `$finally`, and `$using`. A JavaScript debugger shows only the active JavaScript frames: a continuation held by a clause is a heap value, so a breakpoint in a clause shows the clause, and the body's frames reappear when it resumes. Logical stacks across suspensions come from spans (`tracing`) and Effect's span-based devtools.

## Gaps from the feature-coverage audit (2026-10-16)

`docs/research/effect-feature-coverage.md` left these open after D22-D36. All defaults.

**D37. Effect `catch` never sees an exception no contract lists** (resolves X2; amended by D260). Inside `Effect.gen`, a JavaScript `catch` sees any synchronous exception. In an Effect region, `catch` handles expected failures only (D13), so an exception no contract lists, such as one from `Option.getOrThrow`, `Schema.decodeUnknownSync`, or a trusted function's unlisted exception, is a defect it does not see. This difference is intended: those are Effect's "cannot fail here" forms, and each has a typed form for code that can fail (`Option.getOrElse`, `Effect.fromOption`, `Schema.decodeUnknownEffect`). A `try` block that runs Effects with E = `never` lets defects pass through its `catch`; this is EK2004, a warning by default (D34; prototype finding 16), with the typed forms and `Effect.try` as fixes. Evidence: Effect.gen's behavior verified on 4.0.5 in the audit; 487 Smithers and 70 opencode files mix JavaScript `try` with `Effect.gen`.

**D38. Runners** (resolves X4). The compiler knows runners by resolved symbol: `Effect.runPromise`, `runPromiseExit`, `runSync`, `runSyncExit`, `runFork`, `runCallback` and their `*With` forms; `ManagedRuntime`'s `run*` methods; `NodeRuntime.runMain` and `BunRuntime.runMain`; and `@effect/vitest`'s `it.effect`, `it.live`, their `.each` and `.prop` forms, and `layer(…)`. A runner may be called where no fiber runs the code: at a module's top level, and in a plain callback passed from such a place to a TypeScript function (a `describe` body, a framework's route handler). Anywhere else it is EK1005, because it would start a root with an empty Context and no handlers, outside the caller's structured concurrency; call the program or `fork` it. Tests in `.vibe` use `it.effect`; Promise-style tests stay in `.ts`.

**D39. A parameter that accepts a function or an `Effect`** (resolves X9). A function argument with parameters is passed as a function. A function argument without parameters is passed as a function when it compiles to plain JavaScript, and is converted to a program when it can pause; the overload or union member that accepts that form is selected. Effect APIs that decide at run time with `Effect.isEffect` (`HttpRouter.add`, `RpcGroup.toLayer`, `Effect.withErrorReporting`) then see the form the compiler chose.

**D40. Effect 4 service features on abstract-class services** (resolves X12). Static members stay on the emitted class: `static readonly layer` holds the default Layer, and a static `make` method plays the part of Effect 4's `make` option (`Layer.effect(Users, () => Users.make())`). A service class that declares `static readonly default`, a value of the service's own type, compiles to a `Context.Reference` whose `defaultValue` returns it, so using it adds nothing to R. Effect's own `Context.Reference(key, { defaultValue })` works unchanged, because a call that returns a key is data (D24).

**D41. Members of a service** (amended by D90) (resolves X13). `S.member(args)` looks the service up, so `S` joins R whatever the member returns, and then applies the call rule to the member: an `Effect` runs; a plain value is returned through a trusted call when the service comes from Effect's packages (D22) or the member carries `@vibelang trusted`, and is EK4401 otherwise. A member that is an `Effect` value runs when called: `Terminal.readLine()` lowers to `yield* (yield* Terminal).readLine`, a row of its own in the call table (prototype finding 3). Value members are read from the implementation: `Settings().baseUrl`. A member the service declares wins over the key's own members (`pipe`, `key`, `of`, `use`, and, because the key is a class, `name`, `length`, `call`, `apply`, `bind`), so `Rpc.call(…)` reaches the service; a static member with the same name as a service member is EK3006 (amended after prototype finding 4).

**D42. Workflow bodies are ordinary programs** (resolves X17). Effect's workflow engine runs a body on a forked child (`workflow/Workflow.ts:695-780`) and suspends it durably by interrupting that fiber (`Workflow.ts:1031-1036`); every execution, first or replay, reruns the body from the start. A body written in VibeLang therefore behaves as any interrupted and rerun program: held continuations are abandoned through their owners and finalizers run (T4), each execution captures fresh continuations (T11), and no producer position or handler state survives into the next execution. Side effects belong in activities, as in Effect. A handler installed outside `Workflow.execute` cannot reach a control operation inside the body, which runs on another fiber (EK4201 applies). Confirming experiment: G18.

**D43. `Effect.callback` is an explicit boundary** (narrows X11). Its register function may call plain TypeScript, as the D23 boundaries may, and its `resume` takes an `Effect<A, E, R>` (`Effect.ts`). `.vibe` code passes an `Exit`, `resume(Exit.succeed(value))`: an `Exit` is an Effect, and a call returns it as data (D24), whereas `Effect.succeed(value)` would run where it is written. Platform APIs stay behind Effect modules (EK4402), and an adapter for a resource uses the runtime's `suspend` in TypeScript, which reports a lost race (Chapter 6).

## Defaults from the prototype compiler (2026-10-16)

`prototype/esc/FINDINGS.md`: a prototype compiler on `typescript@5.9.3` and `effect@4.0.5` compiles 46 example files written from the spec (26 run, 20 fail with their expected codes) and matches 25 of the spec's 28 claimed contracts. These defaults settle what it found underspecified.

**D44. "The expected type" is the declared, uninstantiated parameter type of the resolved overload** (finding 1). TypeScript's instantiated contextual type is circular: in `ids.map((id) => Users.find(id))`, `U` is inferred from the lambda itself. If overload resolution fails, the candidates whose arity fits are used. The instantiated type is used only when the declared type is a bare type parameter fixed by another argument, such as `Layer.succeed`'s `NoInfer<S>`.

**D45. A service compiles to an interface plus a key class** (finding 19; supersedes D1's emit clause). Effect's `Context.Service` class form makes the instance type the identifier, so `class UsersFake implements Users` is TS2720 and a parameter typed `db: Users` means the identifier. The emission that works is an interface for the shape, with an optional brand `readonly "~vibelang/service"?: "<key>"`, merged with a class whose static side is a `Context.Key` (`prototype/esc/scratch/probe2.ts`): R stays nominal, `implements` works, and a parameter typed with the service means its methods. Control operations and services with a default emit the same way from the runtime's `controlKey` and `referenceKey`.

**D46. Failure lowering** (findings 11, 12, 14). `finally` lowers to `Effect.onExit`, because `Effect.ensuring` requires a cleanup whose E is `never`, and D15 lets cleanup fail. `throw e` lowers to `return yield* Effect.fail(e)`, so narrowing after the `throw` is kept. E is defined as the type of the expected failures in causes made only of expected failures: a cause that also holds a defect or an interruption may carry `Fail` reasons outside E, which no VibeLang `catch` recovers (K14).

**D47. A block is a Scope region when it declares `using` or calls `fork`** (finding 18), even with no `using`; without this rule a fork-only block found no `Scope`.

**D48. `Scope` joins the prelude** (default). In Effect 4, `Scope` is a module, and the type is `Scope.Scope`; contracts name it constantly. The prelude's `Scope` is the module, and the type `Scope` means `Scope.Scope`, as `Effect` does for `Effect.Effect`.

**D49. Collections of programs convert** (amended by D69, D111) (finding 5). An iterable or record of functions without parameters converts to Effects where an iterable or record of Effects is expected, so `Effect.all(stores.map(makeSync), { concurrency: 4 })` type-checks and runs.

**D50. `Continuation<V, E, H>`** (finding 24). V is what the perform site receives, E the operation's declared errors (what `resumeWith` may raise), and H the result type of the enclosing `handle`. Under a deep handler, `resume(k, v)` returns H: the resumed program runs until it reaches the reinstalled prompt, where `onReturn`, or a later clause that does not resume, produces the value. The checker computes H as the least type containing `onReturn`'s result (the program's A without one) and every clause's return type, taking each `resume`'s type as H.

**D51. Foreign calls at a module's top level, and `@throws`** (amended by D100, D101) (finding 21). EK4401 applies inside functions only: a module's top level runs outside every program, where `Effect.try` would be EK1001, so a plain call there is an ordinary JavaScript call and an exception fails the module's import, as in TypeScript. Each `@throws {T}` names an exported class, and the generated code tests `instanceof T`.

**D52. Inference details** (amended by D71, D72, D73) (findings 7, 10, 13). E and R of a recursive function come from a fixpoint over its strongly connected component of the call graph; when A depends on the recursive result, the contract must be written (EK2102). The iteration stays inside the component (amended 2026-10-16 after the single-pass experiment): the checker checks the component's bodies, then rechecks only those bodies, with the E and R found so far as the members' contracts, until E and R stop growing. The rows are finite and each step only adds to them, a `catch` that removes a fixed set of failures included, so the iteration ends. No function outside the component is rechecked, and no lowering decision waits for it. The probe `isEven`/`isOdd`, whose cycle carries `Odd`, needs it: one pass without it gives `isEven` an E of `never`. A is widened as TypeScript widens a function's inferred return type. Definite assignment is checked on the source, before lowering, because region closures defeat TypeScript's own analysis.

**D53. Diagnostic codes follow the prototype.** (amended by D67, D70, D71, D74) EK1003 is `async` or `await`, EK1004 is `using` at a module's top level, EK1005 is a runner inside code a fiber runs (D38), EK2003 is a return annotation that is not a full `Effect<A, E, R>` (until O7), EK2004 marks an Effect try block with E = `never` (D260), EK2005 is a `resumeWith` program outside the operation's contract (D17), EK2102 is a recursive A that needs a contract, and EK3001-EK3006 are a duplicate key, `extends`, `new`, `instanceof`, a generic service, and a static that shares a service member's name. **D54. Regions inside a plain-JavaScript function** (default; completes D10 with D5; amended by D260). **D56. A lambda's form is decided against each overload candidate** (default; refines D44). **D61. EK diagnostics use the TypeScript transport** (default, lane F1). An EK diagnostic is a TypeScript diagnostic with source `EK`, on upstream's content-mapper path. The CLI prints `error EK1003:`; the language server sends `{source: "ES", code: 1003}`, which VS Code shows as `EK(1003)`. `@ts-ignore` and `@ts-expect-error` do not apply to EK diagnostics. The CLI and editor share one diagnostic path.

**D62. The runtime exports define the prelude** (default, lane F1). The prelude is the runtime's exports. A `.vibe` file loads the runtime only when it uses a prelude name it does not declare at top level, so files without prelude names compile as plain TypeScript. Prelude names resolve after every scope and before globals. Emitted JavaScript imports `Effect`, `Layer`, `Schema`, and `Scope` as `import * as X from "effect/X"` and the rest as named imports from `vibelang-runtime`; `.d.ts` files use `import type`. **D63. Local imports name source files** (default, lane F1). A `.vibe` file imports `./x.vibe` or `./x.ts` by source name with no flag (no TS5097); specifiers become `.js` in JavaScript and `.d.ts` output. `./x.js` probes `.vibe` after `.ts` and `.tsx`, so `.ts` wins when both exist; `./x.vibe` falls back to `x.d.ts`. Source names work during checking and output names work in JavaScript.

**D64. Acceptance cases compare diagnostic sets and result lines** (default, lane F1). A failing compiler case passes when its exact set of error codes matches (TypeScript codes count, warnings do not); a runnable case compares only its `@@result` line, so programs may log. EK1002 is defined by type: a `function*` passed where the parameter's type returns a lib `Generator` or `Iterator`. EK1004 also covers class static blocks. Exact codes catch regressions while result markers allow application logging.

**D65. Plain VibeLang calls run inline everywhere** (default, lane F2). A call from a `.vibe` file to a plain function runs inline as `f$direct(a)` everywhere, including a module's top level, because it computes a value and runs no program. 

**D66. Plain overloads reject suspending function values** (default, lane F2). An overload candidate that asks for a plain function rejects a `.vibe` function value that can pause, as it rejects such a lambda (D56 extended to function values); a TypeScript function that returns an Effect passes as data; when every candidate rejects, EK4301 reports against the first candidate's form. Named functions and lambdas follow the same callback safety rule.

**D67. Plain return annotations preserve plain function types** (default, lane F2). A function with a plain return annotation keeps that type and compiles to one plain function; only unannotated or Effect-contract functions get the `$direct` plus `Effect.sync` pair, whose TypeScript type is `(…) => Effect<A, never, never>` (chapter 15's one calling convention). **controversial**: it interacts with EK2003, D55 methods need the annotation, and editors show plain helpers with an Effect type unless hover says otherwise. An explicit plain type supports JavaScript protocols and avoids an unwanted Effect wrapper.

**D68. Contract-less callback parameters carry E and R** (default, lane F2). **D69. Programs lower according to their source form** (default, lane F2). Each conversion preserves cold execution and the collection shape.

**D70. Jumps cannot leave a finally block** (default, lane F3). A `return`, `break`, or `continue` that leaves a `finally` block is a new error, EK2006; in JavaScript such a jump discards the failure in flight, and compiling `finally` to Effect cleanup cannot honor it. Added to chapters 17 and 28. **controversial**. Effect cleanup cannot preserve JavaScript jumps that discard an in-flight failure.

**D71. Recursive catch and return types can require a contract** (default, lane F3). EK2102 also covers a `catch` variable or return type typed before its cycle's E and R are known; the fix is a written contract. The checker cannot revise a type already cached before the recursive channels are known.

**D72. Pure recursion keeps TypeScript diagnostics** (default, lane F3). EK2102 applies only to functions that run Effects; a pure recursive function keeps TypeScript's TS7023, which a plain annotation fixes (consistent with D67). Only functions that run Effects need VibeLang recursive-channel inference.

**D73. Calls use the written contract** (default, lane F3). A call to a function with a complete written contract adds the contract's E and R, not what its body does. A caller must rely on the public contract rather than a narrower implementation.

**D74. Methods allow plain annotations** (default, lane F3). Methods are exempt from EK2003 for a plain annotation, because a method implementing a plain-function member is declared that way (D55). D55 requires methods that implement plain JavaScript protocols.

**D75. The compiler binary identifies as VibeLang** (default, lane F4). The binary built from `tsc/cmd/tsc` always identifies as VibeLang (`vibelang --version` prints `VibeLang 0.0.1 (TypeScript 7.1.0-dev)`); there is no `cmd/vibelang`, which keeps the upstream diff to one seam. **D76. TypeScript editor ownership requires disabling the built-in extension** (default, lane F4). The language server also reads the validation setting, so disabling validation would hide VibeLang diagnostics.

**D77. Hovers distinguish calls and plain helper signatures** (default, lane F4). In `.vibe` files a hover adds "Runs here and returns `T`" at a call that runs, and shows a plain function's direct signature with what TypeScript callers see; `.ts` files keep TypeScript's hover. **controversial** (wording). A call exposes its success value while a helper must explain its TypeScript-facing Effect form.

**D78. Prelude and service members complete in scope** (default, lane F4). Prelude names complete as in-scope names that local declarations shadow, and `Users.` lists the service's members. Programmers need the same discoverability as explicit imports and Context members.

**D79. The editor reuses TypeScript grammar and project-local vibelang** (default, lane F4). The TextMate grammar is VS Code's TypeScript grammar with root scope `source.vibe` (inner scopes keep `.ts` so themes apply); `vibelang` is found from the `vibelang.server.path` setting, then the nearest `node_modules/.bin/vibelang`, then `PATH`; the extension does not run in untrusted workspaces. Existing themes and project compiler versions must keep working, and untrusted workspaces cannot launch the server.

**D82. Runtime extraction preserves the prototype ABI** (default, lane R). The extraction kept the prototype helpers' behavior and continuation parameter order; discrepancies with the spec are documented in packages/runtime/README.md, not fixed silently. Inherited limits: Stream adaptation keeps a one-element buffer (D26's zero-capacity handoff is unfinished, for F7); `$programs` handles iterables, not records (for F2); `$trusted` matches exceptions by name or tag (for F8). Package extraction must not silently change compiler and runtime behavior.

**D83. Scaffolds use absolute file dependencies** (default, lane C). Setup writes absolute `file:` dependencies on the repository's packages into new projects instead of `bun link`; nothing registers globally and nothing is published, so a project keeps working only while the checkout stays where it is. Local projects work without global package registration or publication.

**D90. Service member calls are structural** (default, lane F5). The member-call rule (D41) is structural: it applies to any Context key whose service type declares the member, which covers `.vibe` services, TypeScript `Context.Service` classes, and Effect's `FileSystem` and `Path`. Calling an Effect value with no arguments runs it (chapter 13's `p()` rule, applied generally). Both rules apply only inside `.vibe` function bodies. Effect Context keys and VibeLang services need the same member-call behavior.

**D91. Control calls look up their implementation** (default, lane F5). A control-operation call lowers like a service call, `yield* (yield* Approval).approve(x)`, as the prototype did (chapter 13 prints `yield* Approval.approve(x)`); `handle` provides an implementation that performs the kernel operations. **controversial**: F7 may change it. This preserves the prototype lowering while handle installs kernel-backed operations.

**D92. Methods lower when their body or expected type needs Effect** (default, lane F5). A method in a `.vibe` file becomes an Effect when its body runs or looks up an Effect, or when its expected type returns one; it stays a method whose body is `return Effect.gen({ self: this }, function* () { … })`. The method must retain its receiver while running a generator body.

**D93. Service keys and declarations have a stable shape** (default, lane F5). A service key is the package name (the directory name when there is none), the module path, and `#Name`. Declaration files use the runtime types `ServiceKey` and `ReferenceKey`. A default service needs `static readonly default` (without `readonly` it is an ordinary static). EK2101 requires all three type arguments on `Effect<…>`. `wire` emits its arguments consumers first; EK3204 applies when `Out` is `any` or `unknown`. **controversial**: the `readonly` requirement and EK2101's strictness. Package and module identity keep services distinct and explicit contracts bound provider analysis.

**D94. Using classifies its initializer** (default, lane F6). `using` decides by its initializer. A call that runs an Effect is an acquisition: it gets the block's Scope, `Scope` leaves R, and no `Symbol.dispose` is required. Any other initializer must be a Disposable, `null`, or `undefined`. A Disposable value of either kind also gets `[Symbol.dispose]()` at block exit, so an Effect whose own release already disposes it disposes twice. Effect acquisitions need the block Scope; ordinary values follow JavaScript disposal.

**D95. For-using bodies own a region per iteration** (default, lane F6). In an Effect function, `for (using x of values)` makes each iteration's body a Scope region; the value is taken first, and `using` or `fork` inside the body join that region. Resources and children must end with the iteration that owns them.

**D96. Expression-bodied forks retain Scope** (default, lane F6). A `fork` belongs to the innermost block around it; an arrow function with an expression body has no block, so `() => fork(p)` is `Effect.forkScoped` and keeps `Scope` in R. **controversial**: it differs from `() => { return fork(p) }`; alternatives are treating expression bodies as blocks or reporting a returned block-owned fiber. An expression body has no enclosing block to own the child.

**D97. Continuation result types use the program's original result** (default, lane F7; recorded from the compiler notes). A clause receives `Continuation<V, E, H>`. Without `onReturn`, H is the handled program's A; with `onReturn`, H is `never`, because TypeScript fixes H before checking that callback. The `handle` result unions the program's result (or `onReturn`'s result) with each clause's result and includes their errors and residual requirements. **controversial**: a non-tail resume can be typed more narrowly than its runtime result when another clause returns early with a different type. This keeps handler inference usable without circular callback inference; it does not implement D50's full result fixpoint.

**D98. Producers are lazy Streams with two consumption paths** (default, lane F7; recorded from the compiler notes). A `function*` declaration or function expression returns `Stream<T, E, R>`; generator methods remain JavaScript generators. Direct `for...of` consumption runs the producer under a Yield handler on the consumer's fiber. Consumption through Stream operators starts a producer fiber on the first pull and uses a handoff with no buffer. Closing either path runs producer cleanup. This supplies D26's lazy Stream interoperability and bounded stack without running ahead of the consumer. Not controversial.

**D99. Handler reach checks inspect declared requirements and known fiber boundaries** (default, lane F7; recorded from the compiler notes). EK4201 checks Effect's named forking combinators, nonsequential `concurrency` options, concurrent zip calls, the prelude's `fork`, and producer arguments that require controls. A branch that handles its controls internally passes. EK4202 rejects a non-VibeLang callee whose declared return requirements name a control; generic requirements stay subject to the argument checks. These checks identify unreachable handlers while the runtime enforces fiber ownership. Not controversial; static detection has the gaps recorded below.

**D100. Foreign calls are plain wherever no fiber runs** (default, lane F8). Code no fiber runs is plain JavaScript for EK4401 too: a module's top level and the plain callbacks it passes to TypeScript functions (`describe` bodies, route handlers), the same places D38 allows runners. Top-level framework callbacks need the same boundary treatment as module initialization.

**D101. Expected foreign failures come from explicit parsing contracts** (default, lane F8). Only built-ins that parse outside text declare expected failures (`JSON.parse` with `SyntaxError`, `decodeURI` and `decodeURIComponent` with `URIError`); every other built-in's exceptions are defects. Trusted failures make named functions and free lambdas Effects but stay defects in plain callbacks. Each `@throws` class must be exported by a module the `.vibe` file imports, else the call is EK4401. **controversial**: the plain-callback leniency. Parsing outside text has expected failures; unlisted exceptions remain defects.

**D102. Platform APIs and globals are restricted** (default, lane F8). EK4402 at value imports of Node built-ins and `bun:` modules (type-only imports allowed) and at each reference to a listed platform global, including inside boundaries and at top level; web standards that touch nothing outside the program are allowed (`URL`, `TextEncoder`, `AbortController`, `structuredClone`, `Headers`, `Response`). **controversial**: `console.log` and `createServer` need a `.ts` module (examples/http-api moved its server layer to `src/server.ts`). Revised by the orchestrator, see D108. Effect services provide typed errors and replaceable platform access. D108 supersedes the import restriction.

**D103. Top-level program calls have one diagnostic** (default, lane F8). EK1001 covers any top-level call that would run a program, including service member calls and Effect-value calls, reported once at the outermost call. The outermost call identifies the attempted execution without duplicate errors.

**D104. Generated names and spans follow source names** (default, lane F8). Compiled generators are named after their function, variable, or property (an object method `{ *name() {} }.name` when the body refers to that name); `tracing: "exported"` spans exported functions, `"all"` every named lowered function plus methods through `Effect.withSpan("Class.method")`; anonymous lambdas get no span. Named generators and spans make source-level failures identifiable.

**D105. Vite uses one project compiler subprocess** (default, lane V). Amends D31's mechanism, preserving the behavior. `vibelang-vite` compiles the whole project with one shared `vibelang` subprocess per source revision and serves the output cached under `node_modules/.vibelang/`, instead of `vibelang --api` (amends D31's mechanism, same behavior). Whole-project compilation keeps contracts consistent without depending on the API transport.

**D106. Edits invalidate all loaded VibeLang modules** (default, lane V). After an edit the plugin invalidates every loaded `.vibe` module and its transitive importers, because callers compile differently when a contract changes. A changed contract can change the lowering of callers.

**D107. Vite sources stay under its root** (default, lane V). Sources must sit under Vite's root; the plugin overrides emit paths and source roots there so output lookup and source maps are predictable. **controversial** for monorepos. A shared source root makes output lookup and source maps predictable.

**D108. EK4402 reports platform execution, not imports** (default, orchestrator; implemented by lane F8). Supersedes the import half of D102; its globals list and allowed web standards stand. EK4402 fires where `.vibe` code runs a platform API (a call, `new`, tagged template, or property read of one, including by destructuring or spreading), not where it names one. Imports, re-exports, value uses, and namespace member reads as values (`os.EOL`) are allowed, so `NodeHttpServer.layer(createServer, { port })` compiles in `.vibe`. A call EK4402 reports is not also EK4401. Known gap: a platform function reached through a local alias, a parameter, or an object a platform call returned is not followed. Platform integrations must be able to pass host functions to Effect adapters without calling them.

**D109. Only Effect itself selects an Effect callback form** (default, lane F2). An expected callback or program asks for the Effect form only when its type is effect's own `Effect` interface, or a type parameter constrained to it; subtypes such as `Config` are data (D24), so `Config.orElse`'s fallback stays plain. Structured subtypes such as Config must remain data under D24.

**D110. Pipe looks ahead without checking its first stage early** (default, lane F2). The `pipe` look-ahead (D8) reads the first stage's callee signatures, or a function value's own signatures; it runs only when the first argument can be a program, and never checks the stage early. Reading signatures avoids circular inference from a prematurely checked stage.

**D111. Program collection conversion covers iterables** (default, lane F2). The D49 conversion covers any iterable (`Set`, a `Map`'s values) through its iterated type; an iterable never converts as a record, matching `Effect.all` at run time. Compile-time conversion must match Effect.all at run time.

**D112. Mixed plain and Effect callback returns prefer plain when eligible** (default, lane F2). A callback whose expected return mixes plain and Effect (`boolean | Effect<…>`) is plain when D10 allows and an Effect function otherwise; the same holds wherever both forms fit. Where both forms fit, D10 gives the form without Effect operations.

**D113. Plain contract lambdas expose their success type** (default, lane F2). A lambda with a contract that takes the plain form has type `(…) => A`; where only a plain function fits, inference from its annotation starts from A. Plain callback inference needs A rather than an Effect wrapper.

Refresh existing projects with `bun update vibelang-runtime vibelang vibelang-vite` after rerunning setup; examples do not commit `bun.lock`. **D126. `error` declares a tagged error class** (Will). `error NotFound { id: string }` is short for `class NotFound extends TaggedError("NotFound")<{ readonly id: string }> {}`: the tag is the class name, every field is readonly, and `error Timeout` declares an error without fields. **D127. Effect types are written `Result!Error!Dependencies`** (Will; amends D57, **controversial**). `User!NotFound!Db` is `Effect<User, NotFound, Db>` anywhere a type can appear. An empty slot is `never`: `User!NotFound!`, `User!!Db`, `User!!`. Dependencies left out entirely, as in `User!NotFound`, are `infer R` in the return annotation of a function with a body and `never` everywhere else; errors cannot be left out once a `!` is written, so inferring them takes no annotation or `Effect<A, infer E, ...>`. Unions bind inside a slot: `User!NotFound | Timeout!Db` fails with `NotFound | Timeout`. A slot that starts with `{` is empty, because in a declaration the `{` starts the body; an object type after a `!` needs parentheses. The parser expands the form to `Effect.Effect<A, E, R>`, which resolves whether `Effect` is the prelude's or imported from `effect`, so declaration files read `Effect.Effect<A, E, R>`; hovers and contract messages about `.vibe` code use the `!` form. The postfix `!` of JSDoc types no longer parses in `.vibe` files. `Effect<A, E, R>` stays accepted. Controversial because `!` reads as negation or non-null to a TypeScript programmer.

**D128. `service` and `control` declare services and control operations** (Will; amended by D220, which D223 reverted: written without `class`). `service Users { find(id: string): User!NotFound; region: string }` is short for `abstract class Users { abstract find(id: string): User!NotFound; abstract readonly region: string }`, and `control Approval { approve(request: string): boolean!! }` for the same with `extends Control`. Every member without a body or initializer becomes abstract, and every value member also readonly; static members, such as a layer, stay as written. A member's contract uses the `!` form; a plain return type is not an Effect, so it stays EK2101 rather than quietly meaning `A!!`, which would wrap an alias that already names an Effect type. Without a body, left-out dependencies are never, so `find(id: string): User!NotFound` needs no trailing `!`. A member with an implementation is EK2103, because it would make the class an ordinary abstract class instead of a service. The parser marks the class's `abstract` modifier as synthesized, which is how the checker tells the declaration from a hand-written class. Not controversial.

**D129. `layer` declares a layer** (Will; superseded by D221: a layer is `Layer.effect(Service) { ... }`). `layer UsersLive: Users { const directory = Directory(); find(id) { ... }; readonly region = "eu" }` is short for `const UsersLive = Layer.effect(Users, () => { const directory = Directory(); return { find(id) { ... }, region: "eu" } })`. Statements run once, when the layer builds; members are methods, `name(params) { ... }` or `*name(params) { ... }`, and values, `readonly name = value`, which is not a statement in TypeScript, so it cannot be mistaken for an assignment to an outer variable. Without statements the layer is `Layer.succeed(Users, { ... })`. A method starts with a name and parameters followed by a return type or a `{` on the same line, which a call statement cannot be. Statements come before the members, so the expansion keeps source order; one that follows them is EK2104. Scoped setup works because Effect 4's `Layer.effect` supplies the layer's own Scope. Static layers inside a service stay as written. Not controversial.

**D130. `with` provides a layer to a block** (Will; amended by D172: the keyword is now `provide`; extended by D173: providers may be `Key = value`). `with AppLive { ... }` runs its statements with the services the layer provides, as `Effect.provide(() => { ... }, AppLive)` does, except that the statements are code of the enclosing function: a `return` returns from it, and `break` and `continue` leave its loops. A module is strict code, where JavaScript's `with` statement is a syntax error, so the word is free. The parser reads the block as an ordinary `Block`, flagged `NodeFlagsVibeLang`, whose first statement holds the layer expression, so TypeScript checks both as ordinary code; the analyzer gives the block the errors of its statements and the layer, and the requirements of its statements that the layer does not provide plus the layer's own; the lowering runs the statements as a region closure under `Effect.provide`. The layer expression may be a layer, an array of layers, or a `Context`, as `Effect.provide` accepts. A function with a `with` block is an Effect. A `with` block at a module's top level is EK1001. Not controversial.

**D131. Catch clauses name the failures they handle** (Will; superseded by D216). `try { ... } catch (e: NotFound) { ... } catch (e: Busy | Offline) { ... } catch (e) { ... }`: each clause handles the failures whose `_tag` belongs to its type, a final untyped clause handles the rest, and without one a failure no clause names propagates with its type. The parser writes one catch clause whose block tests `$isFailure<T>($caught)`, a runtime type guard, clause by clause, so TypeScript narrows each clause's variable and the failures left after the chain; the lowering passes the guard the `_tag` of each member of `T`. A failure raised inside a clause is not tested by the clauses after it, as in other languages with several catch clauses. Matching by `_tag` covers tagged errors from other packages, such as `Schema.SchemaError`, and type aliases of unions; a member without a literal `_tag` is EK2105, and a clause after an untyped one is EK2106. A single untyped clause parses as before. Not controversial.

**D132. Handle clauses follow a try block** (Will). `try { BODY } handle Approval.approve(request) { CLAUSE }` handles the control operations that BODY performs, as `handle(() => BODY, Approval, { approve(request, k) { CLAUSE } })` does, except that BODY and CLAUSE are code of the enclosing function: a `return` returns from it, and `break` and `continue` leave its loops. A clause's parameters take the operation's parameter types, and in its own code `resume(value)`, `resume()` for a `void` result, `resumeWith(program)`, and `abandon()` act on its continuation, which it never names. A clause continues after `resume` once the try block finishes, and the statement then ends as the block did, as a pending `return` waits for a `finally` block; a clause that ends without resuming abandons the block, and the statement completes. Several clauses may follow one try, one per operation of each control they name (EK2108; a name that is not a control is EK2107); the first control's handler is innermost. Catch clauses and a `finally` block may follow the handle clauses and cover the block and the clauses. The parser writes `try { BODY } catch ($performed) { if ($performed) { const [$k, request] = $clause(Approval.approve); CLAUSE } }`, flagged `NodeFlagsVibeLang`, so TypeScript's flow analysis lets a clause start anywhere in the block; `$clause` types the bindings, and `$k` makes `resume` return `never`, so a clause that ends with a resume does not complete normally. The lowering runs BODY as a region under the runtime's `handle` and each clause as a generator that returns the statement's completion record, with the tail-resume request (D18) for a resume at a clause's end. `handle(...)` stays the expression form, which returns a value and takes `onReturn`. Not controversial.

**D133. `schema` declares a struct schema and its type** (Will). `schema User { id: string; nickname?: string; role: "admin" | "member"; home: Address }` is short for `const User = Schema.Struct({ id: Schema.String, nickname: Schema.optional(Schema.String), role: Schema.Literals(["admin", "member"]), home: Address })` and `interface User extends Schema.Schema.Type<typeof User> {}`. The parser writes each field's schema from its type: a primitive keyword, a literal (`Schema.Literal`), a union of literals (`Schema.Literals`) or of other forms (`Schema.Union`), `T[]`, `ReadonlyArray<T>`, and `Array<T>` (`Schema.Array`), a tuple, `Record<K, V>`, an object type (a nested `Schema.Struct`), or the name of another schema, which the struct refers to as a value, so any schema constant can be named. `name?: T` is `Schema.optional`, which accepts an absent key or `undefined` whatever `exactOptionalPropertyTypes` says, so decoding accepts every value the type allows; exact optional keys, checks, and transformations stay with `Schema.Struct`. Any other type, and a name whose value is not a schema, is EK2109. The interface is derived from the struct, not from the written field types, so the type and the schema cannot disagree; the written types are not checked as types. The interface goes to the parser's reparse list, which puts it before the constant in the same statement list. Not controversial.

**D134. Members are readonly unless written `mutable`** (Will; **controversial**). In a `.vibe` file, every property signature and index signature of an interface or an object type is readonly unless it is written with `mutable`: `interface Cart { id: string; mutable items: Array<Item> }` means `interface Cart { readonly id: string; items: Array<Item> }`. The parser adds the `readonly` modifier, so declaration files write it and TypeScript code sees the same types. `mutable` is a modifier only when a member name follows it on the same line, so a member named `mutable` parses as before. Class members keep TypeScript's rule, and arrays and tuples are untouched, so `ReadonlyArray` is still written. A schema field written `mutable` gets `Schema.mutableKey`; an error's fields stay readonly whatever is written, because Effect's `TaggedError` types them `Readonly`. Readonly limits writes through the type, not the object: TypeScript lets a mutable object be assigned to a readonly type, so callers in either language pass the same values. Controversial because the same interface means different things in a `.ts` and a `.vibe` file, and code ported from TypeScript that writes through an interface gets TS2540 until its members say `mutable`; the payoff is that immutable data, the common case in Effect code, no longer repeats `readonly` on every field, which the docs and tests wrote 186 times.

**D135. An exported `main` runs when the host starts its module** (Will). A module that exports a function declaration named `main` with no parameters ends with `if (import.meta.main) NodeRuntime.runMain(main())` in its JavaScript, so `node dist/main.js` runs the program, and importing the module, from a test or another module, runs nothing. `NodeRuntime` comes from `@effect/platform-node` when that package resolves from the module; the program resolves it as an implicit import of every module with such a `main` to find out. Without it, the module calls the runtime's `$runMain`, which `Runtime.makeRunMain` builds to behave as `NodeRuntime.runMain`: Effect's runner reports a failure nothing reported, SIGINT and SIGTERM interrupt the program where the host has a `process`, and the exit code follows `Runtime.defaultTeardown`. So a program needs no platform package to run, and Bun and Deno, which also set `import.meta.main`, run it the same way. A module that calls a runner at its top level, any call of a function named `runMain`, `runPromise`, `runFork`, `runSync`, or `runCallback`, starts its program itself and gets no entry statement, so a program never starts twice; that is how an application provides layers or passes runner options. A `main` that compiles to plain JavaScript runs through `Effect.sync`. The examples' `run.vibe` files and the template's runner call are gone. `import.meta.main` needs Node.js 24.2 or later, and VibeLang already requires Node 26. Not controversial.

## Fewer tokens: calls (2026-10-16)

Will approved the token-reduction proposals measured on the docs and examples (59,572 word and punctuation pieces in 632 code units). These decisions cover calls; the declaration keywords have their own section.

**D146. Every export of `effect`'s root is in scope** (Will; extends D4 and D62). A `.vibe` file sees every namespace and function that the `effect` package exports from its root, such as `Console`, `Stream`, `Option`, `Schedule`, `Duration`, `flow`, and `identity`, without an import, after the runtime's prelude names. A local declaration or import shadows one. A global value that JavaScript itself defines wins, so `Array`, `String`, `Number`, `Boolean`, `Symbol`, `BigInt`, `Function`, and `RegExp` keep their meaning and Effect's modules with those names need an import under another name; a host global such as the DOM's `Option` does not shadow Effect's. The emitted JavaScript imports each used module from `effect/<Module>`, never from the root, which would load every module. Subpath packages such as `effect/http` still need imports: their names (`HttpRouter`, `HttpServerRequest`) belong to one kind of program. Imports from `effect` were 5.9% of the corpus.

**D147. Calls are passed by name where a program is expected** (Will; **controversial**; extends D7 and D49). Where a parameter's declared type expects an `Effect`, including an array element or record field of `Effect.all`, an argument expression that calls a `.vibe` function, a function that returns an `Effect`, or a service member is passed by name: the callee receives a program that evaluates the expression each time it runs, as if the source had written `() =>` before it. `fork(fetchReport())`, `Effect.timeout(slowReport(), "20 millis")`, `Effect.race(cachedReport(), slowReport())`, `Effect.all([a(), b()])`, `HttpRouter.add("POST", "/users", createUser())`, and `NodeRuntime.runMain(main())` all mean what they mean in Effect. Elsewhere the call runs where it stands: `Console.log(fast())` logs fast's result, and `Effect.succeed(work())` succeeds with it. An expression whose value is already an `Effect` keeps its meaning. Each overload candidate decides by its own declared parameter, as for lambdas (D56). This applies to every Effect-typed parameter, including a plain callee such as `Stream.fromEffect` (effectscript-4a ruling, Smithers D-10). Constructing that cold program does not lift an enclosing plain-annotated factory; its calls run when the Stream is consumed. EK1001 does not apply at the top level to a call passed by name. A hover on the callee says the call is passed as a program and runs later. Controversial because the call site no longer shows whether a call runs now or later; the parameter's type decides, and the hover says which. A program of several statements still needs `() => { … }`. Thunks around single calls were 2.6% of the corpus.

**D148. Boundary hatches run plain TypeScript** (Will; **controversial**; amended by D229-D232; replaces the boundary role of `Effect.sync`, `Effect.try`, `Effect.promise`, `Effect.tryPromise`, and `Effect.callback` in `.vibe` code). The prelude's `sync`, `try`, and `callback` are escape hatches whose first arguments are plain TypeScript, not VibeLang (D232). `sync(() => …)` is `Effect.sync`, so a throw is a defect; `sync(async () => …)` is `Effect.promise`. `try(() => …)` is `Effect.try`, so a throw is an expected `Cause.UnknownError`, or what an optional second argument such as `(error) => new BadJson({ error })` makes of it; `try(async (signal) => …)` is `Effect.tryPromise`. `callback((resume, signal) => …)` is `Effect.callback`: `resume(value)` succeeds, `resume.fail(error)` fails, `resume.exit(exit)` adopts an Exit, and a function the body returns runs on interruption, awaiting its PromiseLike result. A returned `Effect<void, never, R>` is the interrupt finalizer itself, and its requirements join the callback's R. Registration runs lazily on every execution; the first resume wins, normal completion skips the finalizer, and interruption aborts the signal before running and waiting for the finalizer with interruption disabled. Cleanup throws and promise rejections remain defects. This matches Effect 4.0.5 `src/internal/effect.ts:1161-1205,1210-1216` and its public finalizer type in `src/Effect.ts:1853-1859` (S19-30). A single expression is a hatch too, evaluated when the Effect runs: `sync(crypto.randomUUID())`. Inside a hatch's first argument there is no VibeLang lowering: calls do not run, so calling a `.vibe` function gives an inert Effect value for `runPromise` or `runFork`; `throw`, `async`, and `await` keep their JavaScript meaning; platform APIs and clock reads are allowed (no EK4401, EK4402, or EK4403); `return` returns from the hatch's function; and the function captures nothing of the `.vibe` file, whose values arrive as inputs (D229, D230). A hatch is recognized by name when no scope around the call declares it, so a parameter named `callback` stays a parameter. Controversial because VibeLang now has two meanings for the same function syntax, decided by the call it sits in; the hatch names keep that visible at the call site.

**D149. `try(` is a call in `.vibe` files.** A try statement starts with a block, so `try (` never starts one; the parser reads `try(…)` as a call whose callee is the identifier `try`, which only the prelude can bind. Effect's `{ try, catch }` options object passed to the hatch is EK4404, an error: the hatch would treat it as a value and succeed with the object itself.

**D150. Runners lead back in** (extends D38). `runPromise`, `runFork`, `runSync`, and `runCallback` are in the prelude, re-exported from `effect/Effect`. They are called from plain TypeScript: a `.ts` file, a hatch's body, or a module's top level. EK1005 still reports one in code a fiber runs, and does not apply inside a hatch.

**D151. The Effect module's most used functions need no prefix** (Will; extends D146). `all`, `die`, `forEach`, `log`, `logDebug`, `logInfo`, `logWarning`, `logError`, `race`, `repeat`, `retry`, `sleep`, `timeout`, and `withSpan` are in scope as the Effect module's functions: `sleep("1 second")`, `retry(fetchUser(id), policy)`. They were 329 of the 538 `Effect.` member uses in the docs and examples. Operations that VibeLang spells another way stay qualified: `Effect.fail` is `throw`, `Effect.provide` is `with`, `Effect.scoped` and `acquireRelease` are `using`, and `Effect.sync`, `promise`, `try`, and `tryPromise` are the hatches (D148). Names that read poorly alone, such as `result`, `exit`, and `service`, stay qualified too. A local declaration shadows one; the emitted JavaScript imports each one used from `effect/Effect`.

**D152. Values of Effect's data types take their module's functions as methods** (Will; **controversial**; extends D146). A value whose type one of `effect`'s data-type modules declares takes that module's data-first functions as methods: `readings().filter(hot).take(2)` is `Stream.take(Stream.filter(readings(), hot), 2)`, and `maybe.map(format).getOrElse(() => "none")` is `Option.getOrElse(Option.map(maybe, format), () => "none")`. The modules are `BigDecimal`, `Cause`, `Chunk`, `DateTime`, `Deferred`, `Duration`, `Effect`, `Exit`, `Fiber`, `HashMap`, `HashSet`, `Option`, `Queue`, `Ref`, `Result`, `Schedule`, `Sink`, and `Stream`; the module is the one whose declaration file declares the value's type, and every member of a union must come from the same module, as `None` and `Some` do. A function is a method when its first parameter is named `self`, effect's name for the data-first form of a dual, or ends in `OrOptions`, as in `Stream.flatten`. The receiver is that parameter, written as the call's `this`, so TypeScript checks it and infers type parameters from it, and a type guard on it narrows the receiver: after `if (maybe.isSome())`, `maybe.value` is defined. A type's own members win, so an `Effect`'s `pipe` stays its own, and arrays, strings, and objects keep JavaScript's methods. A method that returns an Effect is a call like any other, so it runs: `fiber.join()` waits for the fiber. The emitted JavaScript calls the module's function, so bundlers drop unused functions as they do for Effect code. Hover on a method names the function it calls, and completion after a dot lists the module's methods. The docs codemod rewrote 180 blocks and removed 682 of 62,163 proxy tokens (1.1%). Controversial because Effect gave up fluent methods on purpose, for tree shaking and one calling style: VibeLang keeps tree shaking, since the methods exist only at compile time, but the same dot now reaches a member on one type and a module function on another, and a member that a later Effect release adds to a type takes the call from the module function of the same name.

**D153. A method of a data type exists only in a call** (EK4501). `const read = maybe.getOrElse` has no function value to bind, because the lowering rewrites the call, not the property. EK4501 reports the access and suggests calling it or passing the module's function, `Option.getOrElse`, itself.

**D154. `.vibe` files have the Hack pipe operator** (Will; **controversial**; supersedes D8). `x |> f(%, a)` evaluates the body `f(%, a)` with the topic `%` standing for `x`, as in TC39's Stage 2 proposal: `fetchUser(id) |> retry(%, policy) |> timeout(%, "1 second")`. The operator is `|` directly followed by `>`; it binds looser than every binary operator and the conditional operator, as an assignment does, and associates to the left. A body is a conditional expression, so an arrow function, an assignment, or a yield there needs parentheses. `%` where an expression starts is the topic of the innermost pipe whose body holds it; after an operand, `%` is still the remainder operator, so `n |> % % 2` is `n % 2`. The pipe has its body's type, and the body has the pipe's contextual type. Hover on `%` shows its type and whether it is a value or a program. The emitted JavaScript has no pipe: a topic used once, before anything in the body that could have an effect, becomes the left side itself (`price |> double(%)` is `double(price)`); otherwise the left side runs once into a variable, and a function in the body that reads the topic keeps the value of the evaluation that created it. The formatter keeps `|>` together. VibeLang uses `%`, the token in the proposal's README, although the proposal's wiki disqualifies it for engine parsing complexity; VibeLang's parser decides by position, and VibeLang will follow the token TC39 chooses. The docs rewrite changed 21 blocks, 15 to `|>` and 6 data-type pipes to method chains (D152), and removed only 23 of 61,678 proxy tokens: `x |> f(%, a)` costs what `pipe(() => x, f(a))` costs. Its gain is reading order and any argument position, not tokens. Controversial because the proposal has been at Stage 2 since 2021, its topic token is undecided, and TypeScript will not parse `|>` until Stage 3, so `.vibe` code moves further from TypeScript.

**D155. A topic follows the by-name rule** (Will; **controversial**; extends D147). Where `%` stands for an argument whose parameter expects a program, and the left side runs an Effect, the left side is passed by name: that `%` is a program that evaluates the left side each time it runs, and the left side does not run before the body. `fetchUser(id) |> retry(%, policy)` means `retry(fetchUser(id), policy)`, and in a chain each `%` passes everything before it: `timeout` in `a() |> retry(%, p) |> timeout(%, t)` receives the retried program. Elsewhere the left side runs once, before the body, and `%` is its value. A pipe that passes its left side by name and also uses it as a value is EK1008, because the left side would run both before the body and inside the program. A pipe whose topic is passed by name runs nothing at a module's top level, so EK1001 does not apply to its left side. Controversial for the reason D147 is: the parameter's type, not the source, decides whether the left side runs now or later; the hover on `%` says which.

**D156. Pipe syntax errors** (default). A body that never uses `%` is EK1006: the left side's value would go nowhere, which the proposal makes an early error. A `%` outside every pipe's body is EK1007; it resolves to the error type, so TypeScript reports nothing more.

## Fibers (2026-10-17)

**D166. `fork` is a keyword** (Will, lane fibers). `fork getUser(id)` parses as `fork(getUser(id))` and `fork { ... }` as `fork(() => { ... })`, so the fiber belongs to the enclosing block (D95) and the operand is passed by name (D147). The operand binds as `await`'s does: `fork a().b` forks `a().b`. The keyword form needs its operand on the same line, starting with a name, `this`, `new`, `super`, `{`, or `await`; `fork(` stays a call, which means the same, and `fork [x]` stays an element access, so no code that parses today changes meaning.

**D167. `await` waits for fibers and Deferreds** (Will, lane fibers; **controversial**; superseded by D225 and D226). Outside an `async` function, `await x` parses as the runtime call `$await(x)`, which runs where it stands: its value is what it waited for and its failures join E. It waits for a `Fiber`, a `Deferred`, or an array, tuple, or object of them, keeping the shape; when one fails, the fibers still running are interrupted and the failure propagates, as `Effect.all` fails fast. `await` before a call that already runs is EK4601, on a promise EK4602, on anything else EK4603, and inside a hatch's function that is not `async` EK4604. `async` stays EK1003, and inside an `async` hatch body `await` keeps its JavaScript meaning (D148).

**D168. `select` races its cases** (Will, lane fibers; **controversial**; superseded by D197). `select { case const x = a(): ... case b(): ... default: ... }` starts each case expression, a program passed by name, in its own fiber in the order written; the first to finish wins, its statements run with its binding, and the others are interrupted; a failure of the first to finish propagates. Of cases ready at once, the first written wins, because a case that finishes while the cases start stops the rest from starting. A `default:` clause runs when no case finishes while they start (a poll). `break` leaves the select, as it leaves a `switch`; the last clause, or `default`, is the final branch, so a select whose clauses all return ends the function. `select {}` waits forever, as in Go. It parses as a labeled block around `$select(...)`, whose result is a union discriminated by the case's index.

**D169. `for concurrent` runs a loop body per item** (Will, lane fibers). `for concurrent(n) (const x of xs) body` parses as `$forConcurrent(xs, n, (x) => { body })`, which is `Effect.forEach` with concurrency `n` (no limit without one) that discards results: every item runs in its own fiber, all join before the loop ends, and a failure interrupts the rest. `continue` ends one item (the parser writes it as a `return` from the body). A `break` that would leave the loop is EK4605 and a `return` is EK4606, because no loop runs on the body's fiber. Use `forEach` for results.

**D170. `detach` and `forkIn` are fork's variants** (lane fibers). `detach(program)` is `Effect.forkDetach`: a fiber nothing owns. `forkIn(scope, program)` is `Effect.forkIn` with the scope first, so the program reads last. Both take the program by name and are prelude names.

**D171. `await`'s types reach one level** (lane fibers; carried to `join` by D228). The runtime waits through nested arrays and objects, but its types, and the EK4603 check, accept an array or object only of `Fiber`s and `Deferred`s themselves: recursive conditional types over arbitrary nesting exceed TypeScript's instantiation depth. Nest awaits instead.

## Names follow Effect (2026-10-17)

**D172. The provide block is spelled `provide`** (Will; amends D130). `provide AppLive { ... }` replaces `with AppLive { ... }`, so the keyword is the name of the function it stands for, `Effect.provide`: VibeLang keywords reuse Effect's own names so a reader can map each form back to Effect. The parser reads `provide` as the block form only when a layer expression and an opening brace follow on the same line, so a local function or variable named `provide`, a call `provide(x)`, and an element access `provide[i]` keep their meaning. The old spelling still compiles the same way and draws EK1009, a warning, whose quick fix replaces `with` with `provide`; the language service matches EK quick fixes by the diagnostic source `EK`. The generated region function is `f$provide`. Not controversial.

**D173. `provide Key = value` provides one service** (Will; extends D130). A provide block's providers are separated by commas, and a provider written `Key = value` provides that one service, as `Effect.provideService` does: `provide AppLive, Clock = testClock { ... }` compiles to `Effect.provide` with `[AppLive, Layer.succeed(Clock.Clock, testClock)]`, and the block's requirements drop every provided key. The parser rewrites the list into an array of layers and each `Key = value` into `$provideService(Key, "Key", value)`, a runtime function whose types check the value against the key's service shape. It has one signature, with the name before the value, so a method in the value is checked against the key's shape from the start (D92). `provide(A, Key = value) { ... }` means the same as `provide A, Key = value { ... }`, as `fork(x)` means `fork x`; the parser reads the parenthesized list as an expression, not as arrow-function parameters. Not controversial.

**D174. An effect module stands for its key of the same name** (lane provide). In a `Key = value` provider, a module whose export of the same name is a service key stands for that key: `Clock` for `Clock.Clock`, `Random` for `Random.Random`, `Scheduler` for `Scheduler.Scheduler`. Those three are references with defaults, so providing one swaps a runtime service for the block and the fibers it starts without changing any contract. A hover over the key names the service it provides. A key that is neither a service key nor such a module is TS2769, which names the key's expected type. Not controversial.

**D175. A provider list is read element by element** (lane provide). The analyzer computes what an array-literal provider provides from each element's type. The array's own type merges the elements into one union, and because a layer is contravariant in what it provides, `Layer<Names> | Layer<never>` reduces to `Layer<never>`, which would hide `Names`. This also fixes `provide [NamesLive, RandomLive] { ... }` written as an array. Not controversial.

## Primitives (2026-10-17)

Will's rule: every Effect primitive has a form in the language itself, in Effect's own words, believable as TypeScript (`.cache/chat-feedback.md`). D176-D180 add the ones the primitives list kept.

**D176. A catch clause typed `Cause` catches every reason** (lane primitives; superseded by D217). `catch (cause: Cause)` (or `Cause<E>`, `Cause.Cause`) is `Effect.catchCause`: it sees expected failures, defects, and interrupts, binds the whole `Cause<E>` where E is what the try block can fail with, and may follow typed and untyped clauses, which still see expected failures only. Clauses after it never run (EK2106). It does not catch a control operation's abandonment, whose internal interrupt unwinds through. A try statement with one makes its function an Effect. A type annotation choosing semantics is new for `catch`; it reuses the typed clauses' shape (D131).

**D177. `throw cause` rethrows every reason** (lane primitives). Throwing a value whose type is a `Cause` (or a union of them) is `Effect.failCause`: the failure keeps every reason, and the Cause's E joins the function's E. Throwing any other value keeps D13's meaning.

**D178. `finally (exit)` binds the Exit** (lane primitives). `finally (exit) { ... }` is `Effect.onExit`: the block runs on every exit without interruption, with `exit: Exit<void, E>`, E being what the try statement can fail with. A success carries no value, because the try block's statements have none; a `return` inside the try block still returns its value. `finally { ... }` keeps D15's meaning.

**D179. `exit`, `interrupt`, and `yieldNow` are bare functions** (lane primitives; extends D151). `exit(program)` is `Effect.exit` with the program passed by name; `interrupt()` is `Effect.interrupt` and `yieldNow(priority?)` is `Effect.yieldNow` or `Effect.yieldNowWith`, functions in the runtime because Effect's own are values. A bare `yield` statement was rejected: it clashes with producers and is not Effect's word.

**D180. `uninterruptible`, `restore`, and `interruptible` blocks** (lane primitives; **controversial**). `uninterruptible { ... }` is `Effect.uninterruptibleMask`; `restore { ... }` inside it runs its statements with the interruptibility the region began with; `interruptible { ... }` is `Effect.interruptible`. Statements inside stay code of the enclosing function, so `return`, `break`, and `continue` keep their meaning. Each block calls the prelude function of its name, `uninterruptible(program)`, `restore(program)`, or `interruptible(program)`, which also take a program directly (by name, D147), so a block read as a block parameter means the same apart from jumps. `restore` finds the innermost region's restore through a fiber reference, so a restore outside any region runs its program unchanged; the block form there is EK2111. At a module's top level the blocks are EK1001. The words are contextual: a name followed by `{` on the same line is a TypeScript syntax error, so no code that parses today changes meaning.

## TC39 forms: blocks (2026-10-17)

**D186. `throw` is also an expression** (lane blocks; [throw expressions](https://github.com/tc39/proposal-throw-expressions), stage 2). In a `.vibe` file, `throw` in expression position takes a unary expression, as the proposal's grammar has it: `users.get(id) ?? throw new NotFound({ id })`, `ok ? value : throw new Invalid()`, `(id) => find(id) ?? throw new NotFound({ id })`. It parses as `(() => { throw operand })()`, so it fails exactly as the throw statement does (an `error` value joins E, a Cause rethrows) and has type `never`; the right side of `??`, `||`, `&&`, and `?:` still runs only when chosen. A statement that starts with `throw` is the throw statement. Its operand is the whole expression, as in TypeScript. In expression position, an unparenthesized `throw` on the left of a binary operator (except comma), as a conditional's condition, or as the operand of `as` or `satisfies` is refused with EK1010: only its unary operand would be thrown. Write `throw (cond ? a : b)` in a catch-expression handler to throw the selected value (S10-12); right-hand throws such as `x ?? throw e` stay legal.

**D187. `do { }` is an expression** (lane blocks; [do expressions](https://github.com/tc39/proposal-do-expressions), stage 1). `do { statements }` in expression position has the completion value of its last statement: an expression statement, an `if` with an `else` whose branches end in one, a `try`/`catch` whose blocks end in one, or a `throw`. A declaration, a loop, or an `if` without `else` at the end is TS1109, and a `return` inside is TS1108, as the proposal forbids it. It parses as `(() => { ...; return last })()`, so it runs where it stands, and a parameter that expects a program takes it by name (D147): `race(do { sleep("1 millis"); "cached" }, fetch())`. A statement that starts with `do` is the do-while statement.

**D188. A block after a call is its program** (lane blocks; [block params](https://github.com/samuelgoto/proposal-block-params), stage 1; **controversial**: where the block goes depends on the callee's type). In a `.vibe` file, a `{` on the same line after a name, a property access, or a call passes the block as a program: `f { block }` is `f(() => { block })`, and `f(args) { block }` is `f(args, () => { block })`, one call. Where `f` is an Effect dual, the block takes the place of its program: the checker also resolves the call against `f`'s data-first signature with its first parameter moved last and its data-last signature flattened to `(args, self)`, so `withSpan("load") { ... }`, `timeout("1 second") { ... }`, and `semaphore.withPermits(1) { ... }` infer every type parameter from the arguments and the block together. The lowering emits `f(block, args)` or `f(args)(block)` for those forms and `f(args, block)` otherwise, as in `it.effect("greets") { ... }`. When several forms fit, the data-first form wins, then the data-last, then the appended call. A block param body is a function body, so a value needs `return`. A heritage clause, `new`, and a provide block's providers keep their own `{`.

## TC39 forms: await operations (2026-10-17)

**D196. The await operations start programs concurrently** (amended by D258) (Will's rule that new syntax comes from TypeScript or a TC39 proposal; lane await-ops; **controversial**). `await.all x`, `await.allSettled x`, `await.race x`, and `await.any x` come from the [await operations](https://github.com/tc39/proposal-await.ops) proposal (stage 1); an object operand comes from [Await Dictionary](https://github.com/tc39/proposal-await-dictionary) (stage 3, `Promise.allKeyed`). The parser writes them as calls of the runtime's `$awaitAll`, `$awaitAllSettled`, `$awaitRace`, and `$awaitAny`, with the operand bound as `await`'s is. Each element is a program passed by name (D147), started in its own fiber; an element that is a `Fiber` or a `Deferred` already running is waited for, not restarted, and a `do { }` element (D187) is a program with statements. Each operation behaves as the `Promise` method of the same name: `await.all` is `Effect.all` with unbounded concurrency (every result, the shape kept, an object's keys in the order written, fail fast with the rest interrupted, held fibers included); `await.allSettled` is `Effect.all` with `mode: "result"` and never fails with a typed error; defects and interruption propagate; `await.race` is `Effect.raceFirst` over any number of elements (the first to finish wins, success or failure; of elements ready at once the first written wins; an empty race never finishes); `await.any` is `Effect.raceAll` (the first success; failure only when every element fails). A race over an object is EK4608. Controversial: the docs rule is "`await.x` behaves like `Promise.x`; a named Effect function keeps Effect's meaning", so `await.race` takes the first to finish while `race(...)` (D151) takes the first success. The alternative, dropping `race` from the bare functions, loses Effect's own name for the common case.

**D197. `await.race` replaces `select`** (Will; supersedes D168). Will found `select { case ... }` foreign: `case` reads as comparing a value, and "select" is not Effect's word. `select { ... }` still parses so that the checker can report EK4607 at its keyword with the replacement: `await.race [a(), b()]`, one element per case, with `do { ... }` for a case's statements. A `default:` clause has no replacement form; poll with `Queue.poll` and an `if` (or `match`). The runtime keeps `$select`, which `$awaitRace` uses.

## TC39 forms: pattern matching (2026-10-17)

All from the TC39 [pattern matching](https://github.com/tc39/proposal-pattern-matching) proposal (stage 1), under Will's rule that new syntax comes from TypeScript or a TC39 proposal.

**D206. `match` is an expression of `when` arms** (lane match). `match (x) { when P: v; ... default: d; }` takes the proposal's syntax: arms are tried in order, the first match gives the value, and `default:` matches anything and must come last. An arm ends with `;`, and ASI applies. `match (x) {` followed by `when`, `default`, or `}` on the same line starts a match; any other `match(...)` is a call, so a function named `match` keeps working. As in the proposal, `and`, `or`, and `not` cannot share a level without parentheses (EK4705). An arm is one expression; `do { }` (D187) gives it statements.

**D207. The supported subset** (lane match). Literals; `let`, `const`, and `var` bindings; array patterns with a rest; object patterns with shorthand bindings, quoted and computed keys, and a rest; identifier and dotted matchers; extractors with an argument list (`Option.Some(let v)`); `and`, `or`, `not`; `if (expr)` guards; `default`; and `x is P`. Deferred: regular expression and relational patterns, `async match`, and iterables in array patterns (D212, D214).

**D208. Option, Exit, Result, and primitive classes are known matchers** (lane match; **controversial**). `Option.Some`/`None`, `Exit.Success`/`Failure`, `Result.Success`/`Failure` compile to the module's own guard and read `value`, `cause`, `success`, or `failure`; `String`, `Number`, `Boolean`, `BigInt`, and `Symbol` compile to `typeof`. The bindings get exact types and need no runtime protocol. Controversial: the proposal resolves every matcher through `Symbol.customMatcher` at runtime, so a local variable named `Option` that shadows the module still compiles to `Option.isSome`. The alternative, custom matchers on Effect's data types, needs Effect to ship them and types the bindings loosely.

**D209. Exhaustiveness is checked at compile time for finite unions** (lane match; **controversial**). A match without `default` whose subject's declared type is a finite union (literals, `null`, `undefined`, `void`, and objects with a string literal `_tag`, which covers `error` classes, Option, Exit, and Result) and whose narrowed type after the last arm is not `never` is EK4701, as `Match.exhaustive` is. Over any other type, an unmatched value throws the proposal's `TypeError` at runtime (`$noMatch`). Controversial: the proposal has no static check, and a match over `number` without `default` compiles even when an arm is missing; reporting every non-`never` remainder would flag correct matches whose guards TypeScript cannot narrow.

**D210. `or` and `not` cannot bind yet** (lane match). A binding inside `or` or `not` is EK4702. The proposal allows a binding in every alternative of an `or`; the lowering writes `or` and `not` as inline boolean expressions, which have nowhere to declare a name.

**D211. `is` binds only in an `if` or `while` condition** (lane match; **controversial**). `x is P` is a boolean at `instanceof`'s precedence. With bindings, it must sit in the `&&` chain of an `if` or `while` condition; the names are in scope in the rest of the chain and in the then branch or loop body. Elsewhere it is EK4703. Controversial: the proposal scopes `is` bindings to the enclosing block and the else branch too; this lowering nests the then branch inside the tests, so names cannot reach the else branch or the statements after.

**D212. Unsupported forms are reported, not misparsed** (lane match). A regular expression pattern, a relational pattern such as `< 10`, and a computed key other than a name or a literal are EK4704, whose fix is a guard: `and if (n < 10)`.

**D213. Matcher semantics** (lane match; **deviation** from the proposal). A matcher value with a `[customMatcher]` method decides. Otherwise a primitive class tests `typeof`; another class tests `instanceof`; another function is a predicate; any other value matches by SameValue, with `0` matching `-0`. A class is a function written with `class` or one whose prototype has methods, so built-ins such as `Date` and `Map` test `instanceof`. Deviation: the proposal gives built-in constructors brand checks (`Date` matches a cross-realm date), which a runtime helper cannot write.

**D214. Lowering and its limits** (lane match). A match after `return` becomes a block whose arms return; a match statement becomes a labeled block whose arms break; any other match becomes an immediately invoked arrow function, which is a VibeLang function, so arms can call Effect functions in every position. A subject that is a name, `this`, or a chain of property and literal element accesses is used directly, so TypeScript narrows it in each arm; others are held in a `const`. Limits: an arm of a match in expression position cannot `yield`; a direct subject is read once per test, which a getter can observe; array patterns match arrays only; object patterns do not match primitives.

**D215. `customMatcher` and tagged errors** (lane match). The runtime exports `customMatcher`, the engine's `Symbol.customMatcher` when it has one and `Symbol.for("Symbol.customMatcher")` otherwise. `TaggedError`, so every `error` class, has a static custom matcher: `instanceof` for `is` and `when NotFound:`, and the instance as the single value for `NotFound(let e)`. Two error classes with the same tag therefore stay distinct, unlike `catchTag`.

## Catching with match (2026-10-17)

**D216. A catch clause no longer tests a failure's type** (Will: catching by tag is "too magical"; supersedes D131). Catch the failure and test it with pattern matching (D206): `catch (e) { return match (e) { when NotFound: "missing"; default: throw e; } }`, or `if (e is NotFound) { ... }` in statement form. No special catch syntax remains. A typed clause, `catch (e: NotFound)`, still compiles as D131 describes and draws the warning EK2112.

**D217. Recovering from a whole cause matches on its exit** (Will; supersedes D176). `match (exit(program)) { when Exit.Success(let value): value; when Exit.Failure(let cause): fallback; }`, or `if (outcome is Exit.Failure(let cause))`, sees every reason: failures, defects, and interrupts. A catch clause typed `Cause` still compiles as D176 describes and draws the warning EK2113.

**D218. A match on a caught failure is checked like any match** (lane catch). An untyped catch variable has the try block's expected failures as its type (D13), so `match (e)` without `default` must handle every one of them (EK4701, D209) and then needs no rethrow; `default: throw e` passes the others on with their types, through a throw expression (D186). The function's E is what the arms let escape.

**D219. The quick fix rewrites retired clauses when the result is exact** (lane catch). EK2112's fix writes one `match` when every clause is a single `return` of a value and every clause names one variable, and an `if (e is T) { ... } else ...` chain otherwise, ending in `else { throw e }` when no untyped clause followed. A clause's type becomes a pattern only when each union member names a class, such as an `error` declaration or `Schema.SchemaError`; for a type alias or an object type the warning has no fix. ## Join (2026-10-17)

**D225. `join` is a keyword** (Will, lane join; supersedes D167). `join fiber` parses as the runtime call `$join(fiber)`, which is `Fiber.join`: its value is the fiber's and its failures join E. `join [a, b]` and `join { a, b }` join every fiber of an array, tuple, or object and keep the shape; when one fails, the fibers still running are interrupted and the failure propagates, as `Effect.all` fails fast. The operand binds as `fork`'s does (D166), and the keyword form needs its operand on the same line, starting with a name, `this`, `{`, or `[` after a space. `join(` stays a call and `join[i]` without a space stays an element access, so a local or imported function named `join`, `path.join`, and `words.join(",")` keep working. A `join` on anything but fibers is EK4611, and a `join` inside a hatch's function, which is plain TypeScript, is EK4612.

**D226. A plain `await` in VibeLang code is an error** (Will, lane join; **controversial**). In JavaScript `await` waits for a promise, so VibeLang keeps that meaning and gives `await` no other: `await fiber` is EK4609, whose quick fix writes `join fiber`; `await d` on a Deferred is EK4610, whose quick fix writes `d.await()`; `await` before a call that already runs is EK4601; a promise is EK4602 and waits in a hatch, `try(async () => …)`; anything else is EK4603. **D227. A Deferred waits with `d.await()`** (lane join). Method syntax (D152) already reaches `Deferred.await`, so a Deferred needs no keyword: `ready.await()` returns its value and propagates its failure.

**D228. `join`'s types reach one level** (lane join; carries D171). The runtime joins through nested arrays and objects, but `$join`'s types and the EK4611 check accept an array or object only of `Fiber`s themselves. Nest joins instead.

## Self-contained hatches (2026-10-17)

Will on hatches: "typescript has to be self contained you can't use values or closures from outside of typescript when writing typescript ... I could see that changing later" (Telegram, 2026-10-17).

**D229. A hatch's TypeScript is self-contained** (Will, lane hatches; **controversial**; amends D148). A hatch's first argument, the function or single expression of `sync`, `try`, or `callback`, may reference its own parameters and locals, globals, prelude names, imports, and the file's `error` declarations, but no other value binding of the `.vibe` file: not an enclosing local or parameter, and not a module-level declaration. A reference to one is EK4405, an error that names the binding, and its quick fix passes the binding as an input (D230). Types are exempt. Error declarations are exempt because an error class is a plain class, and failing with one, `new BadJson({ error })`, is what a hatch most often needs from its file. Controversial because a capture is the shortest way to hand a value to TypeScript. The rule makes a hatch's function read like a standalone TypeScript function that could move to a `.ts` file unchanged, and keeps a VibeLang value from entering TypeScript unannounced. Will expects that it may change.

**D230. Inputs fill the first parameters** (lane hatches). Values reach a hatch as inputs, the arguments after its function: `sync((a, b) => a + b, 2, 3)`, `try((text) => JSON.parse(text), text)`. They fill the function's first parameters, so TypeScript types each parameter from its argument. An async function receives its `AbortSignal` after them, `try(async (url, signal) => fetch(url, { signal }), url)`, and a callback's register function receives `resume` and the signal after them, `callback((ms, resume) => …, 2)`. The compiler lowers inputs with `bind`, `Effect.sync(((a, b) => a + b).bind(undefined, 2, 3))`, so Effect's own signal argument lands after them. A single expression takes no inputs. The alternative, Effect's arguments first, `callback((resume, signal, ms) => …, 2)`, keeps Effect's parameter positions but needs a wrapper function in the lowering and moves the inputs' parameters with each arity. Inputs keep `callback`'s type arguments from being written, because TypeScript infers no type argument once one is written; the prelude type `Resume<A, E>` annotates `resume` instead: `callback((source, resume: Resume<number, Error>) => …, source)`.

**D231. `try`'s error mapper stays second** (lane hatches). `try(code, mapper, ...inputs)`: the mapper keeps the place D148 gave it, and inputs follow it, `try((text) => JSON.parse(text), (error) => new BadJson({ error }), text)`. With inputs first, the mapper's place would move with the number of inputs; with the mapper last, `try(f, g)` would change meaning from D148's. The compiler tells a mapper from a function input by the overload TypeScript chose: a function in second place that accepts the `unknown` error is the mapper. The runtime's `try`, which TypeScript callers and a hatch passed as a value reach, sees only values, so there a function in second place is always the mapper.

**D232. Only the first argument is TypeScript** (lane hatches; amends D148). D148 made all of a hatch's arguments plain TypeScript; now only the first is. The inputs and the mapper are VibeLang code: the inputs run before the hatch starts, so a call among them runs, `sync((name) => name.toUpperCase(), readName())`, and a plain foreign call or a clock read among them is EK4401 or EK4403 as anywhere in VibeLang code. The mapper is an ordinary callback that may read the file's bindings, `(cause) => new ChargeFailed({ cartId, cause })`. The function decides between sync and async: an `async` function, or one whose return type has `then`, is `Effect.promise` for `sync` and `Effect.tryPromise` for `try`; an `any` or `unknown` return stays synchronous.

## Catch expressions (2026-10-17)

Borrowed from Zig's inline catch (`parse(s) catch 0`), which Will approved for the catch lane. TypeScript has no such proposal, but `catch` after an expression is a syntax error today, so no code that parses changes meaning.

**D236. `catch` is also an expression** (Will, lane catch). `x catch fallback` is `Effect.orElseSucceed`: the fallback is evaluated only after an expected failure, and because it is VibeLang code it may run a program itself, as `Effect.orElse`'s would. `x catch (e) => expression` is `Effect.catch`: the handler receives the expected failure, typically `getUser(id) catch (e) => match (e) { when NotFound: guest; when Timeout: cached(id); }`. The left side is passed by name (D147), so it runs inside the catch. Defects and interrupts pass through, and so does a cause that mixes an expected failure with either, as the `catch (e)` statement lets them (D13); Effect's own `Effect.catch` would recover from such a mixed cause. The parser writes `$catchExpression(() => x, () => fallback)` or `$catchExpression(() => x, (e) => expression)`, and the runtime runs it with the kernel's `catchExpected`, which the statement uses.

**D237. `catch` binds between `??` and `? :`** (lane catch). It binds looser than every binary operator, `??` and `||` included, and tighter than `? :`, assignment, arrow functions, and `|>`. It associates to the left: `a() catch b() catch c` tries `b()` after `a()` fails and falls back to `c` after `b()` fails. `lookup(id) ?? "unknown" catch "failed"` applies the default inside the catch, `ok ? find(id) catch "none" : "skip"` catches in one branch, and `id |> find(%) catch "none"` catches inside the pipe's body. A handler is an arrow function, `(e) => …` or `e => …`, whose body extends as far as an arrow function's does, so a `catch` after it belongs to the handler; parenthesize the handler to chain after it. Any other right side, a parenthesized arrow function included, is a fallback. After a try block's `}`, `catch` is the statement's.

**D238. A catch expression is typed and checked as the statement is** (lane catch). The value is `A | B`, A from the left side and B from the fallback or handler. E is what the fallback or handler lets escape: the handler's parameter has the left side's expected failures as its type, so a `match` without `default` must handle every one of them (EK4701, D209) and then removes them all from E, and `default: throw e` passes the rest on with their types (D186). R joins both sides'. A left side with no expected errors is EK2004; defects pass through. A try statement gets that warning only when its block runs Effects with E = `never` (D260). A hover on the keyword names the Effect function, the failures it catches, the value, and the failures that escape.

**D239. No catch expression in a hatch body** (lane catch). A hatch's function is plain TypeScript (D148, D232), where `catch` is only a statement, so a catch expression there is EK2114; move it out of the hatch, or use a try statement inside. At a module's top level it runs a program, so EK1001 applies.

No rule needed a language change: the one candidate, nested `provide` blocks, already has D173's `provide A, B { … }`, which EK4808's quick fix writes.

**D241. EK4801-EK4825 are lint** (lane lsp-rules). Unlike VibeLang's other diagnostics, none marks code without a meaning, so each has a default category and a project can change it: every one except EK4813 is in `compilerOptions.vibelang.diagnostics`, and nine of them are off until a project turns them on. An `@vibelang-diagnostics` comment changes a category from its line to the end of the file, and `@vibelang-diagnostics-next-line` for the next line, as Effect's `@effect-diagnostics` comments do; `*` names every adjustable code. Neither applies to the other EK codes, so `@ts-expect-error`'s rule (D53) stands.

**D242. Three rules also apply to `.ts` files** (superseded by D266) (lane lsp-rules; **controversial**). When VibeLang serves a project's `.ts` files, it replaces the TypeScript server that would run `@effect/tsgo`, so its three correctness rules about how Effect code runs report there too: a discarded Effect (EK4801), `yield` without `*` in an Effect generator (EK4819), and `yield*` of an Effect that never succeeds without `return` (EK4820), each with a quick fix, plus the Effect 4 rename on TS2339. The other rules are about VibeLang's forms or are style; for them, serve `.ts` files with `@effect/tsgo`. Files under `node_modules` are not checked. This is the first EK code in a `.ts` file, which until now kept TypeScript's meaning exactly.

**D243. EK4813 stands in for TS2339** (lane lsp-rules). An Effect 3 name of the Effect module, such as `Effect.catchAll`, is already TypeScript's TS2339. EK4813 replaces it with the Effect 4 name, from the migration table of Effect's language service, and its quick fix writes that name; a `.ts` file keeps TS2339 and gets the same quick fix. As a replaced type error, it is an error that cannot be lowered.

**D244. Defaults stricter than Effect's** (lane lsp-rules; **controversial**). Effect's language service turns off `extendsNativeError`, `newPromise`, and `unsafeEffectTypeAssertion`; VibeLang warns (EK4805, EK4812, EK4810), because a failure in VibeLang is an `error` declaration, VibeLang code cannot wait for a promise, and a contract is only as good as the types it checks. Effect's suggestion level has no VibeLang counterpart, so its suggestions that mark likely bugs (`returnEffectInGen`, `leakingRequirements`) are warnings, and style rules are off.

**D245. Refactors are code actions of kind `refactor.rewrite`** (lane lsp-rules). The language server gains a refactor seam, `ls.RegisterRefactorProvider`, beside its quick fixes, and advertises `refactor.rewrite`. Effect's 15 refactors become seven in `.vibe` files, because VibeLang has one function form and no `Effect.gen`: "Write the inferred contract" and "Remove the contract" (Effect's "Toggle return type signature" and its `annotate` codegen), "Convert to a schema declaration" (an interface or object type alias, Effect's "Structural Type to Schema" and `typeToSchema`), "Convert to a VibeLang function", with or without an `error` declaration per `await` (Effect's four async refactors; each `await p` becomes a `try` hatch that passes what `p` reads as inputs, D229), "Convert to a pipe" and "Convert the pipe to calls" (Effect's pipe and data-first refactors, and `missedPipeableOpportunity`), and the two pipe styles.

**D246. Effect's hovers and completions, VibeLang's way** (lane lsp-rules). A layer's hover lists what it provides, needs, and fails with, and `wire`'s hover lists the order it builds its layers in and which layers each uses: Effect's layer hover and layer graph, as text and without its external graph link. The language server gains a completion seam, `ls.RegisterCompletionHook`, that answers before TypeScript: a string where a `Duration.Input` goes completes `"2 seconds"` and the other units, `Schema.brand("…")` completes the declared name, and an `@vibelang-diagnostics` comment completes its marker and the adjustable codes. Effect's `Self`, `Effect.gen`, `Effect.fn` span, and namespace import completions have nothing to complete in VibeLang.

**D247. Platform package scoping** — Superseded by Will’s W38 (2026-10-18): publish VibeLang 0.0.1 with unscoped `vibelang-<os>-<cpu>` packages.

## The (B) projector keeps D24 (2026-10-18)

**D248. Where L3 and D24 disagree, the switch keeps D24 or asks** (D250 withdrawn by D251) (VibeLang language lead, lane value-call). The text-only projector decides at run time whether a call's result runs (L3, `$isRun`), and to it an `Exit` is a program. D24 decided from types that a call returning an `Exit`, a `Config`, or an error instance returns data, and D43 relies on it: `resume(Exit.succeed(value))` passes the `Exit` as data. Wherever the fork's types say data and L3 would run, the switch keeps D24's meaning or reports EK9100, which asks for an annotation. It never changes what code does without a diagnostic. So `sync(() => Exit.succeed(42))` written without a return type reports EK9100 under the switch, and `sync((): Exit.Exit<number, never> => Exit.succeed(42))` is plain (L2) and returns the `Exit` as data under both compilers. Evidence: the case `vibelang-effect-value-calls`, migrated with that annotation, and a regression case that keeps the unannotated form and expects EK9100.

**D249. A trusted contract becomes a value, `trusted(impl, [Errors])`** (VibeLang language lead, lane value-call; amends D23; **controversial**). The (B) projector reads one file at a time, so it cannot see a JSDoc tag on another file's declaration, and D23's `@vibelang trusted` and `@throws` cannot reach its emit. The TypeScript file states the contract as a value instead: `export const parsePortTrusted = trusted(parsePort, [PortError])`, a public `vibelang-runtime` export that takes the implementation's parameters and returns `Effect<A, E>`, where a listed class is an expected failure and any other exception is a defect, as `$trusted` does today. The contract stays beside the function it describes, which is why D23 put it there, and TypeScript callers keep calling `parsePort`. Under D248, a dropped tag must never change behavior silently. Until the switch, the fork's checker warns at every `.vibe` call of a D23-tagged declaration whose lowering uses the tag (in an Effect function, outside boundary callbacks), with a quick fix that adds `<name>Trusted` beside the declaration and rewrites the call. A call at top level or in a plain or boundary callback is plain under both compilers, so it gets no warning. From the switch on, such a call is an error, because a `PortError` would otherwise become a defect without a diagnostic. Rejected: passing tag contracts into Project's FileContext (cross-file input to the per-file mapper, which breaks stock TypeScript tooling, the reason for (B)), and `Effect.try` at each call site (moves the contract away from the function). The cases `trust-levels` and `ch10-typescript` migrate to `trusted(...)` values, so they keep proving typed failures from TypeScript.

**D250. L3 treats an `Exit` as data** (withdrawn by D251) (VibeLang language lead, lane value-call; amends D248). The run check `$isRun` excludes an `Exit` by its type ID, as it already excludes a `Config`, a Context key, and an error, and `$run`'s types keep `Exit<A, E>` as a value. So D24 holds in both renderings by construction: a call that returns an `Exit` returns it as data, D43's `resume(Exit.succeed(value))` passes it as data, and calling an `Exit` value still runs it. This also covers an `Exit` that only the checker knows, such as one returned by a helper imported from a `.ts` file, which a text-level diagnostic could not see. It needs no annotation and no EK9100 for `Exit`, so D248's example `sync(() => Exit.succeed(42))` is correct code under both compilers, and `vibelang-effect-value-calls` passes unmigrated. D248's rule stands for every other place where L3 and the fork could disagree. Rejected: EK9100 where the text proves an `Exit` (it misses checker-only `Exit`s, so it would violate D248), and a fork-only checker diagnostic (it does not cover stock TypeScript tooling).

**D251. At run time an `Exit` runs; the checking rendering rejects running a D24 data type** (narrowed by D254) (VibeLang language lead, lane value-call; withdraws D250). D250 was unsound. In Effect 4.0.5, `Effect.succeed` is `exitSucceed` (`effect/src/internal/effect.ts:957`), so an ordinary succeed or fail program is an `Exit` object at run time, and excluding `Exit` from `$isRun` turned those programs into data: `lambda-forms` and `ref1-existing-service` regressed, and two helpers that return the same `Exit`, one declared `Exit<number>` and one `Effect<number>`, could not be told apart. Only the static type separates data from a program, and the executable rendering has no types. So L3 runs an `Exit` at run time, as before. The checking rendering, which TypeScript type-checks for the fork and for stock tooling alike, rejects a run position whose static type is a D24 data type, such as `Exit`, with a type error that names the annotation. `$run`'s first overload takes `T & DataEffect`, which keeps `generic<T>(x: T)` inferred as `Effect<T>`. A helper declared `Effect` runs the same way in both renderings, and a value declared `Exit` can never run silently, which is D248's rule. Rejected: keeping D250 (silent wrong results for every opaque helper that returns `succeed` or `fail`), and carrying static types into the emit (not available to a projector that reads text only).

**D252. The (B) projector keeps D152's data methods by dispatching unproven receivers at run time** (amended by D253) (VibeLang language lead, lane annotation census; implements D152 under (B)). A projector that reads one file at a time cannot always prove from text which of D152's modules declares a receiver's type: the census of the docs found 131 such method calls. They type-check through the prelude's module augmentation in the checking rendering, as the fork's D152 does. The executable rendering emits the module's function where the text proves the module, and `$method(x, "isSome", args)` elsewhere. `$method` dispatches on the receiver's TypeId to exactly one of D152's modules. As D152 requires, a value's own member of that name wins, and arrays, strings, plain objects and any value without one of those TypeIds keep JavaScript's method call, so `$method` never calls a module function on a value D152 does not cover. Unproven calls lose tree-shaking for their module function; a proven call keeps it, and the docs and examples prefer forms the text proves. Rejected: errors at unproven receivers (131 documented uses of Will's D152 would stop compiling), and passing receiver modules from the fork into Project (it breaks the content mapper's per-file model for stock tooling).

**D253. A data method whose module the run time cannot tell apart asks for an annotation** (VibeLang language lead, D252 review; amends D252). In Effect 4.0.5 an `Exit` carries both the Exit and the Effect TypeIds: `makeExit` builds its prototype from `ExitTypeId` and the primitive prototype, which spreads `EffectProto` (`effect/src/internal/core.ts:100-101, 531-548`). `Effect.succeed` and its siblings are Exits, and Cause errors such as `NoSuchElementError` carry both the Effect and Cause TypeIds. So `$method` dispatches an unproven receiver only when exactly one module among the call's candidates matches a TypeId the value carries. For a method name that two such modules both define (Effect and Exit: `asVoid`, `isFailure`, `isSuccess`, `map`, `mapBoth`, `mapError`, `match`; Effect and the Cause errors), an unproven receiver is a projector diagnostic that asks for an annotation or for `Module.fn(x)`, never a run-time guess (D248). Likewise an optional or uncalled access to a data method on an unproven receiver is a diagnostic, matching the fork's TS2339 and EK4501. A value's own member wins only when it is callable, and candidates are only exported module functions.

**D254. The checking rendering rejects running only an `Exit`** (VibeLang language lead, lane gate 1; narrows D251). The run-time check `$isRun` already tells a `Config` (its `~effect/Config` key), a Context key (`~effect/Context/Service`), and an error (an `Error` instance, or a YieldableError by its Effect identifier across realms) from a program, and keeps each as data (`effect/src/Config.ts`, `Context.ts`, `internal/core.ts`; verified in the fast-call review). So `$run`'s types keep those values as data too, matching what runs, and D251's type error stays only for `Exit`, the one D24 type the run time cannot separate from a program, because an `Exit` carries Effect's TypeId. Types and run time agree on every other D24 type, so nothing changes silently (D248), and code such as `function withFallback(name: string): Config.Config<string> { return Config.orElse(…) }` followed by `withFallback("MISSING")()` needs no annotation or wrapper. Rejected: keeping the guard on Config, keys, and errors, which makes users wrap every such value reached through a call although the run time already handles it.

## Launch audit rulings (2026-10-18)

**D256. D15 binds VibeLang's own cleanup; Effect operators keep Effect's semantics** (CEO-approved audit ruling; D22 governs). VibeLang never drops a failure from cleanup it runs itself: `using`, `finally`, scope closing, and `abandon` under interruption. This does not extend to failures an Effect operator discards by design, including `timeout`/`race` dropping a loser's cleanup failure. In Effect 4.0.5, `timeout` calls `timeoutOrElse`, which calls `timeoutOption`, which races the source against the timer with `raceFirst` (`effect/src/internal/effect.ts:3870, 3836, 3895`). `raceAllFirst` resolves on the first fiber's exit and interrupts losers on the parent's exit through `onExitUnsafe` and `fiberInterruptAll`; their exits do not join the parent's cause (`effect/src/internal/effect.ts:1668-1700`). Keep this limitation visible and pin the observed behavior with a runtime case so an Effect upgrade that changes it shows up. Report the lost finalizer failure upstream; do not fork `timeout`.

**D257. Overload ranking applies D147 per candidate and prefers passing a program by name** (CEO-approved audit ruling). Among applicable overloads, a candidate whose parameter expects an `Effect` and passes a program argument by name outranks one that would run that same argument. A running call whose result type is `never` makes no parameter applicable during ranking: it means the call fails, not that every parameter accepts it by vacuity. Thus `Effect.race(Effect.fail(a), Effect.fail(b))` selects the two-program form, passing both programs by name, instead of running the second argument as the curried form's `options`. The same rule covers `raceFirst`, `zip`, and `orElse`; a genuinely data-last call such as `pipe(x, Effect.race(y))` keeps the curried form.

**D258. `await.allSettled` never fails with a typed error; defects and interruption propagate** (CEO-approved audit ruling; amends D196). It captures every typed failure, E, as a `Result.fail`, and propagates defects and interruption exactly as `Effect.all(…, { mode: "result" })` does. A defect is a bug, and interruption is the caller's cancellation, rather than an outcome to settle. In Effect 4.0.5, `Effect.result` calls `matchEager` with `onFailure: Result.fail`; `findError(cause)` leaves a cause with no typed failure, including defect-only and interruption-only causes, unchanged (`effect/src/internal/effect.ts:3534, 3718-3745`). `all` applies `result(effect)` in mode `"result"` (`effect/src/internal/effect.ts:4697`). Keep the per-element `Result` type; an `Exit` per element would expose Cause to every caller. Pin defect and interruption propagation with runtime cases.

**D259. The language server treats `null` as absent for optional client fields** (CEO-approved audit ruling). In client-to-server messages, the VibeLang language server reads `null` as absent wherever LSP 3.17 permits the client to omit the field. It never sends `null` for an optional field itself, and required fields stay strict. This tolerates Zed 0.195.3's actual payload so VibeLang works by default in that editor. Implement the tolerance in the fork's LSP decoder, retain the payload as a fixture, and report the spec violation upstream to Zed so the tolerance can eventually be retired.

**D260. Plain contracts keep JavaScript try/catch** (effectscript-4a ruling, `d-syzjja`; amends D37 and D54). A function with a plain contract keeps JavaScript's `try`, `catch`, `finally`, and `throw`: its catch receives every exception its try block throws, as `unknown`, exactly as TypeScript does. The lowering inserts no `$caught` rethrow and no expected-failure wrapper there. Defects are an Effect-level notion: an exception becomes a defect only where it escapes a plain function into an effectful caller, unchanged. An Effect region still catches expected failures only and lets defects and interruption pass through (D13). EK2004 applies to a try statement only when its block runs Effects and E is `never`; its message says defects pass through the catch, rather than claiming the catch can never run. Smithers twins pin coercion through a throwing `Symbol.toPrimitive`, a throwing getter, a revoked Proxy, and a throwing prototype lookup; an Effect try with E = `never` still warns and propagates a defect at runtime.

## Smithers twin rulings (2026-10-18)

**D261. Projects may trust TypeScript packages by name** (CEO-approved twin ruling, `a-6gx4l5`, finding D-2; extends D22). `compilerOptions.vibelang.trustedPackages` lists package-name globs, for example `["@smthrs/*"]`, matched against the nearest `package.json` name, including workspace packages outside `node_modules`. Globs match the whole name: `*`, `?`, and character classes match within a slash-delimited segment. A matching package receives D22's terms: an export that does not return an Effect is a synchronous call whose exceptions are defects, its Effects run where called, and calls into it do not report EK4401. The option does not list expected failures: D249's `trusted(impl, [Errors])` remains the per-function contract for those failures. Without a matching option, foreign calls keep EK4401.

**D262. An explicitly Effect-typed top-level const holds a program** (CEO-approved twin ruling, `a-6gx4l5`, finding B-2; extends D147 and D103). At a module's top level, a `const` whose declared type is an Effect is a program position: `export const migrate: Effect.Effect<void, E, R> = Effect.suspend(() => …)` builds the cold value and runs nothing when imported. Running `migrate` later executes its body. Calls retain their Effect value at the top level; operands still follow D147's parameter positions. The annotation must be on the const declaration, rather than inferred or asserted on its initializer. Without it, the same top-level Effect call still reports EK1001 (D103); mutable bindings and non-Effect annotations do not opt in.

**D263. Plain contracts keep JavaScript throws and calls** (effectscript-4a ruling; completes and amends D260). A function with an explicit non-Effect return annotation, or a plain contract inferred by the checker, is plain JavaScript. Every `throw` in that function, inside or outside `try`, is JavaScript's throw: it does not run an Effect, infer an error channel, or cause EK2003. Its declaration keeps its plain return type, and its emitted function returns a value or throws, never an Effect object. Calls whose types return non-Effect values, including plain-function parameters and trusted or untrusted TypeScript imports, are JavaScript calls there: no EK4401 and no Effect inference. Exceptions propagate unchanged and become defects only where they escape into an effectful caller. Running an Effect under a plain contract remains EK2003. Smithers twin findings A-1, B-4, and E-1 pin synchronous validation and callback APIs.

**D264. Shared web-standard globals keep their names** (effectscript-4a, Smithers twin ruling; amends D146). Web-standard globals defined by every runtime VibeLang targets win over effect-root names, just as JavaScript's built-ins do: `Request`, `Response`, `Headers`, `URL`, `URLSearchParams`, `TextEncoder`, `TextDecoder`, `AbortController`, `AbortSignal`, `Blob`, `FormData`, `structuredClone`, and `fetch`. Of effect@4.0.5's root names, only `Request` collides today: `new Request("https://x.test")` constructs the web Request, and Effect's module requires `import { Request } from "effect"`. DOM-only globals such as `Option` still lose to Effect's modules. Explicit imports and local declarations keep precedence.

**D265. Contextually Effect-typed object fields hold programs** (effectscript-4a, Smithers twin findings A-6, B-6, C-6, D-6; implements D147, no new rule). D147 already names the fields of a record among the places where an expected `Effect` takes a program by name (spec 213), as D262 is D147's top-level case. The compiler now applies it to every object-literal field whose contextual type is an Effect: a service implementation's member, a parameter's record field, or a field of a declared type. `Layer.sync(Journal, () => ({ read: Effect.sync(() => …) }))`, `make({ read: work() })`, and `const journal: { read: Effect.Effect<number, never, never> } = { read: work() }` build values and run none of the stored programs. Running the field later executes the program, on every invocation. A field whose contextual type is not an Effect keeps the ordinary rule: a program call runs where it stands. Operands retain their ordinary program positions, as in D262.

**D266. EK diagnostics belong to VibeLang files** (effectscript-4a ruling, `d-gumuam`, Smithers twins W46 C-3; supersedes D242). A `.ts`, `.tsx`, `.mts`, or `.cts` file keeps TypeScript's verdict: no VibeLang-specific EK diagnostic attaches there, regardless of project diagnostic options or inline directives. The shared EK diagnostic constructor enforces the source-file boundary for every registered code. This removes EK4801, EK4819, and EK4820 from ordinary TypeScript; other EK rules already enter through VibeLang-only checks, including EK4813's replacement of TS2339. Ordinary TS errors remain. Editor hints may be offered separately. The Ownership.ts terminal `yield* logWarning.pipe(annotateLogs, andThen(onLapse), andThen(Effect.interrupt))` is valid TypeScript; the identical generator in `.vibe` still receives EK1002 because `function*` there declares a producer.

**D267. A tagged template runs like a call of its tag** (effectscript-4a ruling, `d-gumuam`; Smithers twins B-1; extends D24 and D147). A tagged-template expression whose return type is Effect itself runs where a call would run, in a statement or an expression, and evaluates to its success value. Its failures and requirements join the enclosing program's channels. A program position passes it by name under D147; hatches keep TypeScript, and positions that cannot run follow the call diagnostics, including EK1001 at module top level and EK4301 in a synchronous callback. Plain tags and D24 data results keep their JavaScript meaning. A discarded structured Effect result (such as SQL Statement) reports EK4301 and asks for an explicit call of the result or an Effect return annotation; an Effectful template in an unlowerable position also reports EK4301. The projector also runs an explicit `Effect.service(Key)` lookup: Effect returns the key itself at run time, which this call runs rather than keeping it as D24 data. Both compiler renderings preserve native tag invocation, its receiver, template object, and substitution order. Never emit an Effect-valued template cold in a position where a call would run. Evidence: `tagged-template-runs`, including the fake SqlClient migration shape that left Smithers' tables uncreated.

**D268. Purity crosses files with the function** (effectscript-4a ruling, `d-6zir73`, 2026-10-18). A provably pure export carries a runtime marker, `f[$direct] = f$direct`, in both the native compiler and (B), including local named exports and aliases. Re-exports and import-then-export preserve the same function object. The checking projection merges a phantom namespace containing `$plain: $Plain<typeof f>` into the exported function; its plain call signature survives aliases and barrels. Parity strips only this generated namespace, retaining the public Effect signature. In plain callback positions an importer passes `$adapt(f)`: its branded overload selects the brand's plain signature, and its unbranded overload is `<F>(f: F) => F`, preserving generics without a conditional inference boundary. Known unbranded Effect imports stay in their original contextual positions. At runtime it is `f[$direct] ?? f`; correctness never depends on types. Without a marker the function remains an Effect function. Evidence cases: `plain-export-lists` maps to `[2, 4]`, `plain-imports` maps to `[3, 6]`, and an impure import running `Effect.log` retains its Effect behavior.

**D269. A function declared to return an Effect may return a program; a typed `const` holds one at any scope** (effectscript-4a ruling, CEO a-jxd7kk; Smithers twin findings A-4, C-4, S8-1; extends D7, D262, and D265; D24 and D147 unchanged). In a function whose declared return type is `Effect<A, E, R>` (its annotation, its binding's annotation, or for a lambda the declared member or parameter type it is checked against, D44), a `return` whose expression is a program that TypeScript would reject as an `A` returns that program unrun. A program is a function literal with no parameters, converted as D7 converts it, or a non-call expression whose type is `Effect` itself (D24). Such a function is a factory: its body runs when it is called, as plain JavaScript under D263, and running its result runs the program, every time. Every path of a factory returns a program (EK2116); its body runs no Effect and looks up no service (EK2115); it has no plain variant, so D9 rejects it where a plain function is expected (EK4301). A `const` whose declared type is `Effect` holds its initializer in any scope, as D262 holds it at the top level and D265 in a declared field: `const built: Made = make(config)` calls `make` now and runs nothing. VibeLang callers do not change: a call to a factory runs it (D24), is passed by name where a program is expected (D147), and is held where a declared Effect type holds it. Only TypeScript callers and held programs see the two phases, and the phases are TypeScript's. Code that compiles today keeps its meaning: each new form is TS2322 today, and where `A` is a type parameter that the call infers, as in `Effect.suspend(() => () => 1)`, the returned function stays the value. Rejected: inferring the phases from a plain prefix (it silently moves work in existing exports to call time and recursion onto the JavaScript stack), a `hold(…)` marker (the quotation operator Chapter 5 rules out), and a recipe alone (it unblocks 1 of 29 files). Evidence: `smithers-lanes/a4-probes-opus/`.

**D270. A union consisting entirely of Effects runs where it stands** (effectscript-4a ruling, Smithers twin finding S14-1; clarifies D24 and D147). A call whose type is a union in which every member is Effect<A, E, R> itself counts as an Effect for D24 and D147. It runs where it stands; its success is the union of the members' successes, its error channel the union of their errors, its requirements the union of theirs. A union that mixes an Effect with a non-Effect, or with a structured Effect subtype, is not an Effect and stays data. The checker's call types, the execution plan, and the lowering share the same predicate. Evidence: `union-effect-calls` and `union-effect-channels.fail`.

**D271. An explicit JavaScript iterator contract keeps a JavaScript generator** (effectscript-4a, Smithers twin finding S13-2; extends D263 to generators and amends D26). A generator function (`function*`, `async function*`) whose explicit return annotation is a JavaScript iterator type (`Generator`, `Iterator`, `IterableIterator`, `Iterable`, `AsyncGenerator`, `AsyncIterator`, `AsyncIterableIterator`, `AsyncIterable`) is plain JavaScript: it compiles to the same generator TypeScript would, and its `yield` is JavaScript's. A generator function with no annotation, or one annotated as a `Stream`, keeps VibeLang's stream-producer form. JavaScript iterator contracts preserve `.next()`, spread, `yield*` delegation and its return value, throws and catches, and async iteration with `for await`. EK1002 still rejects an unannotated producer passed to a JavaScript generator API; an explicitly iterator-annotated generator may be passed to that API. Evidence: Smithers mcp McpClient cooperative coroutines silently returned Streams despite their `Generator` types, so `.next()` died at runtime; cases `plain-generator`, `plain-async-generator`, `generator-stream`, and `plain-generator-yield.fail` pin the ruling and TypeScript's invalid-yield diagnostic.

**D272. A curried topic-only pipe stage keeps method-pipe inference** (effectscript-4a ruling, Smithers twin lane S15-1, will-direct-session `b-8839ue`; extends D154). A stage `g(%)` whose callee `g` is itself a call expression, as in `x |> f(args)(%)`, types and lowers exactly as `x.pipe(f(args))`. The stage receives the method pipe's contextual type, preserving data-last Schema combinators whose outer call infers the input schema from that context. The parser normalizes this form before checking and lowering; both compiler renderings emit the method call. Other topic forms retain D154/D155, including extra arguments, member reads on the topic, and additional topic references inside the stage factory. The left side must call nothing (no call, tagged template, or `new` outside nested functions), and every earlier stage of the chain must be such a stage: a call there may run a program (D24), and `.pipe` would then reach its result instead of the program, so `load() |> Effect.map(f)(%)` keeps D154 and passes `load()` by name (Smithers twin agent/model, 0.0.2). Bind a schema built by a call first: `const s = Schema.NullOr(Schema.String)`, then `s |> f(args)(%)`.

**D273. Block-param calls accept ordinary postfix operations** (effectscript-4a ruling, Smithers twin lane S15-2, will-direct-session `b-8839ue`; clarifies D188). A block-param call is a primary expression like any call: member access, element access, and another call may follow its closing brace. Thus `Layer.unwrap { return Layer.empty }.pipe(Layer.fresh)` parses like the corresponding parenthesized program argument. Parsing resumes the ordinary call/member loop after the block; D188's existing argument placement and block boundaries stay in force. Invalid members, indices, and calls on the result keep TypeScript's diagnostics.

**D274. A single-result Effect body returns its Effect without a generator** (effectscript-4a, Smithers twin findings S5-20 and A-12, will-direct-session `b-r4z1vt`; amends D36 and D104). When an Effect function's lowered body is empty or one return, and every call in it that runs is in a result position (through conditionals, commas, and parentheses), the function returns that Effect: `Effect.suspend(thunk)` when a result runs a program, `Effect.sync(thunk)` when every result is a value, or `Effect.void` for an empty body. A value result beside a program result becomes `Effect.succeed(value)`, as for by-name results (D147). The body still runs each time the Effect runs, a throw in it is still a defect, and nothing in the thunk can capture or park, so the frame invariant holds. The thunk is an arrow, so `this`, `arguments`, and `super` are the function's, and it is the property of an object literal named after the source, so a stack frame reads `PrimitiveImpl.<name>` at the `.vibe` line (Effect calls the thunk as a method). Functions with a default or destructured parameter, async and generator functions, traced functions, and handler clauses keep the generator. Evidence: `Effect.fnUntraced` costs every call two run-loop operations more than the TypeScript a twin replaces (suspend, iterator, final success), and Effect yields every 2048 operations, so in the agent/harness twin the supervisor fiber ran inside CellTurn's last frame and judged it (4 failures, A-12's extra evaluator request). With D274 the twin fails exactly the tests TypeScript fails at budgets 1024 (11), 1792 (4), and 2048 (none). Cases `debug-stack` (the thunk's frame), `vibelang-lower`, `vibelang-infer`, and `vibelang-concise-comments` pin the emitted forms.

**D275. VibeLang settings may sit at the tsconfig's top level** (default, Smithers migration lane, 2026-10-20; amends D34). A `vibelang` object at the top level of `tsconfig.json` holds the same settings as `compilerOptions.vibelang`, with the same validation, and a config that `extends` another inherits them as it inherits compiler options. TypeScript 5.x, typescript-eslint, and editors' TypeScript servers reject `compilerOptions.vibelang` as an unknown compiler option (TS5023), so a VibeLang project's tsconfig broke every stock tool that reads it; they ignore an unknown top-level key. The docs show the top-level form; `compilerOptions.vibelang` stays accepted for existing projects. Evidence: `@smthrs/fs`'s ESLint target failed with TS5023 until its settings moved to the top level.

**D276. dprint formats .vibe files through a process plugin that writes them as TypeScript** (Smithers migration lane, formatting half, 2026-10-20; Will: "get formatting and linting working. Ideally we can use our existing formatters and linters"). The `vibelang` package ships a dprint process plugin, `npm:vibelang/dprint-plugin.json`, which is the native compiler started with `--parent-pid`. For each `.vibe` file it parses the file, writes each VibeLang form as TypeScript of the same shape, asks dprint to format that with the configuration's own TypeScript plugin and `typescript` settings (a host format request), and writes the result back: `A!E!R`, `mutable x`, patterns, and headers such as `provide X` become identifiers of the same width; a block param `f(args) { }` becomes `f(args)(($v) => { })`, which dprint lays out as Effect's `Effect.fn(name)(body)`; `match` becomes an object literal whose properties are the arms, so `catch (e) => match (e) {` stays on one line; `x catch y` becomes `x.$v(y)`, so a line break before `catch` stays; `|>` becomes `||`; `fork`, `join`, `throw`, and await operations become `void`; `is` becomes `in`; `provide` and mask blocks become labeled blocks; `error` and `schema` become type aliases and `service` and `control` classes; extra try clauses become labeled blocks glued back after formatting. The parser records each form's tokens for this (`parser.ParseVibeLangSyntax`), since the tree holds only the TypeScript a form abbreviates. A file whose result would not parse to the same tree, parentheses and import order aside, fails instead of changing; so does a file with a syntax error or a comment inside a form's own tokens. The superseded `layer` declaration and the retired `select` stay as written. Rejected: a wasm plugin (dprint's wasm ABI and the size of the Go compiler), dprint-plugin-exec with a nested dprint run per file (a second configuration and a process per file), the language server's formatter (TypeScript's formatter, not dprint's style), and a new formatter (it would not follow the repository's dprint settings). Not controversial.

**D277. ESLint lints `.vibe` files through the compiler's ESTree** (default, Smithers lint lane, 2026-10-20; amends D35). `vibelang/eslint`, an ESLint parser in the `vibelang` package, runs `vibelang --estree`, which converts the VibeLang parser's tree to ESTree (`internal/vibelangestree`). TypeScript forms convert as `@typescript-eslint/typescript-estree` 8 converts them, so typescript-eslint's rules and the plugins that read TypeScript apply unchanged; the test holds the two to the same output node for node on every `.ts` file in this repository, and a run over Smithers' 8,524 `.ts` files found one difference, now fixed. The forms whose TypeScript long form would mislead a rule take node types of their own: `VibeEffectType` for `A!E!R`, `VibeInferType` for D57's `infer` outside a conditional type, `VibePipeExpression` and `TopicReference` for `\|>` and `%`, `VibeCatchExpression`, `VibeProvideStatement` and `VibeServiceProvider`, and `VibeMaskStatement`. A pipe is not a `BinaryExpression`, as Babel has it, because a pipe statement runs its body and `no-unused-expressions` would report it. Every other form keeps the TypeScript the checker reads, so a block param starts its own code path and an `error` is a class. Names the parser writes for the checker are marked `synthesized` and kept out of scope analysis; a typed catch clause's `$caught`, a handle clause's `$performed` chain, a match statement's label, and a schema's interface are left out. Ranges are UTF-16 offsets into the `.vibe` text, and the tokens and comments are one scan of the source, so reports, fixes, and `eslint-disable` comments land on what the author wrote. Rules that need type information do not run on `.vibe` files, as D35 has it: no TypeScript program loads one. Rejected: linting the TypeScript 7 projection (`packages/ts-mapper`), whose lowering (`$gen`, `$run`, `$use`) changes the shapes rules match and has no source position for most of what it writes; rebuilding TypeScript 5 nodes for typescript-estree's own converter, which walks token children that synthesized nodes do not have; and switching Smithers to Oxlint, whose built-in TypeScript parser rejects VibeLang syntax and which accepts no custom parser (D35 assumed VibeLang added no syntax). ESLint's custom parser interface is the one vue-eslint-parser and svelte-eslint-parser use. Evidence: `@smthrs/fs`'s lint target checks its `.vibe` sources with the repository's rules and fails on a seeded violation; `packages/compiler/test/eslint`.

**D278. Declarations that stand for classes are classes** (Will, 2026-10-21; amends D126 and D128). `error`, `service` and `control` declare named TypeScript classes. The keyword supplies only the base class and what VibeLang derives from the name; everything else a class declaration accepts keeps its TypeScript meaning, and the transform lowers the declaration to that class. For `error` this includes `abstract`, `extends` another error, `implements`, constructors with `super`, methods, accessors, `override`, static members and private members, so `SmithersError` with its validating constructor and `toJSON` is an `error` declaration. Two rules are VibeLang's own. Every `error` class, a subclass included, is tagged with its own name: `catchTag("IntegrationError")` matches the subclass, and `is SmithersError` and `match` match the whole family through `instanceof`. A tag is the bare class name, never qualified by package and module as a service key is (D93), because `catchTag("NotFound")` is how Effect code names a failure; two packages that declare `error NotFound` share the tag and are told apart by class. Behaviour that is not idiomatic Effect is dropped rather than given syntax: a base error renamed at construction (`new SmithersError(…, { name: "AdapterError" })`) becomes a subclass. Services and controls keep D128's EK2103 for a member with a body, because an Effect service implementation is a plain object that would not inherit it. Will: "These things like error SmithersError are named typescript classes and all class related semantics should work and then a transform transforms it into typescript so being able to extend an error was already a decision we implicitly made and it's true for other class based keynames we made too", and "if we lose behavior it's only a problem if that behavior is normal idiomatic effect if it's not idiomatic effect it's good". Evidence: today's parser rejects `extends`, `implements`, constructors, methods and static members in an `error` (TS1128, TS1005, TS1434), which kept `@smthrs/errors`' `SmithersError` a 219-line `Data.Error` class.

**D279. `schema error` declares an error that serializes** (Will, 2026-10-21; extends D126, D133 and D278). `schema error FsError { code: Code; method: string; description: string; path?: string }` is short for `class FsError extends Schema.TaggedError<FsError>()("FsError", { code: Code, method: Schema.String, description: Schema.String, path: Schema.optional(Schema.String) })`. Fields map to schemas as a `schema` declaration's do (D133), and D278's class rules apply: `extends`, constructors, methods, and a tag of its own per class. A field whose type has no schema, such as a function, is a compile error that names the field. The tag is the bare class name (D278). Where code has already persisted an error under a qualified tag such as `"flows/fs/FsError"`, the package that reads those records keeps them readable by also accepting the old tag when decoding; that is data compatibility in the package, not syntax. Evidence: Smithers declares `Schema.TaggedError` in 327 files and `Data.TaggedError` in 147, and 228 of the Schema tags are qualified, so without this form most of its errors would stay Effect's TypeScript class form in `.vibe`. Will approved the proposal as written.

**D280. `schema Name = <type>` declares a schema of any mapped type** (Will, 2026-10-21; extends D133). The alias form writes the schema of a type with D133's mapping, unchanged: `schema Code = "root_missing" | "read_failed"` is short for `const Code = Schema.Literals(["root_missing", "read_failed"])` and `type Code = typeof Code.Type`, and the same holds for a union of other forms (`Schema.Union`), arrays, tuples, `Record<K, V>`, object types and named schemas. One name is both the schema and its type, as with the struct form. Refinements and transformations stay `Schema` constants, as D133 has it, and a type outside the mapping is EK2109. Evidence: Smithers writes `Schema.Literal` or `Schema.Literals` 1,666 times, most beside a hand-written type of the same union. Will approved the proposal as written.

**D281. `service Name: Type` declares a service of any shape** (Will, 2026-10-21; extends D128, D223 and D278). `service Search: SearchApi` is short for `class Search extends Context.Service<Search, SearchApi>()(key) {}`, with the key derived as for every service (D93). `Type` is any type: an interface declared elsewhere, a primitive (`service Prefix: string`), a function type. The body is optional and holds only static members, such as a layer; an instance member there is EK2103, as D278 keeps for services. Reading is unchanged: `Prefix()` returns the implementation (D90) and `Search.find(q)` calls a member (D41, D90). Evidence: Smithers declares 103 services as `Context.Service<X, Service>` with the interface beside them, 8 with a plain `string` shape, and about 60 with other named shapes; the fs rewrite had to wrap a string service in an object member, which changed every caller. Will approved the proposal as written.

**D282. `throw` always fails; plain functions never fail and need nothing** (Will, 2026-10-21; supersedes D263, amends D260 and D67). In a `.vibe` file, `throw` is a typed failure everywhere outside a hatch, and `try`/`catch` keep VibeLang's meaning. Only a hatch (`sync`, `try`, `callback`), whose function is plain TypeScript, has JavaScript's `throw` and `catch`. A function with a plain return annotation (D67) is plain JavaScript because it never fails and never needs a service: a `throw` in it is a compile error, as running an Effect in it already is (EK2003), and the fix is an Effect contract (`A!E`) or a hatch. Exceptions thrown by TypeScript code it calls still propagate unchanged and become defects where they reach an effectful caller. To catch such an exception, use the `try` hatch. Will: "throw is not javascript throw I'm telling you you aren't allowed to do that. If vibelang allows that that's a bug. It would be extremely bad if throw meant completely different thing contextually. Only way for throw to be a javascript throw is for it to be in something like a try where we escaped to normal typescript", and "plain javascript functions must never error and never take a dep". The point: "this makes it so if you think of it as an effect you won't misunderstand how program works". Reading any `.vibe` code as Effect code is never wrong.
