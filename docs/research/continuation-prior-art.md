# Continuation prior art for EffectScript

Research notes, 2026-10-15. Scope: one-shot delimited continuations, effect handlers, and coroutine runtimes, read for a language whose core is a one-shot delimited continuation runtime on Effect 4 (`effect@4.0.5`: fibers, `Context` services, `Scope` resources, interruption).

Conventions:

- Text inside quotation marks is copied verbatim from the cited source. Text labeled "paraphrase" is not.
- UNCONFIRMED marks a claim we could not verify against a primary source.
- Dimensions: (a) one-shot enforcement and second resume; (b) abandonment of an unresumed continuation; (c) cancellation-versus-resumption races; (d) dynamic state across capture and resume; (e) deep or shallow, lexical or dynamic binding; (f) what crosses thread or fiber boundaries; (g) representation and capture cost; (h) compilation to JavaScript; (i) tail-resumptive optimization.

## Summary

Every production one-shot runtime checks "at most once" at run time and leaves "at least once" to a scope or to the programmer: OCaml raises `Continuation_already_resumed`, Kotlin throws `IllegalStateException("Already resumed")`, Swift's checked continuation traps (and Swift 6.4 makes double resume a compile error), Loom throws `"Continuation terminated"`, and WasmFX traps, while Effection 4 and Effect 4's own `Effect.callback` silently drop later resumes. No system finalizes an abandoned continuation from the garbage collector. OCaml, Kotlin, Swift, Loom, Effekt, and WasmFX leak it or collect it silently, OCaml's attempt to discontinue from the GC stalled over finalizers running at arbitrary points, and only designs that tie the continuation to a handler or scope unwind it deterministically (Koka re-enters a non-resumed `ctl` continuation with a final yield; Effection calls `return()` when the scope dies; OCaml and WasmFX need an explicit `discontinue` or `resume_throw`). Cancellation races are settled by one take-once cell that resume and cancel both contend for (Kotlin, Eio, Loom, Swift's `Task.sleep`); only Kotlin hands a value that lost the race to a release callback. For dynamic state, the Delimited Dynamic Binding rule holds up: bindings inside the delimiter travel with the continuation, bindings outside come from the resumer, and the handler sees only the outside; Koka's evidence vectors, WasmFX handler lookup, and Racket's continuation marks all follow it. Tail-resumptive operations decide performance: Koka runs them in place under the handler's evidence for 10× on its counter benchmark and Effekt rewrites them statically, while OCaml, js_of_ocaml, and WasmFX have no fast path. On JavaScript, selective transformation wins (Koka cut CPS-translated functions by over 80%; Stopify measured generators about 2× slower than its exception-based capture), and every system refuses to capture through foreign frames. The host adds three constraints we verified in `effect@4.0.5`: `Effect.gen` drops the generator without calling `return()`, so JavaScript `finally` blocks in generated code do not run on failure or interruption; a late `resume` runs the woken fiber inline on the resumer's stack; and `provide` restores an absolute previous `Context`, so a captured stack slice cannot be spliced under a new provider without rebasing.

## 1. OCaml 5 effect handlers

Pinned: OCaml 5.5.1 (2026-09-04), [manual 5.5](https://ocaml.org/manual/5.5/effects.html), Eio v1.6, domainslib 0.5.2. Paper: Sivaramakrishnan, Dolan, White, Kelly, Jaffer, Madhavapeddy, "Retrofitting Effect Handlers onto OCaml", PLDI 2021 ([arXiv PDF](https://arxiv.org/pdf/2104.00250), [DOI](https://doi.org/10.1145/3453483.3454039)).

- **(a) One-shot.** At most once is checked at run time; at least once is not. `continue` and `discontinue` first null the continuation's stack field (a compare-and-swap when several domains run), so a second use raises in the resumer before any stack switch.
  - "every captured continuation must be resumed either with a continue or discontinue exactly once. Attempting to use a continuation more than once raises a Continuation_already_resumed exception." ([manual](https://ocaml.org/manual/5.5/effects.html))
  - "While the “at most once resumption” property of continuations is ensured with a dynamic check, there is no check to ensure that the continuations are resumed “at least once”." (same)
  - Code: [fiber.c#L641-L677](https://github.com/ocaml/ocaml/blob/5.5.1/runtime/fiber.c#L641-L677). The 2021 paper says "resuming the continuation more than once raises an Invalid_argument exception." (§3.1); the shipped exception is `Continuation_already_resumed`.
  - Rationale: "Since our primary use case is concurrency, continuations will be resumed at most once, and copying fibers is unnecessary and inefficient." (paper §5.2). Marshalling a continuation fails ([extern.c#L883-L884](https://github.com/ocaml/ocaml/blob/5.5.1/runtime/extern.c#L883-L884)).
- **(b) Abandonment.** Leak. No `finally` block or handler inside the suspended fiber runs, and the GC never unwinds an unreachable continuation.
  - "Not resuming continuations will leak the memory allocated for the fibers as well as any resources that the suspended computation may hold." ([manual](https://ocaml.org/manual/5.5/effects.html))
  - The remedy is `discontinue k exn`, which raises at the `perform` site so `finally` code runs. A GC finaliser that discontinues is expensive: "Attaching this finaliser to every captured continuation slows down generator (chameneos) benchmark by 4.1× (2.1×) compared to not attaching a finaliser." (paper §6.3.3)
  - Open [PR #14580](https://github.com/ocaml/ocaml/pull/14580) would discontinue unreachable continuations from the GC. Reviewers object: "My main concern is around things like taking a mutex, which can easily deadlock when done from a finalizer." ([comment](https://github.com/ocaml/ocaml/pull/14580#issuecomment-4005157907)); "a first step might be to only free the memory used by unreachable fiber stacks and not discontinue them in the finaliser." ([comment](https://github.com/ocaml/ocaml/pull/14580#issuecomment-4177436176))
  - Diagnostics: only `Gc.stat.live_stacks_words` ([gc.mli#L104-L109](https://github.com/ocaml/ocaml/blob/5.5.1/stdlib/gc.mli#L104-L109)).
- **(c) Cancellation vs resumption.** The core has no cancellation. `discontinue` is itself a resumption and takes the same cell, so racing resumers get one winner and `Continuation_already_resumed` for the rest. Eio adds cancellation with one shared atomic:
  - "Therefore, cancelling and completing both need to update an atomic value (with {!Atomic.compare_and_set}) so that only one can succeed." ([eio__core.mli#L626-L667](https://github.com/ocaml-multicore/eio/blob/v1.6/lib_eio/core/eio__core.mli#L626-L667))
  - If completion wins: "If the taking fiber is cancelled after this, the cancellation must be ignored and the operation will complete successfully." If cancellation wins, the racing value "will be given to the next waiter instead." (same)
- **(d) Dynamic state.** A continuation carries its fiber segments (frames, exception handlers) and, for a deep handler, the handler. Everything outside comes from the resume site, because resume links the continuation's last fiber under the resumer's stack ([amd64.S#L1253-L1262](https://github.com/ocaml/ocaml/blob/5.5.1/runtime/amd64.S#L1253-L1262)).
  - "Whenever a continuation is captured in a deep handler, the captured continuation also includes the handler." ([manual](https://ocaml.org/manual/5.5/effects.html))
  - `Domain.DLS` is per domain and the stdlib has no fiber-local storage. Eio pairs each `k` with a fiber context holding its cancellation context and an `Hmap` of fiber-local variables ([suspended.ml#L6-L9](https://github.com/ocaml-multicore/eio/blob/v1.6/lib_eio/utils/suspended.ml#L6-L9), [cancel.ml#L24-L30](https://github.com/ocaml-multicore/eio/blob/v1.6/lib_eio/core/cancel.ml#L24-L30)).
- **(e) Deep or shallow; binding.** Both. `Effect.Deep` has syntax since 5.3 (`match e with effect P, k -> ...`); `Effect.Shallow` has none. Binding is dynamic: innermost handler first; unmatched effects re-perform outward.
  - "The continuation captured in a shallow handler does not include the handler." and "If effects do not have a matching handler, then an Effect.Unhandled exception is raised at the point of the corresponding perform." ([manual](https://ocaml.org/manual/5.5/effects.html))
- **(f) Boundaries.** Continuations are heap values. The runtime's CAS supports resuming on another domain, and domainslib does so ([task.ml#L36-L38](https://github.com/ocaml-multicore/domainslib/blob/0.5.2/lib/task.ml#L36-L38)); the manual states no policy (UNCONFIRMED as a supported rule). C frames are never captured:
  - "It is not possible for an effect to cross a call to caml_callback, this would instead result in an Effect.Unhandled exception." ([manual](https://ocaml.org/manual/5.5/effects.html))
- **(g) Representation and cost.** Heap-allocated, growable fiber stacks: 64 words initially in 5.5.1 (the paper says 16), doubled with a copy on overflow, recycled per domain ([fiber.c#L475-L510](https://github.com/ocaml/ocaml/blob/5.5.1/runtime/fiber.c#L475-L510)).
  - "Capturing a continuation does not involve copying stack frames." ([manual](https://ocaml.org/manual/5.5/effects.html))
  - Paper timings on Multicore OCaml 4.10: allocate a fiber and switch 23 ns, perform and handle 5 ns, resume 11 ns, return and free 7 ns (§6.3). Handler search is "linear in the number of handlers" (§5.4). Code that uses no effects pays "a mean 1% overhead" (abstract).
- **(h) JavaScript.** N/A upstream; see section 9. The native design rejected CPS: "Hence, we choose not to use CPS translation and represent the continuations as call stacks." (paper §1)
- **(i) Tail-resumptive.** No fast path: every `perform` allocates a continuation and switches stacks ([cmmgen.ml#L891-L897](https://github.com/ocaml/ocaml/blob/5.5.1/asmcomp/cmmgen.ml#L891-L897)). A `continue` in tail position is a tail call: "We perform tail-call optimisation so that resumptions at tail positions do not build up stack." (paper §5.4)
- **Design note.** "dynamic-wind is not quite the right abstraction as resources need to be cleaned up only on non-returning exits" (paper §7).
- **UNCONFIRMED.** Cross-domain resumption as a documented guarantee; OCaml 5.5 per-operation timings (only 2021 figures exist); whether PR #14580 lands.

## 2. Kotlin coroutines

Pinned: [KEEP-0164](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md) at `e06f0b9`, Kotlin 2.4.21, kotlinx.coroutines 1.11.0.

- **(a) One-shot.** Library wrappers enforce it. `suspendCoroutine` wraps the continuation in `SafeContinuation`, a CAS cell; raw intrinsics are unchecked.
  - "Resuming the same continuation more than once is not allowed and produces `IllegalStateException`." ([KEEP L493](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L493))
  - `else -> throw IllegalStateException("Already resumed")` ([SafeContinuationJvm.kt#L35-L47](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/jvm/src/kotlin/coroutines/SafeContinuationJvm.kt#L35-L47); [JS](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/stdlib/js/src/kotlin/coroutines/SafeContinuationJs.kt#L26-L38)). kotlinx: `error("Already resumed, but proposed with update $proposedUpdate")` ([CancellableContinuationImpl.kt#L555-L557](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuationImpl.kt#L555-L557)).
  - "The choice to support only resume-once continuations is purely pragmatic as none of the intended use cases need multi-shot continuations." ([KEEP L495-L500](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L495-L500))
- **(b) Abandonment.** The GC collects a dropped continuation; no `finally` runs and nothing reports it.
  - "If you lose the reference to suspended coroutine's continuation, then it will be ultimately collected by garbage collector." ([KEEP L1176-L1182](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L1176-L1182)); "It is explicitly out of the scope of Kotlin coroutines to introduce a language mechanism for an automated resource management." ([L1230-L1238](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L1230-L1238))
  - kotlinx replaces abandonment with cancellation: `suspendCancellableCoroutine` "throws a [CancellationException] if the [Job] of the coroutine is cancelled or completed while it is suspended" ([CancellableContinuation.kt#L323-L326](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L323-L326)), so `finally` runs. A parent "waits in the _completing_ state for all its children to complete" ([Job.kt#L67-L70](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/Job.kt#L67-L70)).
- **(c) Cancellation vs resumption.** Cancel and resume race through one CAS; exactly one succeeds. A resume that loses is ignored, and its value can be released.
  - "allows concurrent invocations of the [cancel] and [resume] pair, guaranteeing that only one of these operations will succeed." ([CancellableContinuation.kt#L43-L49](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L43-L49))
  - Prompt cancellation guarantee: "If the [Job] of the coroutine that obtained a cancellable continuation was cancelled while this continuation was suspended it will not resume successfully, even if [CancellableContinuation.resume] was already invoked but not yet executed." ([#L51-L68](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L51-L68))
  - "If continuation was cancelled, then resume attempt must be ignored, because cancellation is asynchronous and may race with resume. Racy exceptions will be lost, too." ([Impl#L493-L523](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuationImpl.kt#L493-L523))
  - Resource handoff: `resume(value) { cause, value, context -> ... }` calls the lambda "if and only if the [value] was not successfully used to resume the continuation." ([#L258-L311](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L258-L311)); stable since 1.9.0 ([CHANGES.md](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/CHANGES.md?plain=1#L108-L134)). It took three releases (1.2.0, 1.4.0-M1, 1.9.0) to reach this shape.
  - "At most one [handler] can be installed on a continuation. Attempting to call `invokeOnCancellation` a second time produces an [IllegalStateException]." ([#L210-L234](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L210-L234))
  - `suspendCoroutine` is not cancellable: "In contrast, custom suspending functions that use suspendCoroutine() don't react to cancellation." ([docs](https://kotlinlang.org/docs/coroutines-cancellation.html#suspension-points-and-cancellation))
- **(d) Dynamic state.** The context is immutable and belongs to the continuation, so a resumed coroutine runs with its own context on whatever thread resumes it. Thread-locals are re-installed around each resumption.
  - "The difference is that thread-local variables are mutable, while coroutine context is immutable" ([KEEP L557-L563](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L557-L563))
  - `ThreadContextElement` is "installed into the thread context every time the coroutine with this element in the context is resumed on a thread." ([ThreadContextElement.kt#L6-L8](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/jvm/src/ThreadContextElement.kt#L6-L8))
- **(e) Handlers.** N/A: no effect handlers. The delimiter is the coroutine; `@RestrictsSuspension` restricts suspension lexically through the receiver type ([KEEP L841-L847](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L841-L847)).
- **(f) Boundaries.** Frames, context, and a `Result` cross threads; thread-locals do not.
  - "a suspended coroutine does not consume a thread and it is not bound to a thread in any way." ([KEEP L1264-L1268](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L1264-L1268))
- **(g) Representation and cost.** CPS: each suspend function takes a hidden `Continuation` and returns `T` or `COROUTINE_SUSPENDED`. One frame object per call holds `label`, spilled locals, and `completion`; suspension copies nothing.
  - "An instance of the state machine object in created when suspending function is invoked and is discarded when it completes." (sic) ([KEEP L1037-L1046](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L1037-L1046)); `suspendCoroutine` "wraps the actual continuation of the state machine into an additional object on each suspension of coroutine." ([L1063-L1070](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L1063-L1070))
- **(h) JavaScript.** Default: state machines (`CoroutineImpl.doResume`). Since Kotlin 2.0.0: "This release introduces Experimental support for ES2015 generators for compiling suspend functions." ([what's new](https://kotlinlang.org/docs/whatsnew20.html#suspend-functions-as-es2015-generators)); every suspension point becomes `yield*` ([lowering](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/ir/backend.js/src/org/jetbrains/kotlin/ir/backend/js/lower/coroutines/JsSuspendFunctionWithGeneratorsLowering.kt#L46-L113)).
- **(i) Tail-resumptive analogue.** A call that does not suspend "returns its result or throws an exception directly." ([KEEP L885-L892](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L885-L892)). "we do not generate a continuation class and a state machine for suspending functions, which have all their suspend calls in tail position." ([codegen notes](https://github.com/JetBrains/kotlin/blob/v2.4.21/compiler/backend/src/org/jetbrains/kotlin/codegen/coroutines/coroutines-codegen.md?plain=1#L1601-L1647)). Direct invocation is forbidden: "The actual implementation of the suspending function is not allowed to invoke the continuation in its stack frame directly because that may lead to stack overflow on long-running coroutines." ([KEEP L894-L898](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L894-L898))
- **UNCONFIRMED.** Any diagnostic for a garbage-collected unresumed continuation (none found); stability of Kotlin/JS generator mode beyond Experimental; late-value delivery under `suspendCoroutine` (derived from `MODE_ATOMIC` in source, not documented).

## 3. Swift concurrency continuations

Pinned: swift-evolution `f006bf3`, swift `swift-6.4.0-RELEASE`. Swift 6.4 added a noncopyable `Continuation` ([SE-0528](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0528-noncopyable-continuation.md)) and cancellation shields (SE-0504).

- **(a) One-shot.** Four tiers.
  - `UnsafeContinuation`: "it is undefined behavior if a `resume` method is invoked on the same continuation more than once." ([SE-0300 L127-L128](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L127-L128))
  - `CheckedContinuation`: an atomic exchange with null, then a trap: `fatalError("SWIFT TASK CONTINUATION MISUSE: \(canary.function) tried to resume its continuation more than once, returning \(value)!\n")` ([CheckedContinuation.swift#L164-L174](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/CheckedContinuation.swift#L164-L174)).
  - `SWIFT_DEBUG_VALIDATE_UNCHECKED_CONTINUATIONS` makes the runtime abort on a second resume of any continuation ([EnvironmentVariables.def#L50-L51](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/runtime/EnvironmentVariables.def#L50-L51)).
  - Swift 6.4 `Continuation`: "a noncopyable continuation type that makes double-resume a compile-time error and missing-resume a guaranteed runtime trap, with no allocations and no atomic operations on the fast path." ([SE-0528 L20](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0528-noncopyable-continuation.md?plain=1#L20))
  - Conflict: the `CheckedContinuation` type documentation says it "logs a message if either of these invariants is violated" ([#L107-L111](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/CheckedContinuation.swift#L107-L111)); the method docs, the code, and SE-0300 trap on double resume.
- **(b) Abandonment.** The task hangs and leaks. `CheckedContinuation` only logs, from `deinit`.
  - "if the continuation is discarded and never resumed, then the task will be left suspended until the process ends, leaking any resources it holds." ([SE-0300 L129-L131](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L129-L131))
  - `"SWIFT TASK CONTINUATION MISUSE: \(function) leaked its continuation without resuming it. This may cause tasks waiting on it to remain suspended forever.\n"` ([CheckedContinuation.swift#L76-L87](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/CheckedContinuation.swift#L76-L87))
  - Why log rather than trap: "The precise moment at which such a deinit would execute is not entirely predictable because of refcounting variability from ARC optimization." ([SE-0300 L376-L379](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L376-L379)). The 6.4 `Continuation` traps: `fatalError("Continuation was deinitialized without being resumed.")` ([Continuation.swift#L53-L55](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/Continuation.swift#L53-L55)).
- **(c) Cancellation vs resumption.** Cancellation is a flag plus handlers; it never resumes or invalidates a continuation, and the resume path has no cancellation check, so a value resumed after cancellation is delivered (read from source).
  - "cancellation has no effect at all unless something checks for cancellation." ([SE-0304 L394-L402](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0304-structured-concurrency.md?plain=1#L394-L402))
  - "If the task has already been cancelled at the point `withTaskCancellationHandler` is called, the cancellation handler is invoked immediately, before the `operation` block is executed." ([SE-0304 L886-L889](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0304-structured-concurrency.md?plain=1#L886-L889))
  - "If cancellation occurs while the operation is running, the cancellation handler executes *concurrently* with the operation." and "The cancellation handler may be invoked while holding internal locks associated with the task or other tasks.  Other operations on the task, such as resuming a continuation, may acquire these same internal locks." ([TaskCancellation.swift#L64-L75](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/TaskCancellation.swift#L64-L75))
  - The stdlib's own `Task.sleep` settles the race with a five-state atomic machine and drops a wake that arrives after cancellation ([TaskSleep.swift#L161-L195](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/TaskSleep.swift#L161-L195)).
- **(d) Dynamic state.** A continuation captures only its task; resuming re-enters that task, so its task-local bindings are intact and the resumer's never flow in. After resume, a compiler-inserted hop restores the caller's isolation ([SILGenBuiltin.cpp#L1867-L1887](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/lib/SILGen/SILGenBuiltin.cpp#L1867-L1887)).
  - "Detached tasks do not inherit task-local values, however tasks created using the `Task { ... }` initializer do inherit task-locals by copying them to the new asynchronous task, even though it is an un-structured task." ([TaskLocal.swift#L86-L88](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/TaskLocal.swift#L86-L88))
- **(e) Handlers.** N/A: "a continuation only represents a *single suspension point* in the lifetime of the task." ([SE-0300 L387-L391](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L387-L391))
- **(f) Boundaries.** Both continuation types are `Sendable`: "there are no other restrictions on where the continuation can be resumed." ([SE-0300 L244-L246](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L244-L246)). Resume values are `sending` (SE-0430).
- **(g) Representation and cost.** "Lowering will split an async coroutine into a ramp function and one resume function per suspend point." ([LLVM coroutines](https://llvm.org/docs/Coroutines.html#async-lowering)). Async frames come from a per-task bump allocator: "Because allocation is task-local, and there's at most one thread running a task at once, no synchronization is required." ([TaskAlloc.cpp#L13-L16](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/TaskAlloc.cpp#L13-L16)). `CheckedContinuation` adds a heap canary and a sequentially consistent atomic exchange per resume.
- **(h) JavaScript.** N/A: no JS backend. SwiftWasm's JavaScriptKit bridges promises with `withUnsafeContinuation` ([JavaScriptEventLoop.swift#L189-L205](https://github.com/swiftwasm/JavaScriptKit/blob/0.60.0/Sources/JavaScriptEventLoop/JavaScriptEventLoop.swift#L189-L205)).
- **(i) Fast path.** A resume inside the body continues on the current thread without an enqueue (`// If the status is already Resumed, we can resume immediately.`, [Task.cpp#L1596-L1601](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/Task.cpp#L1596-L1601)). After a real suspension, resume always enqueues. SE-0300 deferred an immediate-resume API (`unsafeResumeImmediately`), warning that its user must ensure "that it is safe to take over control of the current thread from the caller for a potentially unbounded amount of time." ([SE-0300 L446-L455](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L446-L455))
- **UNCONFIRMED.** That a child hung on a leaked continuation blocks its parent's task group forever (inference from SE-0300 plus SE-0304); the exact text of the 6.4 `Continuation` trap when the creation site is reported.

## 4. Java Project Loom

Pinned: OpenJDK `jdk-27-ga`. Design documents: [Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html), [State of Loom](https://cr.openjdk.org/~rpressler/loom/loom/sol1_part1.html).

- **(a) One-shot.** The `Continuation` object is a mutable, non-reentrant handle; each `run()` continues from the latest `yield`, so no suspension point can be resumed twice.
  - "A one-shot delimited continuation." ([Continuation.java#L40-L43](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/jdk/internal/vm/Continuation.java#L40-L43)); `run()` after completion: `throw new IllegalStateException("Continuation terminated")`; a concurrent `run()`: `throw new IllegalStateException("Mounted!!!!")` ([#L217-L242](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/jdk/internal/vm/Continuation.java#L217-L242)).
  - "the continuations discussed here are non-reentrant, meaning that any invocation of the continuation may change the "current" suspension point. In other words, the continuation object is stateful." ([Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html))
  - Virtual threads ignore duplicate scheduling: `if (!compareAndSetState(initialState, RUNNING)) { return; }` ([VirtualThread.java#L265-L304](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/VirtualThread.java#L265-L304)).
  - Multi-shot was deferred: "cloning would need to be "deep" in some customizable way." ([Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html))
- **(b) Abandonment.** No unwind API; suspension runs no `finally`; an unresumed continuation's heap chunks are collected silently.
  - "When a continuation suspends, no try/finally blocks enclosing the yield point are triggered (i.e., code running in a continuation cannot detect that it is in the process of suspending)." ([Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html))
  - Pressler (2020): "In that case, the virtual thread (and associated continuation) will be garbage-collected. From a semantics perspective, it is the same as sleeping forever." ([loom-dev](https://mail.openjdk.org/pipermail/loom-dev/2020-July/001469.html)). Since JDK 21, `jdk.trackAllThreads` defaults to true, so the root container holds every virtual thread strongly: a never-unparked thread leaks but appears in thread dumps ([ThreadContainers.java#L53-L62](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/jdk/internal/vm/ThreadContainers.java#L53-L62), [commit 2e9eff5](https://github.com/openjdk/jdk/commit/2e9eff56418273e85accc43dcef533995c6be8bf)).
- **(c) Cancellation vs resumption.** Cancellation is `Thread.interrupt()`: it sets the virtual thread's flag and calls `unpark()`. Interrupt, unpark, and timeout share one `PARKED|TIMED_PARKED → UNPARKED` CAS and a non-accumulating permit.
  - "permits do not accumulate. There is at most one." ([LockSupport.java#L47-L72](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/locks/LockSupport.java#L47-L72)); a wake that lands mid-suspension is caught after the freeze: `// may have been unparked while parking` ([VirtualThread.java#L559-L588](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/VirtualThread.java#L559-L588)).
  - Structured concurrency ([JEP 533](https://openjdk.org/jeps/533), preview in JDK 27; [JEP 543](https://openjdk.org/jeps/543) proposes final in JDK 28): "If one of the findUser() or fetchOrder() subtasks fails, by throwing an exception, then the other is cancelled, i.e., interrupted, if it has not yet completed." and "The close method always waits for threads executing subtasks to finish, even if the scope is cancelled." A result that arrives after cancellation is dropped (`// nothing to do if scope is cancelled`, [StructuredTaskScopeImpl.java#L336-L361](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/StructuredTaskScopeImpl.java#L336-L361)).
- **(d) Dynamic state.** A raw `Continuation` swaps nothing, which is why it stays internal. Virtual threads swap identity and state at mount.
  - Pressler (2022): "The main issue is that the Continuation class can be used in a way that would cause the current thread (i.e. Thread.currentThread()) to change mid-method." ([loom-dev](https://mail.openjdk.org/pipermail/loom-dev/2022-July/004820.html))
  - "Thread-local variables of the carrier are unavailable to the virtual thread, and vice-versa." ([JEP 444](https://openjdk.org/jeps/444))
  - Scoped values travel with frames and are inherited by structured forks without copying: "Unlike with thread-local variables, there is no copying of a parent thread's scoped value bindings to the child thread." ([JEP 506](https://openjdk.org/jeps/506)); a fork throws `StructureViolationException("Scoped value bindings have changed")` if they changed ([Thread.java#L381-L394](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/Thread.java#L381-L394)).
- **(e) Handlers.** `ContinuationScope` objects are prompts compared by identity and found dynamically (innermost). Each `run()` re-enters through the entry frame, so the delimiter is reinstalled on every resume (deep). There are no operations or handlers.
  - "Code running inside a continuation is not expected to have a reference to the continuation, and the scopes normally have some fixed names (so suspending scope A would suspend the innermost enclosing continuation of scope A)." ([Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html))
- **(f) Boundaries.** "Continuations, therefore, are not thread-safe and none of their operations creates cross-thread happens-before relations." ([Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html)). A virtual thread carries its stack chunks, identity, thread-locals, interrupt flag, scoped values, and (since JDK 24, [JEP 491](https://openjdk.org/jeps/491)) its monitors. Frames that cannot be frozen pin: `protected void onPinned(Pinned reason) { throw new IllegalStateException("Pinned: " + reason); }` ([Continuation.java#L394-L404](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/jdk/internal/vm/Continuation.java#L394-L404)); `VirtualThread` overrides it and parks the carrier instead.
- **(g) Representation and cost.** Frames live in heap `StackChunk` objects. Freeze copies only frames on the thread stack; thaw is lazy behind a return barrier.
  - "we copy only the topmost frame (or some small batch of frames), and install a "return barrier" that, when the bottom-most of the copied frames is popped, copies over another frame from the heap." ([loom-dev 2018](https://mail.openjdk.org/pipermail/loom-dev/2018-March/000037.html))
  - "The amortized budget for each of those two operations is ~100-150ns." ([continuationFreezeThaw.cpp#L90-L108](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/hotspot/share/runtime/continuationFreezeThaw.cpp#L90-L108)); whole-chunk thaw below `threshold = 500; // words` ([#L2298-L2319](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/hotspot/share/runtime/continuationFreezeThaw.cpp#L2298-L2319)).
- **(h) JavaScript.** N/A. The proposal calls generator-style lowering the weaker form: "In contrast, stackless continuations may only suspend in the same subroutine as the entry point." ([Loom Proposal](https://cr.openjdk.org/~rpressler/loom/Loom-Proposal.html))
- **(i) Fast path.** "If already unparked then the parking permit is consumed and this method completes immediately (meaning it doesn't yield)." ([VirtualThread.java#L748-L780](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/VirtualThread.java#L748-L780))
- **Public API.** "I don’t see us releasing continuations before virtual threads, or even making continuations public in the first release of virtual threads." ([Pressler, 2020](https://mail.openjdk.org/pipermail/loom-dev/2020-March/001116.html)); `jdk.internal.vm` is exported only to five JDK modules ([module-info.java#L241-L246](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/module-info.java#L241-L246)).
- **UNCONFIRMED.** Any post-2022 plan to publish a continuation API; collection of an unreachable parked virtual thread with `-Djdk.trackAllThreads=false`; the 500-word threshold and 100–150 ns budget come from code comments, not published measurements.

## 5. WebAssembly stack switching (WasmFX) and JSPI

Pinned: [Explainer](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/Explainer.md) at `c7be390`, Wasmtime v49.0.3, V8 `7474de1`, JSPI spec `5b247b1`. Paper: Phipps-Costin, Rossberg, Guha, Leijen, Hillerström, Sivaramakrishnan, Pretnar, Lindley, "Continuing WebAssembly with Effect Handlers", OOPSLA 2023 ([arXiv PDF](https://arxiv.org/pdf/2308.08347v3)).

Instructions: `cont.new`, `cont.bind`, `resume $ct (on $e $l | on $e switch)*`, `resume_throw`, `resume_throw_ref`, `suspend $e`, `switch` ([Explainer#L503-L670](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/Explainer.md#L503-L670)).

**Status on 2026-10-15.** Stack switching is Phase 3 (voted at the October 2025 CG meeting, [CG-10.md#L1317-L1321](https://github.com/WebAssembly/meetings/blob/882204b422e23e1c289978b7364e535357b7253d/main/2025/CG-10.md#L1317-L1321); [proposals table](https://github.com/WebAssembly/proposals/blob/df6a2aca1cd9d779eb4f2f3e19dae8277f336015/README.md#L16-L67)). A May 2026 design note proposes "replacing the concept of reified continuations with **reified fibers**" ([design note](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/design-notes/reified-fibers/Explainer.md#L3)). Wasmtime: Tier 3, "This feature is `false` by default." ([config.rs#L1251](https://github.com/bytecodealliance/wasmtime/blob/v49.0.3/crates/wasmtime/src/config.rs#L1251)). V8/Chrome: experimental flag, off by default. JSPI is Phase 5 and shipped in Chrome 137, Firefox 153, and Safari 27.0 ([Firefox 153](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/153), [Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/), [WG vote](https://github.com/WebAssembly/meetings/blob/882204b422e23e1c289978b7364e535357b7253d/main/2026/WG-2026-06-24.md#L89-L94)).

- **(a) One-shot.** Consumption is destructive and checked at run time; reuse traps ("continuation already consumed" in the reference interpreter and Wasmtime; "WasmFX: resuming an invalid continuation" in V8).
  - "In order to ensure that continuations are one-shot, `resume`, `resume_throw`, `resume_throw_ref`, `switch`, and `cont.bind` destructively modify the suspended continuation such that any subsequent use of the same suspended continuation will result in a trap." ([Explainer#L696-L700](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/Explainer.md#L696-L700))
  - "we follow the lead of OCaml 5 and dynamically check that continuations are invoked at most once — trapping in the case that an attempt is made to invoke a continuation more than once." (paper §6.1)
- **(b) Abandonment.** No finalization semantics; cleanup inside a continuation runs only if its holder aborts it with `resume_throw`. Engines retain abandoned continuations.
  - "Correct code is expected to consume all continuations linearly, i.e., either resume them or abort them explicitly with resume_throw — both will ultimately terminate the computation and reclaim the stack." (paper §3.1)
  - Wasmtime: "Note that we currently don't support deallocating them. Instead, all continuations remain allocated throughout the store's lifetime." ([store.rs#L2133-L2135](https://github.com/bytecodealliance/wasmtime/blob/v49.0.3/crates/wasmtime/src/runtime/store.rs#L2133-L2135))
- **(c) Cancellation vs resumption.** One thread per agent, so the first of `resume`, `resume_throw`, `switch`, or `cont.bind` consumes the continuation and the rest trap. Abort is cooperative: the injected exception can be caught and the computation can suspend again.
  - `resume_throw` "raises the exception `$exn` with parameters of type `te*` at the control tag invocation point in the context of the supplied continuation." ([Explainer#L593-L595](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/Explainer.md#L593-L595)); "Handling exception x may trigger further suspensions" (paper §3.1).
- **(d) Dynamic state.** The continuation holds frames, locals, `try_table` catch contexts, and inner non-matching handlers between `suspend` and the handling `resume`; it excludes the matching handler. Globals, memories, and tables belong to the instance.
  - "The extent of a suspended continuation captures execution from the instruction immediately following `suspend $e` up to the `resume` instruction that handles `$e`." ([Explainer#L230-L232](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/Explainer.md#L230-L232))
- **(e) Handlers.** The paper calls the design "sheep handlers": "The handlers in WasmFX can be seen as a hybrid of shallow and deep: “sheep handlers”." and "As with shallow handlers this handler can be changed each time we resume." (§6.1). Lookup is dynamic by tag: "execution continues at the *innermost* ancestor whose `resume` instruction installed a suspend handler for `$e`." ([Explainer#L225-L227](https://github.com/WebAssembly/stack-switching/blob/c7be390539e5fc10669c88cadc4fa4b32fba1d47/proposals/stack-switching/Explainer.md#L225-L227)). Tags are generative per instantiation, which gives lexical-style privacy.
- **(f) Boundaries.** Continuation references are unshared; no shared continuation type exists. JS frames are never captured: "It is definitely NOT intended that stack switching in any guise will be permitted to capture JavaScript frames." and "The 'may not capture JS frames' is a hard requirement from TC39." ([issue #49](https://github.com/WebAssembly/stack-switching/issues/49#issuecomment-2087508452)). JSPI throws `SuspendError` when a JS frame sits between `promising` and the suspending import ([JSPI spec#L1497](https://github.com/WebAssembly/js-promise-integration/blob/5b247b1026d2f438eefe51914a79f4218cbda9f9/document/js-api/index.bs#L1497)); its Overview still says "Traps" (conflict).
- **(g) Representation and cost.** Separate stacks, switched rather than copied: "One-shot continuations admit direct and efficient implementations of continuations as stacks in which it is never necessary to copy the stack." (paper §6.1). Wasmtime uses a two-word fat pointer (object, revision) checked on every use ([fatpointer.rs#L7-L8](https://github.com/bytecodealliance/wasmtime/blob/v49.0.3/crates/cranelift/src/func_environ/stack_switching/fatpointer.rs#L7-L8)). V8 (May 2026): a generator step costs 53 ns against 2.4 ns for a direct call ([slides](https://github.com/WebAssembly/meetings/blob/882204b422e23e1c289978b7364e535357b7253d/stack/2026/Presentations/WasmFX%20in%20V8.pdf)). The 2023 prototype was "more than a factor of three slower" than Asyncify at run time, with smaller binaries (paper §5.1).
- **(h) JavaScript.** N/A for WasmFX. The JSPI authors model JSPI as `reset` at the `promising` export and `shift` at the `Suspending` import ([ImplementationGuide#L35-L55](https://github.com/WebAssembly/js-promise-integration/blob/5b247b1026d2f438eefe51914a79f4218cbda9f9/proposals/js-promise-integration/ImplementationGuide.md#L35-L55)); V8 builds WasmFX on JSPI's stacks. "The actual cost of a stack switch is of the order of five to 10 C function calls." ([#L179](https://github.com/WebAssembly/js-promise-integration/blob/5b247b1026d2f438eefe51914a79f4218cbda9f9/proposals/js-promise-integration/ImplementationGuide.md#L179))
- **(i) Tail-resumptive.** None: "WasmFX as it stands includes no facilities for identifying and inlining tail-resumptive handlers." (paper §6.2). Wasmtime disables inlining with stack switching ([config.rs#L2706](https://github.com/bytecodealliance/wasmtime/blob/v49.0.3/crates/wasmtime/src/config.rs#L2706)).
- **UNCONFIRMED.** Whether V8 retains abandoned suspended stacks at run time (inferred from root scanning); whether shipped JSPI always suspends per [PR #57](https://github.com/WebAssembly/js-promise-integration/pull/57); how continuation references cross into JS ([issue #95](https://github.com/WebAssembly/stack-switching/issues/95)); whether reified fibers replace tags and continuations.

## 6. Koka

Pinned: koka `v3.2.9` (2026-09-17). Papers: Xie and Leijen, "Effect Handlers, Evidently", ICFP 2020 ([PDF](https://www.microsoft.com/en-us/research/uploads/prod/2020/07/evidently.pdf)); Xie and Leijen, "Generalized Evidence Passing for Effect Handlers", ICFP 2021 ([PDF](https://www.microsoft.com/en-us/research/uploads/prod/2021/08/genev-icfp21.pdf)); Leijen, "Type Directed Compilation of Row-Typed Algebraic Effects", POPL 2017 ([PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/algeff.pdf)).

- **(a) One-shot.** None. `ctl` resumptions are multi-shot; the only static restriction is `linear effect`, which rejects `ctl` and allows only tail-resumptive `fun`/`val` clauses. No runtime counter exists.
  - `ctl choice() resume(False) ++ resume(True)` ([book](https://koka-lang.github.io/koka/doc/book.html#sec-multi-resume))
  - "Use linear effect to declare effects whose operations are always tail-resumptive and use only linear effects themselves (and thus resume exactly once)." ([book](https://koka-lang.github.io/koka/doc/book.html#sec-linear)); parser: `then fail "'ctl' operations are invalid for a linear effect"` ([Parse.hs#L1204-L1213](https://github.com/koka-lang/koka/blob/v3.2.9/src/Syntax/Parse.hs#L1204-L1213))
- **(b) Abandonment.** Three rules by clause kind. A `ctl` clause that returns without resuming finalizes the continuation by re-entering it with a final yield, so every `finally` in the abandoned segment runs after the clause body. A `final ctl` (such as `exn`) unwinds `finally` frames before the clause body. A `raw ctl` finalizes nothing automatically.
  - `finally` "takes as its first argument a function that is always executed when either returning normally, or when unwinding for a non-resuming operation." ([book](https://koka-lang.github.io/koka/doc/book.html#sec-resource))
  - `// otherwise, if we are not yielding, resume k with finalization (to run all finally clauses)` ([hnd.kk#L618-L640](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/core/hnd.kk#L618-L640))
  - `-- don't optimize ctl to exc since exc runs the finalizers before the clause (unlike ctl)` ([Infer.hs#L950-L956](https://github.com/koka-lang/koka/blob/v3.2.9/src/Type/Infer.hs#L950-L956))
  - For `raw ctl`: "it is now the programmers' resposibility to ensure the resumption is eventually resumed or finalized (such that any resources can be released)." (sic) ([book](https://koka-lang.github.io/koka/doc/book.html#sec-rcontrol))
  - With multiple resumes, `finally` runs on each: "the second time it resumes the file handle will be closed again which is probably not intended." ([book](https://koka-lang.github.io/koka/doc/book.html#sec-resource))
- **(c) Cancellation vs resumption.** The core has none; `std/async` builds it from handlers. A cancelled scope delivers `Cancel` to each outstanding await, which turns into a `final ctl` so `finally` blocks run. Late host callbacks are stopped only by each primitive's dispose function.
  - "Of course, `finally` blocks still execute so external resources can be released properly." ([async.kk#L15-L37](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/async/async.kk#L15-L37))
  - `// set callback to null in the dispose function as we cannot really cancel NodeJS requests` ([file.js#L50-L55](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/async/api/uv/file.js#L50-L55)): a late Node result is silently dropped.
  - The 2017 design checked that the await was still outstanding: "This is an essential check: even if an operation is canceled it may still happen that a callback is called later on if the resources were not properly released." ([MSR-TR-2017-21 §3.4.2](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/05/asynceffects-msr-tr-2017-21.pdf)); that check is gone in v3.2.9.
- **(d) Dynamic state.** The handler stack is the evidence vector. Clauses run under the vector current when the handler was installed, not the perform site's; a resumed `prompt` re-inserts its evidence on top of the resumer's vector.
  - "In contrast, we evaluate each clause under their original context and need the evidence vector corresponding to that." (ICFP 2020 §4.4)
  - ICFP 2020 required scoped resumptions because "efficient evidence translation (with its subsequent performance benefits) is not possible if we allow resumptions to be this dynamic." (§2.2); ICFP 2021 lifted it. In v3.2.9: `val w1' = if evv-eq(w0,w0') then w1 else evv-insert(w0',ev)` ([hnd.kk#L402-L410](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/core/hnd.kk#L402-L410)).
  - `var` locals are saved at each yield and restored on resume ([hnd.kk#L469-L478](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/core/hnd.kk#L469-L478)). An open PR reports the resulting hazard: "So a resumed strand sees the caller's scope" ([PR #934](https://github.com/koka-lang/koka/pull/934), unmerged).
- **(e) Handlers.** Deep: "For our purposes, we always need “deep” handling where the resumption evaluates under the same prompt again" (ICFP 2020 §5.1); `raw ctl` offers `resume-shallow`. Binding is dynamic by effect label; "mask only masks an operation once for its innermost handler" ([book](https://koka-lang.github.io/koka/doc/book.html#sec-mask)). `named` handlers are lexical values outside the evidence vector; `named scoped` adds a rank-2 type that prevents escape.
- **(f) Boundaries.** No threads in the effect system. The JS runtime keeps evidence and yield state in module globals (`var _evv = [];`, `var _yield = null;`, [hnd.js#L31-L32](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/core/inline/hnd.js#L31-L32)). "now we can implement interleaving using only single-shot resumptions (which we need for example when targeting native WASM stacks)." ([interleave.kk#L275-L287](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/async/interleave.kk#L275-L287))
- **(g) Representation and cost.** Yield bubbling: the resumption is built from join-point closures while the yield propagates; non-yielding code allocates nothing but checks a flag.
  - "instead of capturing the delimited evaluation context E wholesale, we are going to build a resumption function piecemeal while bubbling up." (ICFP 2021 §2.7)
  - "segmented stacks need a dedicated runtime system but can capture and resume an operation in constant time (for one-shot resumptions), while a multi-prompt monad is linear in the continuation points." (ICFP 2021 §1)
- **(h) JavaScript.** v1 used type-directed selective CPS: "At first, we tried a full CPS translation in Koka but it turned out to slow down the code significantly." and "In the Koka core library, this reduced the set of CPS translated functions by over 80%." (POPL 2017 §5). Current Koka uses evidence passing plus a multi-prompt monad for every backend; the evidence runtime is "about 100 lines of JavaScript" with JS speedups over the CPS runtime of 1.94× (counter) to 46.09× (nqueens) (ICFP 2020 §6.5). `--target=js`, `jsnode`, `jsweb` remain in v3.2.9 ([Syntax.hs#L267-L282](https://github.com/koka-lang/koka/blob/v3.2.9/src/Common/Syntax.hs#L267-L282)).
- **(i) Tail-resumptive.** `fun`/`val` clauses run in place: "it calls it directly as a regular function (except with an adjusted evidence vector for its context). Unlike a general ctl operation, there is no need to yield upward to the handler, capture the stack, and eventually resume again." ([book](https://koka-lang.github.io/koka/doc/book.html#sec-opfun)). "the third component w is the evidence context: this is the evidence vector under which the handler h is defined and is used for the evaluated-in-place expression." (ICFP 2021 §2.6). "Finally, tail-resumptive optimization speeds up the counter benchmarks by 10×." (ICFP 2021 §5)
- **UNCONFIRMED.** Behavior when a `ctl` resumption is resumed after auto-finalization (no guard in code; not executed); the release that first shipped automatic `ctl` finalization; whether CI runs JS-target tests.

## 7. Effekt

Pinned: effekt `v0.82.0` (2026-09-28). Papers: Brachthäuser, Schuster, Ostermann, "Effects as Capabilities", OOPSLA 2020 ([PDF](https://infoscience.epfl.ch/bitstreams/d8c0cff1-6103-46c7-acb6-c9cc3dbb2704/download)); Schuster et al., PLDI 2022 ([TR](https://se.cs.uni-tuebingen.de/publications/schuster22typed.pdf)); Müller et al., "Back to Direct Style: Typed and Tight", OOPSLA 2023 ([TR](https://se.cs.uni-tuebingen.de/publications/mueller23continuation.pdf)); Muhcu et al., ICFP 2025 ([PDF](https://se.cs.uni-tuebingen.de/publications/muhcu2025multiple.pdf)); Voigt et al., OOPSLA 2025 ([PDF](https://se.cs.uni-tuebingen.de/publications/voigt2025dynamic.pdf)).

- **(a) One-shot.** Not enforced; `resume` is multi-shot by design. The JS runtime has no used-flag; the LLVM backend copies a resumption only when it is shared (reference count) and aborts on reentrant resume.
  - "Calling `resume` multiple times runs the rest of the computation multiple times: this is how nondeterminism and backtracking work." ([tour](https://github.com/effekt-lang/effekt/blob/v0.82.0/examples/tour/effect-handlers.effekt.md#L119-L122))
  - "Resumptions are not reentrant, meaning that a continuation cannot be resumed, while it is already running. Our implementation leads to a runtime error in this case." (ICFP 2025)
- **(b) Abandonment.** The continuation is discarded and no user code runs. The stdlib `finalize` runs only on normal return or `Exception[E]`.
  - "Not calling `resume` aborts the producer, and the continuation is discarded (as with `throw` above)." ([tour L120](https://github.com/effekt-lang/effekt/blob/v0.82.0/examples/tour/effect-handlers.effekt.md#L120))
  - The research fix runs cleanup at capture time: "Since we cannot be sure whether the continuation will be discarded or resumed, we need to ensure that all resources are released during the continuation capturing (stack unwinding)." (OOPSLA 2025); only on JS, and [PR #701](https://github.com/effekt-lang/effekt/pull/701) is an open draft.
- **(c) Cancellation vs resumption.** N/A: Effekt has no interruption. Late or duplicate FFI callbacks are unguarded: `const res = body(x => TRAMPOLINE(() => k(x, ks)))` ([effekt_runtime.js#L125-L131](https://github.com/effekt-lang/effekt/blob/v0.82.0/libraries/js/effekt_runtime.js#L125-L131)).
- **(d) Dynamic state.** The metacontinuation is a list of segments, each with a prompt and an arena of `var` cells. Capture moves segments up to the target prompt and snapshots arenas; resume pushes them onto the resumer's metacontinuation.
  - "This is because the state (like mutable variables) is allocated on the stack, and thus, the captured continuation includes the initial state of `x` and is therefore restored when resumed." ([regions tour L61](https://github.com/effekt-lang/effekt/blob/v0.82.0/examples/tour/regions.effekt.md#L61))
  - "A snapshottable arena: a bag of `Ref`s whose collective state can be captured in O(1) and restored in O(#writes since capture)." ([effekt_runtime.js#L35-L38](https://github.com/effekt-lang/effekt/blob/v0.82.0/libraries/js/effekt_runtime.js#L35-L38))
- **(e) Handlers.** Deep and lexically bound: `try` creates a fresh prompt and binds a capability that closes over it; operation calls `shift` to that prompt with no search by type.
  - "Closing over capabilities avoids accidental handling, a problem that arises when handlers are allocated on the stack and dynamically searched at runtime." (OOPSLA 2020)
  - Continuations were second-class in 2020: "However, in Effekt continuations are blocks and can neither be returned, nor stored in data structures." (OOPSLA 2020). Since System C, `box` makes them first-class with a capture set. Open soundness hole: [issue #1176](https://github.com/effekt-lang/effekt/issues/1176) ("Prompt not found").
- **(f) Boundaries.** `extern def spawn[T](task: () => T at {io, async, global}) at async: Unit` ([io.effekt#L11-L17](https://github.com/effekt-lang/effekt/blob/v0.82.0/libraries/common/io.effekt#L11-L17)); a spawned task starts on an empty metacontinuation, so no prompts or arenas cross.
- **(g) Representation and cost.** JS: a segment is `{stack, prompt, arena, rest}`; capture is O(segments to the prompt), resume O(segments) plus O(writes since capture) ([effekt_runtime.js#L109-L178](https://github.com/effekt-lang/effekt/blob/v0.82.0/libraries/js/effekt_runtime.js#L109-L178)). LLVM: per-prompt growable stacks; "We introduce prompts with stable addresses as an indirection to stacks." (ICFP 2025)
- **(h) JavaScript.** Source → Core → CPS → JS ([JavaScript.scala#L40-L65](https://github.com/effekt-lang/effekt/blob/v0.82.0/effekt/shared/src/main/scala/effekt/generator/js/JavaScript.scala#L40-L65)). All Effekt-defined functions are CPS; direct style comes from extern capture sets (`!(isAsync || isMutableState) && (isIO || isResource)`, [symbols.scala#L415-L422](https://github.com/effekt-lang/effekt/blob/v0.82.0/effekt/shared/src/main/scala/effekt/symbols/symbols.scala#L415-L422)), a `DirectStyle` pass for join points, and loop emission for self-recursion. "Back to Direct Style" inserts control "only where necessary, i.e. where continuations are used non-trivially." ([TR](https://se.cs.uni-tuebingen.de/publications/mueller23continuation.pdf)); whether the compiler implements it is UNCONFIRMED.
- **(i) Tail-resumptive.** `StaticResumptions` ([PR #1471](https://github.com/effekt-lang/effekt/pull/1471), merged 2026-09-22) rewrites `shift(p){k => B[resume(k){s}]}` to `B[s]`: "Sound iff every use of `k` is a tail shift, reached only through segments no shift observes, and every exit is one too" ([StaticResumptions.scala#L334-L341](https://github.com/effekt-lang/effekt/blob/v0.82.0/effekt/shared/src/main/scala/effekt/core/optimizer/StaticResumptions.scala#L334-L341)). With finalizer clauses: "Thus, in general, this optimization is not semantics-preserving." (OOPSLA 2025 §4.2)
- **UNCONFIRMED.** Whether calling an `$effekt.capture` callback twice corrupts state; one-shot cost of the three Chez runtimes.

## 8. Effection

Pinned: `effection` 4.2.0 (tag `effection-v4.2.0`, published 2026-10-02); 3.x at `effection-v3.6.1`; `@frontside/continuation` 0.1.6. From v4.0.0, Effection runs its own coroutine and reducer and no longer uses `@frontside/continuation` ([v4 post](https://frontside.com/blog/2025-12-23-announcing-effection-v4/), maintainer blog).

- **(a) One-shot.** v4: each `perform` stores a fresh resolver; only the current resolver resumes, and second, stale, or late resolves are dropped with no signal ([coroutine.ts#L94-L106](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/coroutine.ts#L94-L106)):
  ```ts
  let resolve = resolver = (result) => {
    if (resolver === resolve) {
      resolver = null;
      routine.resume(result);
    }
  };
  ```
  `@frontside/continuation` 0.1.6 wraps each continuation function in `oneshot()`, which returns the first call's cached result on later calls ([mod.ts#L163-L177](https://github.com/thefrontside/continuation/blob/v0.1.6/mod.ts#L163-L177)); the guard is per function, not per suspension point.
- **(b) Abandonment.** A never-resolved effect parks the coroutine until its scope is destroyed: "A suspended operation will remain paused until its enclosing scope is destroyed, at which point it proceeds as though return had been called from the point of suspension." ([suspend.ts#L7-L9](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/suspend.ts#L7-L9)). No GC path or leak diagnostic. Halting is lazy: "You must observe it (`await` / `yield*` / `.then()`), or shutdown is not guaranteed to complete." ([agents.md#L116-L117](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L116-L117))
- **(c) Cancellation vs resumption.** Halt clears the resolver, runs the current effect's exit function, then calls `iterator.return()` once ([coroutine.ts#L86-L92](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/coroutine.ts#L86-L92)). A Promise that settles after a halt finds no resolver and is dropped ([call.ts#L93-L97](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/call.ts#L93-L97)). An effect inside a delegated `finally` loses the halt: "If a `finally` block then yields, the generator suspends _inside_ the finally and reports `{ done: false }`, so the routine resumes it with `iterator.next()` — and that takes the frame out of return-mode." ([agents.md#L264-L269](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L264-L269)). Maintainer: "There is simply no way for the machine driving a generator to know if it is inside a finally block." ([#1154](https://github.com/thefrontside/effection/issues/1154#issuecomment-4261531118), open). The docs conflict: the scope guide says "In fact, Effection handles this case for you" ([scope.mdx#L177-L178](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/scope.mdx#L177-L178)); the agent contract says "You must not `yield*` inside a `finally`." ([agents.md#L251](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L251)).
- **(d) Dynamic state.** Context lives on the Scope, not the JS stack: `contexts = Object.create(parent.contexts)` ([scope-internal.ts#L41-L48](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/scope-internal.ts#L41-L48)), read live when a context effect runs, so values survive suspension. "You must treat context as scope-local. Children inherit from parents; children may override without mutating ancestors." ([agents.md#L142-L143](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L142-L143))
- **(e) Handlers.** Built-in effects carry their interpretation in `enter`; no handler stack is searched. 4.1 added experimental Contextual APIs looked up on the scope at call time ([api-internal.ts#L36-L45](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/api-internal.ts#L36-L45)). "Lexical" there means "scope hierarchy follows the lexical structure of operation invocation sites (e.g. `yield*`, `spawn`, `Scope.run`), not where references are stored or later used." ([agents.md#L28-L30](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L28-L30))
- **(f) Boundaries.** One thread. Task handles, errors (to the nearest trap), context, and priority cross between tasks; only settled values cross Promise boundaries. `until()` "does not make the promise cancellable" ([agents.md#L208-L209](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L208-L209)).
- **(g) Representation and cost.** A continuation is the coroutine's top iterator plus one resolver closure; frames are the native `yield*` chain. "For deeply nested or recursive operations, the cost of resuming a single yield point is O(depth)." ([effectionx inline README#L13-L14](https://github.com/thefrontside/effectionx/blob/752a97f4a2a184f5e0c49814bf9609a53f37ce14/inline/README.md#L13-L14))
- **(h) JavaScript.** Plain generators. The optional `@effectionx/inline` transform rewrites `yield* expr()` into `(yield $$inline(expr()))` and drives delegation from an explicit frame stack ([README#L83-L85](https://github.com/thefrontside/effectionx/blob/752a97f4a2a184f5e0c49814bf9609a53f37ce14/inline/README.md#L83-L85)).
- **(i) Tail-resumptive.** A synchronous effect resolves inside `enter`; while the reducer runs, `schedule` only enqueues ([reducer.ts#L16-L18](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/reducer.ts#L16-L18)), so the stack does not grow. No static detection. In 0.1.6, `k.tail(v)` reuses the running reduction loop; a test resumes 100,000 times ([test#L107-L118](https://github.com/thefrontside/continuation/blob/v0.1.6/t/continuation.test.ts#L107-L118)).
- **Why generators.** "Critically for our use-case, generator functions allow for an explicit return() which signals them to exit posthaste from wherever they are currently executing." ([Await Event Horizon](https://frontside.com/blog/2023-12-11-await-event-horizon/), maintainer blog)
- **UNCONFIRMED.** In v4.2.0 an `action` that resolves synchronously may never run its exit function, because the next `perform` overwrites the stored exit first ([coroutine.ts#L49-L58](https://github.com/thefrontside/effection/blob/effection-v4.2.0/lib/coroutine.ts#L49-L58)); a `suspend()` inside `finally` during halt may never settle `halt()`. Both are from source reading only.

## 10. Rompf, Maier, Odersky, ICFP 2009 (Scala selective CPS)

"Implementing First-Class Polymorphic Delimited Continuations by a Type-Directed Selective CPS-Transform" ([PDF](https://infoscience.epfl.ch/server/api/core/bitstreams/3b4fdf4f-16da-4e39-b616-61a92e16d7e0/content), [DOI](https://doi.org/10.1145/1596550.1596596)).

- **Selection rule.** "we employ a selective CPS transform, which is driven entirely by effect-annotated types and leaves pure code in direct style." and "We thus define an expression as pure if and only if it does not reify its continuation via shift in the course of its evaluation."
- **Delimiting.** "A shift will capture the control context up to, but not including, the nearest dynamically enclosing reset". Annotations "propagate via the return types to the dynamically enclosing context. The propagation stops upon reaching a `reset` block." ([package.scala#L74-L76](https://github.com/scala/scala-continuations/blob/17008dcb93aa4a82de7ee71d842d138d7b6706ce/library/src/main/scala/scala/util/continuations/package.scala#L74-L76))

- **Cost.** About 30% faster than Kilim on actor ping-pong; for generators "the speedup for the tree-like case is more significant and amounts to more than a factor of seven." ## 11. Stopify (PLDI 2018)

Baxter, Nigam, Politz, Krishnamurthi, Guha, "Putting in All the Stops: Execution Control for JavaScript" ([arXiv v2 PDF](https://arxiv.org/pdf/1802.02974v2); code at [nuprl/Stopify](https://github.com/nuprl/Stopify); stopify.org returns HTTP 410).

- **Strategies** (§3.2): checked-return (`retval`): "every function application is instrumented to check whether the program is in capture mode."; exceptional (`lazy`, Loitsch 2007): "C throws a special exception and every function application is guarded by an exception handler that catches the special exception, reifies the stack frame, and re-throws it."; eager: "maintains a shadow stack at all times [71]. This makes capturing continuations trivial and very fast. However, maintaining the shadow stack slows down normal execution." "Both checked-return and exceptional continuations reify the stack lazily."
- **Restore** (§3.1): each frame saves "(1) a copy of the local variables, (2) a label that identifies the current position within the function, and (3) a thunk called reenter that re-enters the function."
- **Generators rejected** (§3): "Alternatively, we could use generators to implement one-shot continuations [3]." Reasons: "on several benchmarks, we find that cps and generators are 3x and 2x slower than the approach we present below." and "both approaches change the type of instrumented functions (cps adds an extra argument and generators turn all functions into generator objects)." The paper adds that this "makes it hard to support features such as constructors and prototype inheritance."
- **Numbers** (Fig. 10, median slowdown yielding every 100 ms): from 1.4–3.8× (PyJS) to 13.7–37.2× (plain JavaScript) depending on source language and browser; no strategy-by-strategy medians are published (UNCONFIRMED). Exceptional capture won on Chrome, Firefox, and Safari; checked-return on Edge (Fig. 11). Code size grew "a factor of 8x on average with a standard deviation of 5x" (§6.1).
- **Deep stacks** (§5.2): "This mode tracks a stack depth counter that is updated in every function call. On reaching a predefined limit, the stack is captured with C, and computation resumes with an empty stack (that closes over the captured one)." The shipped wiki marks this mode "currently broken" (UNCONFIRMED scope).
- **Yield timing.** Counting basic blocks yielded every 30 ms on some Chrome benchmarks and every 1.5 s on some Edge benchmarks (Fig. 2c); sampling `Date.now()` "ensures that the program interrupts every δ milliseconds with high probability." (§5.1)

## 12. Revisiting Coroutines (TOPLAS 2009) and Yield (TPDC 2011)

**de Moura and Ierusalimschy, "Revisiting Coroutines"**, TOPLAS 31(2) ([published PDF mirror](https://www.cs.tufts.edu/~nr/cs257/archive/roberto-ierusalimschy/revisiting-coroutines.pdf), [tech report](https://www.inf.puc-rio.br/~roberto/docs/MCC15-04.pdf), [DOI](https://doi.org/10.1145/1462166.1462167)).

- **Claim** (§1): "when provided as first-class objects and implemented as stackful constructs (i.e., when a full coroutine mechanism is implemented) coroutines have power equivalent to one-shot continuations and one-shot delimited continuations."
- **Generators are not full coroutines** (p. 6:5): a Python generator "can only suspend its execution when its control stack is at the same level that it was at creation time. In other words, only the main body of a generator can suspend."
- **One-shot by construction.** Resume clears the label: "In order to prevent the coroutine to be reactivated, its label is mapped to nil." Their `call1cc` encoding redefines `throw` "to invalidate its label after using it" (§5.2).
- **Multi-shot.** "We also did not prove that we cannot express multishot continuations using coroutines." Intuition: "while the rewrite rule for callcc duplicates a context, no rule in λa ever does so." (§6)
- **Why asymmetric.** "since asymmetric coroutines always transfer control back to their invokers, control sequencing is much simpler to manage and understand." (p. 6:4); "Like delimited continuations, asymmetric coroutines are composable" (p. 6:28).

**James and Sabry, "Yield: Mainstream Delimited Continuations"** ([PDF](https://homes.luddy.indiana.edu/sabry/files/yield.pdf)).

- **Claim.** "The resulting yield operator turns out to be a new sort of delimited continuation operator equivalent to shift-reset and this is our main result." (§1). "The mainstream variants of yield turn out to be one-shot or linearly used restrictions of delimited continuations." (abstract)
- **Mainstream restriction.** "yield suspends exactly the current method and the continuations captured by it may be described as one-frame or lexically delimited continuations." (§3.1); re-yielding through every frame is "inefficient due to the explicit frame-by-frame unwinding of the stack" (p. 8); "methods that yield are treated differently from methods that don’t, requiring the former to be called in a special manner." (p. 6)
- **The equivalence uses reusable continuations**: "the term (λx.run E[return x]) is indeed a pure function that may be called any number of times." (p. 7). No one-shot theorem: "its restricted (linearly-used) versions are still useful and their expressiveness deserves further study." (§5)

## 13. Bruggeman, Waddell, Dybvig, PLDI 1996

"Representing Control in the Presence of One-Shot Continuations" ([Wayback copy of author PDF](https://web.archive.org/web/20250413082745/https://legacy.cs.indiana.edu/~dyb/pubs/call1cc.pdf), [ACM scan](https://www.khoury.northeastern.edu/home/shivers/cs6983/papers/dybvig-1shot-conts.pdf), [DOI](https://doi.org/10.1145/231379.231395)).

- **Rule.** One-shot continuations "differ from multi-shot continuations only in that it is an error to invoke a one-shot continuation more than once." (§2). A normal return counts: "a continuation can be invoked either implicitly, by returning from the procedure passed to call/cc or call/1cc, or explicitly". Invocation marks it: "it is marked “shot” by setting the size and current size to −1." (§3.2). Chez v10.4.1 raises `"attempt to invoke shot one-shot continuation"` ([cpnanopass.ss#L4964-L4978](https://github.com/cisco/ChezScheme/blob/v10.4.1/s/cpnanopass.ss#L4964-L4978)).
- **Representation.** Segmented stacks: "the entire current segment is encapsulated in the continuation and a fresh stack segment is allocated to replace the current stack segment"; "For one-shot continuations, there is no need to copy the saved stack segment since the continuation will be invoked only once." (§3.2)
- **Promotion.** "One-shot continuations must be promoted to multi-shot status when they are captured as part of a multi-shot continuation." (§2); after promotion the check is gone ([CSUG](https://cisco.github.io/ChezScheme/csug/control.html)).
- **Cost.** "The version using call/1cc is 13% faster than the version using call/cc and allocates 23% less memory." (§4); stack overflow handled as an implicit one-shot capture is "300% faster" (§4). A segment cache is required: "Without a stack segment cache, we found that many programs written in terms of call/1cc were unacceptably slow, much slower than the equivalent programs written in terms of call/cc." (§3.2)
- **Abandonment.** Not discussed; a captured one-shot continuation retains its whole segment: "With a default stack size of 16KB, 100 threads created using call/1cc occupy 1.6MB of memory." (§3.4)

## 14. Kiselyov, Shan, Sabry, "Delimited Dynamic Binding", ICFP 2006

[PDF](https://okmij.org/ftp/Computation/DBplusDC/DDBinding.pdf), [page](https://okmij.org/ftp/Computation/dynamic-binding.html).

- **Principle** (abstract): "capturing a delimited continuation closes over part of the dynamic environment, rather than all or none of it; reinstating the captured continuation supplements the dynamic environment, rather than replacing or inheriting it."
- **Rule** (§4.2.3): "capturing a delimited continuation should close over the dynamic bindings within the delimiter but discard those beyond the delimiter." It applies to one-shot use too: "Analogous design considerations apply whether delimited continuations are used as coroutines (when each delimited continuation is invoked exactly once) or for backtracking".
- **Worked example** (§4.2, example 6): capture under `dlet p=1 · reset · dlet r=10`, resume under `dlet p=2 · dlet r=20`; "The captured delimited continuation contains the dynamic binding r = 10 but not p = 1, so the result is 12." The shift body (the handler) sees only bindings outside the delimiter: in example 5, "the “shift” in (5) above discards the later binding p but not the earlier one, so it evaluates to 1."
- **Critique.** Existing implementations force continuations "to close over (capture) all or none of the dynamic environment" (§4.1); Chez parameters: "The parameterisation may fail for some print expressions clearly within parameterisation’s dynamic scope."
- **Implementation.** "Each parameter p of DB is translated into a unique prompt of DC." Correct "So long as the prompts that correspond to dynamic variables are not accessible to the user". Deep binding is favored: "Because control delimiters let us slice, dice, and recombine dynamic environments, the arguments above in favour of deep binding are particularly severe in the presence of delimited control." (§7)

## 16. Rust: cancellation by drop and async drop

Pinned: Rust 1.99.1, tokio 1.53.3.

- **Abandonment is drop.** Dropping an unfinished future runs drop glue for values live at the last suspension point; "the canceled future will get no notification of cancellation and no opportunity to clean up (besides its destructor)." ([async book](https://rust-lang.github.io/async-book/part-guide/more-async-await.html#cancellation)). Destructors are not guaranteed: "forget is not marked as unsafe, because Rust’s safety guarantees do not include a guarantee that destructors will always run." ([mem::forget](https://doc.rust-lang.org/1.99.1/std/mem/fn.forget.html))
- **Completion is one-shot.** "Once a future has completed (returned Ready from poll), calling its poll method again may panic, block forever, or cause other kinds of problems" ([Future](https://doc.rust-lang.org/1.99.1/std/future/trait.Future.html)); `async fn` futures panic with "`async fn` resumed after completion" ([terminator.rs#L298-L300](https://github.com/rust-lang/rust/blob/1.99.1/compiler/rustc_middle/src/mir/terminator.rs#L298-L300)). `oneshot::Sender::send(self)` consumes the sender; a dropped sender surfaces as `RecvError` rather than a hang ([tokio oneshot](https://docs.rs/tokio/1.53.3/tokio/sync/oneshot/index.html)).
- **Races are at the edges.** `select!` drops losing branches, hence "Cancellation safety describes what happens when a future is dropped before it completes." ([tokio select](https://docs.rs/tokio/1.53.3/tokio/macro.select.html#cancellation-safety)). wasm-bindgen cannot cancel promise callbacks: "one of the callbacks is likely always going to be invoked." ([js-sys futures](https://github.com/wasm-bindgen/wasm-bindgen/blob/0.2.129/crates/js-sys/src/futures/mod.rs#L183-L197))
- **Dynamic state.** Tokio swaps task-locals around every `poll` and around `drop`, so destructors see the capture-site value ([task_local.rs#L330-L341](https://github.com/tokio-rs/tokio/blob/tokio-1.53.3/tokio/src/task/task_local.rs#L330-L341)).
- **Async drop.** Not stable; [tracking issue #126482](https://github.com/rust-lang/rust/issues/126482) is open with unresolved questions including "Synchronously undroppable types". The 2026 roadmap still says "Destructors are sync-only." ([roadmap](https://github.com/rust-lang/rust-project-goals/blob/0c707594d5126c52a1c1557678ea4c521416fbbd/src/2026/roadmap-just-add-async.md?plain=1#L29)).

## Supplementary primary sources

### Host baseline: Effect 4.0.5

These facts come from the `effect@4.0.5` source (tag `effect@4.0.5`, commit `7f524e25cfb49a71ac39b0f44278d08d40dda5de`) and from one-command reproductions run with Node v26.10.0 in `experiments/` (`node --input-type=module -e '...'`). They describe the runtime EffectScript lowers to, so every rule below has to be implemented against them.

- **`Effect.callback` is already a one-shot continuation that ignores later resumes.** "Call `resume` at most once with the effect that should complete the fiber; later calls are ignored. Return an optional cleanup effect from the registration function to run if the fiber is interrupted." ([Effect.ts#L1816-L1859](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/Effect.ts#L1816-L1859)). The guard is a closure flag: `if (resumed) return` ([internal/effect.ts#L1141-L1207](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L1141-L1207)). Reproduced: two `resume` calls deliver only the first value.
- **A value delivered after interruption is dropped silently.** On interruption the frame's finalizer sets `resumed = true`, calls `controller?.abort()`, and runs the registration's cleanup effect (same lines). Reproduced: after `Fiber.interrupt`, the cleanup ran and a late `resume(Effect.sync(...))` was never evaluated. There is no hook that receives the dropped value, unlike Kotlin's `onCancellation` (section 2).
- **Synchronous resume does not suspend, and asynchronous resume runs the fiber on the resumer's stack.** If `resume` is called inside the registration function, the effect is returned directly (same lines; reproduced with `Effect.runSync`). If it is called later, `fiber.evaluate(effect)` runs the run loop inline. Reproduced order: `before-resume -> fiber-continued -> after-resume`.
- **`Effect.gen` abandons the generator object on failure or interruption; JavaScript `catch` and `finally` in the body do not run.** `Effect.gen` is `suspend(() => fromIteratorUnsafe(body()))` ([internal/effect.ts#L1222-L1245](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L1222-L1245)), so each run gets a fresh iterator. The iterator frame defines only a success continuation `[contA]` ([internal/effect.ts#L1413-L1445](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L1413-L1445)), and `getCont` pops frames that lack the requested continuation ([internal/effect.ts#L680-L700](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L680-L700)). Nothing calls `iterator.return()` or `iterator.throw()`. Reproduced: `try { yield* Effect.fail("boom") } catch {...} finally {...}` ran neither block; `try { yield* Effect.never } finally {...}` did not run `finally` when the fiber was interrupted.
- **The fiber's continuation is an explicit heap stack.** `FiberImpl` keeps `_stack: Array<Primitive>` and pops continuation frames ([internal/effect.ts#L487-L700](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L487-L700)). Success values pass "straight to the next continuation", and every `maxInlineSteps` (32) call returns an `Exit` "so continuations calling continuations never nest deeper than that" ([internal/effect.ts#L702-L712](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L702-L712), [#L773-L774](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L773-L774)). Fairness: "The default value is `2048` operations" before a yield ([Scheduler.ts#L280-L297](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/Scheduler.ts#L280-L297)). `_stack` is internal; no public API slices it.
- **Context provision is shallow binding with absolute restore frames.** `updateContext` calls `fiber.setContext(nextContext)` and registers an exit frame that runs `fiber.setContext(prevContext)` ([internal/effect.ts#L2186-L2211](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L2186-L2211); the frame is pushed on `_stack` at [#L4228-L4233](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L4228-L4233)). The restore frame stores a whole previous `Context`, not a delta. A captured stack slice that contains such a frame would restore the capture-time outer `Context` if spliced under a different provider.
- **Host async context is captured at suspension and restored on resume (Node only).** When the run loop yields, the fiber stores `new AsyncResource("effect/Fiber")` from `node:async_hooks`, and the next `evaluate` runs inside `asyncContext.runInAsyncScope(...)` ([internal/effect.ts#L468-L481](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L468-L481), [#L583-L598](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L583-L598)). This fixed [issue #8581](https://github.com/Effect-TS/effect/issues/8581), where a woken fiber ran in the waker's `AsyncLocalStorage` store because it resumed on the waker's stack. The rule from [PR #8629](https://github.com/Effect-TS/effect/pull/8629): "Like `await`, a fiber resumes in the async context it had when it suspended." Browsers get no capture, because `process.getBuiltinModule` is absent.
- **Child fibers copy the parent's `Context` at fork and are supervised.** `forkUnsafe` constructs `new FiberImpl(parentRuntime.context, ...)` ([internal/effect.ts#L5527-L5549](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L5527-L5549)); "when the parent fiber terminates, the child fiber will be terminated as well, ensuring that no fibers leak" ([Effect.ts#L17922-L17926](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/Effect.ts#L17922-L17926)).
- **Scope finalizers are uninterruptible by default.** "By default, finalizers run uninterruptibly, so interrupting the closing fiber waits for them to finish; a finalizer can explicitly restore interruptibility." ([Scope.ts#L546-L582](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/Scope.ts#L546-L582)).

### ECMAScript generators: the one-shot primitive JavaScript provides

ECMA-262 draft, §27.8.3 ([GeneratorValidate](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-generatorvalidate), [GeneratorResume](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-generatorresume), [GeneratorResumeAbrupt](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-generatorresumeabrupt)):

- Re-entrant resume is an error: "If state is executing, throw a TypeError exception."
- Resuming a finished generator is a silent no-op: "If state is completed, return CreateIteratorResultObject(undefined, true)."
- Completion is final: "Once a generator enters the completed state it never leaves it and its associated execution context is never resumed."
- `return()` on a generator suspended at a `yield` resumes it with a return completion, so its `finally` blocks run, and a `yield` inside such a `finally` suspends the generator again.

Consequence: a generator object is a one-shot coroutine, not a one-shot continuation. A second `next()` resumes the next suspension point, not the old one, so the language cannot detect a double resume of a captured continuation from generator state alone. It needs a per-suspension token.

### Racket: prompts, barriers, and parameters

The [Racket reference §1.1.11 and §1.1.13](https://docs.racket-lang.org/reference/eval-model.html) states the capture rules for dynamic state and foreign frames:

- "When a delimited continuation is captured, the marks associated with the relevant frames are also captured."
- "In a non-empty continuation, a parameter’s value is determined through a parameterization that is associated with the nearest enclosing continuation frame via a continuation mark".
- "A continuation barrier thus prevents “downward jumps” into a continuation that is protected by a barrier."

The [continuations chapter](https://docs.racket-lang.org/reference/cont.html) makes capture across a barrier fail at capture time: "When call-with-composable-continuation is called, if a continuation barrier appears in the continuation before the closest prompt tagged by prompt-tag, the exn:fail:contract:continuation exception is raised (because attempting to apply the continuation would always fail)."

### Lexa: lexical handlers compiled to stack switching

Ma, Ge, Lee, Zhang, "Lexical Effect Handlers, Directly", OOPSLA 2024 ([PDF](https://cs.uwaterloo.ca/~yizhou/papers/lexa-oopsla2024.pdf)):

- "Conventionally, effect handlers are dynamically scoped: when an effect is raised, the dynamically closest enclosing handler is chosen to handle the effect. But recent work has found that dynamic scoping threatens abstraction safety and makes it hard to reason modularly about effectful programs".
- On running tail-resumptive handlers in place: "In languages where handlers are dynamically scoped, in-place invocation of tail-resumptive handlers is tricky to get right: extra care must be taken to ensure that the in-place invocation of a handler does not bring in unintended handlers in the dynamic context."
- Result: the compiler reduces "running-time complexity from quadratic to linear in some cases" (abstract).

## Rules EffectScript should adopt or reject

1. **Adopt: one take-once cell per suspension; a second value-resume is a defect.** Resume, discontinue, interruption, and timeout all contend for one cell, including a resume that fires before suspension completes (Loom's `// may have been unparked while parking`, [VirtualThread.java#L559-L588](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/VirtualThread.java#L559-L588)). A value-resume that finds the cell taken by an earlier value-resume fails loudly, as in OCaml ([manual](https://ocaml.org/manual/5.5/effects.html)) and Swift ([CheckedContinuation.swift#L164-L174](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/CheckedContinuation.swift#L164-L174)); one that finds it taken by interruption follows rule 2. `Effect.callback` ignores every later call ([Effect.ts#L1816-L1859](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/Effect.ts#L1816-L1859)), so the handler `resume` must wrap it. Key the cell by suspension, not by generator object, because a second `next()` silently resumes the next suspension point ([ECMA-262 §27.8.3](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-generatorresume)); Wasmtime uses a revision counter for the same reason ([fatpointer.rs#L7-L8](https://github.com/bytecodealliance/wasmtime/blob/v49.0.3/crates/cranelift/src/func_environ/stack_switching/fatpointer.rs#L7-L8)).
2. **Adopt: interruption wins a race, and the losing value is released, not dropped.** Follow Kotlin's prompt cancellation guarantee ([CancellableContinuation.kt#L51-L68](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L51-L68)) and give `resume` an `onCancellation(cause, value)` hook that runs "if and only if the [value] was not successfully used to resume the continuation" ([#L258-L311](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/common/src/CancellableContinuation.kt#L258-L311)). Effect 4 drops a late value with no hook (host baseline), which leaks any resource the value owns.
3. **Adopt: abandonment discontinues at a known point.** When a handler clause returns without resuming, its `Scope` closes, or the fiber is interrupted, resume the continuation with interruption so finalizers inside the captured segment run: OCaml's `discontinue` ([manual](https://ocaml.org/manual/5.5/effects.html)), WasmFX's `resume_throw` ([paper §3.1](https://arxiv.org/pdf/2308.08347v3)), Koka's final yield ([hnd.kk#L618-L640](https://github.com/koka-lang/koka/blob/v3.2.9/lib/std/core/hnd.kk#L618-L640)). Pick one order relative to the clause body and test it; Koka runs `finally` after a `ctl` clause but before a `final ctl` clause ([Infer.hs#L950-L956](https://github.com/koka-lang/koka/blob/v3.2.9/src/Type/Infer.hs#L950-L956)).
4. **Reject: finalization driven by garbage collection.** OCaml's GC-discontinue patch stalled because finalizers "can easily deadlock" ([PR #14580](https://github.com/ocaml/ocaml/pull/14580#issuecomment-4005157907)), and JavaScript engines may "skip calling finalization callbacks for any reason or no reason" ([WeakRefs README#L88](https://github.com/tc39/proposal-weakrefs/blob/a13c3efc5d3b547e05731fa2af7e50348cf61173/README.md#L88)). Use `FinalizationRegistry` only for a development-mode leak report, as Swift logs "leaked its continuation" ([CheckedContinuation.swift#L76-L87](https://github.com/swiftlang/swift/blob/swift-6.4.0-RELEASE/stdlib/public/Concurrency/CheckedContinuation.swift#L76-L87)).
5. **Adopt: lower `finally` and `using` to Effect finalizers, never to JavaScript `finally` inside generated generators.** `effect@4.0.5` abandons the iterator on failure and interruption, so generated `finally` blocks do not run ([internal/effect.ts#L1413-L1445](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L1413-L1445), reproduced). Even calling `return()` is not enough: Effection loses the halt when a delegated `finally` performs an effect ([agents.md#L264-L269](https://github.com/thefrontside/effection/blob/effection-v4.2.0/docs/agents.md#L264-L269)).
6. **Adopt: delimited dynamic binding for `Context`.** On resume, the effective `Context` is the resumer's `Context` overlaid with services provided between the handler and the perform site; the handler clause sees only the outer `Context` ([Kiselyov, Shan, Sabry §4.2](https://okmij.org/ftp/Computation/DBplusDC/DDBinding.pdf); [Racket §1.1.11](https://docs.racket-lang.org/reference/eval-model.html)). Store provided services as deltas in the continuation. Effect 4's restore frames hold an absolute `prevContext` ([internal/effect.ts#L2186-L2211](https://github.com/Effect-TS/effect/blob/effect@4.0.5/packages/effect/src/internal/effect.ts#L2186-L2211)), so splicing captured frames under a new provider would restore stale services.
7. **Adopt: run tail-resumptive operations in place under the handler's definition-site `Context`.** Koka's `fun` clauses skip capture and give 10× on its counter benchmark ([book](https://koka-lang.github.io/koka/doc/book.html#sec-opfun), [ICFP 2021 §5](https://www.microsoft.com/en-us/research/uploads/prod/2021/08/genev-icfp21.pdf)); Lexa warns that in-place invocation under dynamic scoping can "bring in unintended handlers" ([Lexa](https://cs.uwaterloo.ca/~yizhou/papers/lexa-oopsla2024.pdf)). Service methods that close over Layer-acquired dependencies already have this shape; reserve capture for operations that use `resume` non-trivially.
8. **Adopt: deep handlers identified by generative prompt identity; defer shallow handlers.** Effekt binds handlers through capabilities because dynamic search causes "accidental handling" ([OOPSLA 2020](https://infoscience.epfl.ch/bitstreams/d8c0cff1-6103-46c7-acb6-c9cc3dbb2704/download)); WasmFX tags are "created fresh each time the module is instantiated" ([Exceptions.md#L59-L61](https://github.com/WebAssembly/exception-handling/blob/af287a73d8f3bf7ea216c10592f9e350b947c4f2/proposals/exception-handling/Exceptions.md#L59-L61)). Nominal Effect `Context` keys can carry that identity.
9. **Reject: multi-shot resumption.** Every runtime above that runs fibers or threads (OCaml, Kotlin, Swift, Loom, WasmFX) is one-shot. Multi-shot Koka reruns finalizers on each resume: "the second time it resumes the file handle will be closed again which is probably not intended." ([book](https://koka-lang.github.io/koka/doc/book.html#sec-resource)). Kyo keeps `handleCont` single-shot because "a second application would re-enter a bracket the first one already released" ([kyo-kernel README#L245](https://github.com/getkyo/kyo/blob/432aac1f69cb008ddb1e0ac35c0dbec123a2ed96/kyo-kernel/README.md#L245)), which is exactly Effect's `Scope` model, and Effect's maintainer says generators "are only valid to express `one-shot` effect types" ([#3413](https://github.com/Effect-TS/effect/issues/3413#issuecomment-2271114636)).
10. **Adopt: a barrier at foreign frames, diagnosed at compile time or at capture.** OCaml raises `Effect.Unhandled` across `caml_callback` ([manual](https://ocaml.org/manual/5.5/effects.html)); js_of_ocaml: "an effect cannot be performed across a JavaScript frame" ([effects.mld](https://github.com/ocsigen/js_of_ocaml/blob/21add21a7449ff884713e9ade59cdf40a379d777/manual/effects.mld#L38-L54)); JSPI throws `SuspendError` ([spec#L1497](https://github.com/WebAssembly/js-promise-integration/blob/5b247b1026d2f438eefe51914a79f4218cbda9f9/document/js-api/index.bs#L1497)); Racket raises at capture time when a barrier intervenes ([cont.html](https://docs.racket-lang.org/reference/cont.html)).
11. **Adopt: selective transformation with function types polymorphic in "may suspend".** Transform only code that can reach a capture ([Rompf et al.](https://infoscience.epfl.ch/server/api/core/bitstreams/3b4fdf4f-16da-4e39-b616-61a92e16d7e0/content); Koka cut CPS-translated functions "by over 80%", [POPL 2017 §5](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/algeff.pdf); Stopify measured generators "2x slower", [§3](https://arxiv.org/pdf/1802.02974v2)). Without that polymorphism every higher-order API needs a capturing twin, as Scala's plugin required ([CompilerErrors.scala#L27-L36](https://github.com/scala/scala-continuations/blob/17008dcb93aa4a82de7ee71d842d138d7b6706ce/library/src/test/scala/scala/tools/selectivecps/CompilerErrors.scala#L27-L36)); that plugin "is no longer maintained" ([README](https://github.com/scala/scala-continuations/blob/17008dcb93aa4a82de7ee71d842d138d7b6706ce/README.md#L3-L5)).
12. **Adopt: a cross-fiber or host resume never runs the continuation on the resumer's stack.** Effect 4 runs a late resume inline (reproduced), and that design already leaked the waker's async context until [PR #8629](https://github.com/Effect-TS/effect/pull/8629) restored "the async context it had when it suspended". Swift deferred inline resume because it takes over "the current thread from the caller for a potentially unbounded amount of time" ([SE-0300 L446-L455](https://github.com/swiftlang/swift-evolution/blob/f006bf3cf2594bdd4a972f9126f93bd1743ed524/proposals/0300-continuation.md?plain=1#L446-L455)), and Kotlin forbids direct invocation because "that may lead to stack overflow" ([KEEP L894-L898](https://github.com/Kotlin/KEEP/blob/e06f0b96231226a3b2ed64416dc02c3649b4d3d6/proposals/KEEP-0164-coroutines.md?plain=1#L894-L898)). Resume inline only within the owning fiber's run loop; schedule every other resume through the owning fiber, and test a 100,000-fiber wake chain for stack depth and `Context` isolation.
