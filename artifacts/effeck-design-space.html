01 / The core model

The language at a glance

Effeck makes suspension, dependency injection, failure handling, and resource lifetime part of the language. Every function denotes a computation. Ordinary calls compose computations, the compiler tracks their success, errors, and requirements, and Effect supplies the runtime.

The compiler sequences effectful operations and resolves services in the current fiber Context. Success, expected failures, and service requirements must each independently support inference or explicit annotation. This applies to local functions as well as public boundaries. Callers must supply Users and Mailer; providers acquire dependencies and resources through Effect Layers. A cold program can be retried, supervised, and interrupted by the same Effect runtime.

The compiler emits real Effect values and ordinary TypeScript declarations. Scopes own resources and child work, while a checked provider graph satisfies service requirements.

02 / An honest baseline

What we should beat

Effect already has generator notation, inferred channels, service keys, and function helpers. Compare against those conveniences rather than an unnecessarily verbose version. Current docs present Effect 4; the experiments below pin effect@4.0.5. A production compiler should name its supported runtime versions explicitly. [1] [2]

The opportunity is larger than deleting yield*: concise services and tagged errors, ordinary failure control flow, resource-safe scopes, effect-aware higher-order functions, readable diagnostics, and automatic foreign-call adaptation. Merely replacing Effect.gen leaves much of the real friction intact.

03 / Computations and their contracts

One function model

Design requirement

Every function denotes a computation. Calls compose computations through the same language model. Success A, expected failures E, and service requirements R are independently inferred or explicitly declared; the compiler chooses the internal representation.

Calls expose successful results directly. The compiler composes the callee into the current computation and propagates its expected errors and service requirements. Throwing contributes to the failure channel of the owning computation. An explicit Effect<A, never, R> contract rejects escaping expected failures.

Function expressions and callbacks use the same model. A callback can have empty or nonempty channels, which must be checked against the contract of the function that consumes it. Higher-order functions propagate callback channels. A foreign synchronous callback needs a proven compatible synchronous implementation.

Empty expected-error and requirement channels do not establish purity or synchronous completion. The compiler separately analyzes suspension, observable work, and execution timing before specializing a computation into ordinary synchronous code. Public Effect contracts remain stable across these internal optimizations.

04 / The semantic core

Make “one-shot” a precise contract

A delimited continuation is the rest of a computation up to a particular boundary. Suspending an operation captures that remainder; a handler or runtime supplies the operation’s result and continues it. One-shot means a captured continuation may be resumed at most once. Zero resumptions are permitted when failure, cancellation, or an aborting handler ends that path.

Distinguish a cold program description from a live continuation. An Effect description can be executed twice or retried; each execution creates fresh dynamic continuation state. Retrying is not permission to resume an old continuation twice. A JavaScript generator instance is one-shot; a generator factory can create a fresh instance per run.

  • Prompt identity: use a generative or nominal identity so unrelated handlers cannot collide. Specify lexical scope, dynamic dispatch, and nesting.
  • Resume ownership: start with scoped, non-escaping resumptions; validate at-most-once dynamically. Full static affine checking across unrestricted TS aliases would be a much larger language change.
  • Abandonment: describe finalization on handled failure, unhandled failure, cancellation, and an operation whose handler never resumes.
  • Deep or shallow: does resuming re-enter the same handler? Deep handlers are a reasonable first model, but this choice must be explicit.
  • Scheduling: callbacks that finish async operations must never resume twice after cancellation; use Effect’s existing async machinery and cancellation protocol.
  • Stack safety: long continuation chains need trampolining or an equivalent stack-safe interpreter. Pure CPU loops also need a deliberate fairness/safepoint policy.

Compiler research demonstrates several implementations: evidence passing, yield bubbling, and monadic translations can realize algebraic effects through different intermediate representations. A continuation-based language does not require a public shift/reset syntax, nor does it imply JavaScript exposes a stack-capture primitive. [4]

Critical distinction: service substitution, typed failures, and effect sequencing are not by themselves a full algebraic-handler system. A service method returning an Effect can model many tail-resumptive operations. It does not automatically give a handler control over the caller’s captured remainder. Keep that claim out of the language until demonstrated.

05 / The rules people will feel

Calls, values, and cold execution

Calls compose computations uniformly. The compiler can specialize verified synchronous code into ordinary calls and preserve continuation handling for computations that may suspend. Imported functions that return an Effect are executed in the surrounding fiber. Promise-returning foreign calls are lazily adapted. Unannotated foreign synchronous calls are conservatively adapted too. Plain .ts modules retain their own semantics.

These are proposed compiler rules: task is a quotation boundary; value(expr) preserves an Effect as ordinary data. A call composes the callee into the current computation automatically. The compiler uses checked computation contracts rather than recursively flattening any object that happens to look like an Effect.

Preserve left-to-right evaluation, receiver binding, short-circuiting, exceptions, and single evaluation of getters. In f() + g(), execute f before g. In obj.method(arg()), do not detach the method and lose this. In condition && load(), do not eagerly lift both sides.

Specialization preserves the computation model

Pure synchronous arithmeticOrdinary function calls, inlining, or eliminationPreserve the result and valid evaluation behavior

For example, Effect.sleep and Effect.sync can both have empty expected-error and requirement channels. One can suspend; the other can perform observable work. The compiler therefore needs implementation knowledge or trusted contracts beyond A/E/R. Optimizations must not move work from execution time to cold-program construction time. TypeScript-facing exports retain their declared Effect ABI even when internal helpers use ordinary functions.

06 / Runtime contracts and generated APIs

TypeScript interoperability at two levels

Effect-native APIs preserve their declared success, failure, and service contracts. Foreign-call adapters need additional rules for invocation, exceptions, cancellation, and callback ownership.

Boundary A: TypeScript already returns Effect

No Promise bridge or nested runPromise call belongs here. The imported program runs in the same fiber with the same Context, cancellation, Scope, logging, and tracing. Calls that construct an Effect may themselves throw; defer construction and treat unexpected construction exceptions as defects, consistent with an Effect-native contract. A foreign declaration is trusted and can still lie, as it can today.

Recognition should use resolved symbols, runtime-version compatibility, and canonical Effect type identity, not a method named pipe or any iterable object. Preserve aliases, overloads, generic inference, receiver types, and unions. A return type User | Effect<User, E, R> needs an explicit policy or adapter rather than an arbitrary flattening rule. Supporting v3 and v4 does not mean their runtime values are universally interchangeable; support or bridge each version deliberately.

Boundary B: TypeScript does not use Effect

This implements the requested pessimistic policy. Defer the invocation, not just observation of a previously created Promise. Catch synchronous throws, Promise rejection, and errors while reading/invoking a thenable. Preserve this-binding and evaluate arguments once. Imported type-only symbols add no runtime effects; module initialization remains a separate boundary.

An opaque foreign call can open files, start timers, mutate globals, retain callbacks, or launch detached work. Wrapping it catches the errors visible at that boundary; it cannot infer, supervise, or reverse every hidden effect. Static ESM imports may run code before any Effect starts. Represent module initialization risk explicitly rather than claiming that lazy invocation makes the whole dependency graph pure.

07 / Preserve known errors and requirements

Foreign-call uncertainty

Within an Effect-native dependency graph, declared E/R stay precise. A foreign call needs a representation for the parts of its behavior that remain unknown. The alternatives below compare precision, diagnostics, and how that uncertainty can be discharged.

The literal unknown mode is valid as a gradual top type and matches your requested starting intuition. It has a real ergonomic cost: a single foreign call erases the visible union of known requirements and expected failures. It also gives no concrete Context key for an ordinary Layer to provide.

PolicyWhat the user seesHow it can be dischargedTradeoff
Literal unknown in E and RExactly Effect<A, unknown, unknown>Reviewed boundary contract or an explicit unsafe boundary acceptanceMost pessimistic; useful details disappear and normal provision cannot close arbitrary unknown
Nominal foreign markers in E and RKnown unions plus named foreign boundariesA reviewed adapter/manifest; a marker permit acknowledges opacity, it does not supply hidden dependenciesBetter diagnostics and interop; marker is a policy capability, not actual dependency discovery
Separate opacity channel, keep ordinary E/RKnown Effect types plus compiler-only foreign-effect informationA foreign contract or explicit boundary acceptance; export the information for language consumersClean separation; plain TS cannot enforce metadata without extra branded contracts
Only unknown errors, R = neverWhat the runtime wrapper can actually establishHandle/map errors; contextual dependencies remain outside analysisEasy TS interop but weaker than the requested dependency pessimism

Recommendation: keep known errors and requirements plus named opacity internally. Offer literal-unknown declarations as a strict policy/output option. Prefer named markers or a separate foreign-effect channel for everyday diagnostics. Do not secretly substitute never for unknown requirements because the runtime adapter itself happens not to request a service.

Contracts must specify whether they merely declare types or validate/map failures at runtime. Mapping unknown into a domain error improves E; it does not prove the callee has no hidden dependencies. Effect-native modules should preserve their declared E/R by default rather than acquire blanket unknown merely because their source extension is .ts.

08 / The hardest interoperability boundary

The callback test

A one-shot continuation does not magically cross an untransformed JavaScript stack. A library expecting (A) => B cannot generally accept (A) => Effect<B, E, R> and behave the same way. Never make that “work” by silently running a new Effect runtime inside every callback.

Synchronous callback returning BProve callback is synchronous and boundary-compatible; otherwise reject or use an effect-aware replacementSuspend while keeping an untransformed synchronous caller on the stack

Repeated listener / unsubscribeScope-owned subscription and Stream adapterOwnership if the library retains the callback beyond the declared scope

Even TypeScript’s permissive assignment to a void-returning callback can hide a floating Effect. The language checker must track callback channels and synchronous-execution constraints rather than rely on structural assignability alone. A local lambda has its own independently checked contract. Higher-order functions propagate that contract; merely placing a lambda inside another computation does not make it compatible with every foreign callback protocol.

A useful scope boundary

Seamless means ordinary data interop and ordinary Effect composition. Legacy calls can be wrapped automatically, while callback protocols need known contracts. Making those limits explicit is more honest and more useful than promising transparent conversion of every JavaScript program.

09 / Inference, polymorphism, and stability

A type system beyond three visible generics

Use TypeScript’s data types and module resolution as the base. Add effect information to function and callback types. Display three primary channels—success A, expected failure E, requirements R—but retain compiler knowledge of suspension and observable work, foreign opacity, and any resumptive-operation row needed by custom handlers. The existing Effect E/R parameters are not a complete proof of purity, suspension behavior, or arbitrary handled operations. [5]

One return annotation describes the computation

Design requirement

An explicit function contract uses Effect<A, E, R>: success A, expected failures E, and service requirements R. Omitting the return annotation requests inference from the implementation. Each channel must also support independent inference or explicit declaration; the shorthand for partial channel inference remains to be specified.

As with an async function annotated Promise<A>, the annotation describes the complete computation while a successful return expression is checked against A. In Effeck every function uses this computation model. The compiler supplies Effect construction and composition; callers receive successful values directly inside authored code.

An explicit annotation is a checked contract: successful results must fit A, escaping expected failures must fit E, and remaining service requirements must be covered by R. A wider declared contract may be valid; an annotation must never hide additional errors or requirements. E = never rejects escaping expected failures, while R = never rejects remaining service requirements. Empty E/R alone does not establish purity or synchronous completion.

Partial channel inference remains a design requirement. Its type-argument shorthand and defaults are not yet selected. A request for inference must not silently become an assertion of never or unknown; the rules must distinguish inference from an explicit empty channel.

Inference needs an implementation or a contextual contract. Declaration-only functions, service contracts, foreign APIs, and recursive inference cycles need explicit contracts or separately specified defaults. The same A/E/R distinction must survive higher-order function types and emitted declarations.

A full row-polymorphic system can express open sets of algebraic operations and handler subtraction. Simple E/R unions cover much of Effect-style application code with less checker work. Start there if custom operation handlers are not required in v0; reserve a place in IR for richer rows. Do not conflate an error union, service requirements, and resumptive control effects into a single unstructured union.

10 / Familiar syntax with explicit semantics

Failures, defects, and catch

Source throw in an authored function means expected typed failure; ordinary foreign .ts keeps JavaScript throw behavior and adapters translate visible exceptions into unknown or foreign failures. Unexpected exceptions in generated code or trusted Effect construction remain defects. Ordinary typed catch handles E, not interruption or all defects. Add an explicit Cause-level recovery API when needed. Preserve multiple causes when concurrent work fails. [6]

All authored functions use this failure model. A throw contributes to the owning computation’s inferred error channel, and an explicit error annotation constrains what may escape. A function whose declared Effect contract has E = never may handle a failure internally but must not let an expected failure escape. Unexpected runtime defects remain distinct from expected errors.

Do not implement catch by text replacement

In a generator, a yielded Effect failure is handled by the Effect interpreter. It does not throw through the generator’s JavaScript catch block. The experiment verified this. A language-level try/catch must lower to Effect failure handling or an equivalent control-flow state machine; finally and early returns must be transformed too.

11 / Services, provider graphs, and lifetimes

Dependency injection is a language contract

A function’s requirements must mean something the compiler can verify and the runtime can supply. Make service identity, dependency capture, graph composition, scope, and overrides part of the initial language design. A pretty service declaration without those rules would only hide Effect boilerplate.

Services, providers, and an application

The service declaration becomes one nominal runtime Context key plus its method contract. inject Database runs when UsersLive is acquired; the methods close over that database implementation. The application composes provider dependencies and owns their resources. main remains a cold Effect description. Nothing is connected merely because the module is imported.

Do not leak implementation dependencies

A caller of Users.find needs Users. Database belongs to constructing UsersLive. If a method looks up another service at call time instead of capturing it during acquisition, the residual requirement must remain visible or the provider must be rejected against its promised method contract. Never erase it because the service has a convenient name.

A compiler error should explain the graph: welcome → Users → UsersLive → Database → DatabaseLive → Config, then point to the missing provider. Show where an acquisition error originated too. For a cycle, print the shortest useful dependency cycle. A claimed closed program must have no missing service requirements, no unresolved foreign requirement policy, and no escaped resource lifetime.

Overrides, program construction, and execution

Cold tasks normally resolve requirements from the Context where they execute, not whichever Context happened to be active while they were constructed. provide(layer, task) explicitly binds provision to the program. By contrast, const users = inject Users captures an implementation value: later nested overrides do not rewrite that value. Make both rules visible in the specification.

Child fibers should inherit the appropriate Context while keeping Effect’s supervision and Scope rules. Resuming a continuation under a nested provider must follow the selected delimited-control context rule; a raw JavaScript callback should not accidentally resume under a different request’s services. This is one reason DI and continuation semantics must be designed together.

The TypeScript ABI should be ordinary Effect DI

UsersLive has no setup failure in this particular example because it only captures Database during acquisition; its query errors belong to find. A real acquisition body may add failures and requirements. TypeScript consumers can use the exported key, an ordinary Layer, and Effect.provide; TypeScript-authored Effect providers can satisfy the generated service too. Do not introduce a second DI container beside Effect.

Errors and schemas

Schemas are a separate design axis. Option A keeps Effect Schema as the source of truth and derives TS types. Option B makes suitable language data declarations reifiable and generates schemas. Option C uses explicit derive calls over a checked type. Arbitrary TS types—functions, conditional types, opaque classes, cyclic identities—do not all have a meaningful JSON decoder. Start with a defined reifiable subset and report unsupported cases.

12 / Syntax should protect the runtime model

Resources and concurrency stay structured

The quotation boundaries ensure that the branches remain cold until the concurrency combinator starts them. Define success, failure, sibling interruption, joining, and finalization through Effect combinators, not Promise.all. Ordinary calls remain sequential; concurrency must be visible.

Scope, quotation, acquisition, and child-work constructs need precise ownership rules. Register release immediately after successful acquisition; cover cancellation races. Define finalizer failure policy, usually defects/Cause-level reporting rather than casually adding recoverable E. A task must not outlive a resource it captures unless ownership is explicitly transferred.

Structured concurrency does not prove resource lifetime safety for arbitrary closures or mutable objects. If v0 does not enforce non-escape, document that limit and diagnose clear escapes. A native child-fiber construct needs a parent Scope, a join policy, and error reporting; detached launches belong at an explicit application boundary, not as a hidden adapter behavior.

13 / A valuable but separate choice

How far should user-defined handlers go?

The handler contract must define operation result types, handler answer types, resumption ownership, and abandonment behavior. This API is a proposal rather than an existing Effect feature. A compiler-owned operation interpreter must implement it and preserve Context and Scope behavior.

Tail-resumptive operationsHandlers compute an operation’s result and immediately continueMany service-like operations; optimize with ordinary Effect-returning methods

The maintainer’s advice is most useful as an implementation discipline: define suspension, resumption, and unwinding first. It does not force every application author to manipulate a continuation, or force a custom scheduler before the first language experiment.

14 / Architecture and emitted TypeScript

Fork the Go compiler with a narrow seam

The old microsoft/typescript-go staging repository is archived and directs development back to microsoft/TypeScript. The current repository exposes the Go compiler under tsc/. Choose the maintained native compiler lineage and pin a specific revision; do not start from the archived staging tree by habit. [7] [8]

An external Go package cannot freely import another module’s internal compiler packages. Keep the language integration inside the compiler fork or expose a deliberate narrow protocol/API from it. Vibelang already documents this seam; that architectural lesson is directly reusable. [9] [10]

A concrete lowering

Generators are a reasonable first backend for straight-line code and loops. Lower typed try/catch, finally, early exits across scopes, and custom handlers through explicit CFG regions; a global substitution of calls with yield is inadequate. Later backends can emit flatMap chains or state machines from the same IR. Benchmark before claiming an allocation or speed improvement.

Compiling to TypeScript buys ecosystem compatibility, not automatic access to every TypeScript tooling benefit in the source language. Map generated TS diagnostics to original spans, extend LSP hovers and completions, preserve declarations, compose JS source maps, and test package exports and incremental invalidation. TypeScript-generated .d.ts can carry a real Effect ABI, but compiler-only foreign and calling-mode metadata needs its own stable representation.

The local effect-tsgo checkout already demonstrates native checker hooks, Effect-specific diagnostics, and v3/v4 awareness. Reuse its knowledge of actual Effect types and its diagnostic patterns where practical. A language service that lints Effect is useful prior art; it is not by itself a language lowering pipeline. 15 / Architecture, without inheriting every choice

What to borrow from your Vibelang

I found smithersai/vibelang and the live vibelang.sh documentation. The current specification makes functions eager, uses must-use Result values for expected failures, infers nominal requirements, and keeps imported .ts/.tsx semantics intact. Its async functions stay Promise-based. These are explicit current choices, not an Effect runtime hiding under the syntax. [12] [13]

Its older language spike explicitly reports gaps in methods, aliases, higher-order calls, row polymorphism, and source maps. That is good evidence for using the real checker and a typed control-flow IR rather than extending a source-rewrite prototype indefinitely. The current normative generic Result model supersedes older syntax experiments. [14]

A useful split: Vibelang informs compiler architecture and foreign-boundary discipline; Effect supplies the execution model. Native bytecode and distributed durability would be separate projects. Neither follows automatically from compiling an Effect program or capturing a continuation.

  • Existing Effect service: import a generic, overloaded, aliased TS Effect function; compose it without changing E/R; supply a Layer in ordinary TS.
  • Provider graph: shared database acquisition, two dependent services, fake overrides, setup failure, a missing provider, an ambiguous provider, and a cycle; verify setup dependencies do not leak to callers.
  • Resourceful retry: acquire, fail, finalize, retry with fresh locals, then cancel during a later attempt; release exactly once per acquisition.
  • Callback-heavy program: pure Array.map, rejecting a suspending sort comparator, effect-aware traversal, and a Promise callback bridge with captured context.
  • Program as data: store, return, retry, and concurrently compose a cold Effect without accidentally running it or flattening nested values.
  • One-shot handler: nested prompts, one resumption, rejected double resumption, abort without resumption, and finalization during abandonment.

Evaluate line count, repeated annotations, calling-mode clarity, emitted ABI readability, quality of failure diagnostics, callback surprises, formatting round trips, and runtime allocation/fairness.

Foreign-call adapter checks should cover synchronous throw, Promise rejection, receiver binding, AbortSignal, retained callbacks, and unknown-versus-named-opacity diagnostics.

What the first compiler slice should contain

A version-pinned Go compiler fork, uniform function semantics, typed service and provider composition, inferred contracts and explicit Effect<A, E, R> annotations, real Effect imports, cold program quotation, source-mapped diagnostics, and actual .d.ts output. Add typed catch and resource scopes through CFG regions; demonstrate one-shot handler behavior separately before claiming general delimited control.
